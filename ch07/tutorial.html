第 7 章

OAuth2 与 OpenID Connect

让第三方应用替你办事，但只给它办这件事所需要的权限——而不是把家门钥匙整串交出去。

前几章里，Natter 的令牌都是"你自己"用的：你登录，拿到令牌，用它访问自己的账号。但如果你想让一个 第三方记账 App 帮你统计 Natter 里的消息数量，或者让一个自动化脚本代表你发帖，你要怎么给它权限？ 最简单粗暴的办法是把自己的用户名密码告诉它——这正是第 3 章努力避免的事情：密码一旦泄露给别人， 别人就能做你能做的所有事，包括你压根不想让它做的事（比如删除空间、拉黑成员）。

更好的类比是酒店代客泊车：你把车钥匙交给泊车员，但给的是一把"阀门钥匙"（valet key）——它只能 发动车子、把车开进车库，却打不开后备箱，也开不了车载保险柜。OAuth2 要解决的正是这个问题： 如何签发一把只能做"泊车"这件事的钥匙，而不是把车主的万能钥匙整串交出去。这一章你会看到 Natter 如何先给令牌加上"作用域"（scope）限制它能做什么，然后把令牌的签发工作整个外包给一个专门的 授权服务器（Authorization Server，AS），Natter 自己则退居为只负责校验令牌、 执行业务逻辑的资源服务器（Resource Server，RS）。本章不会教你自己实现一个 AS （这超出了本书范围，通常会用现成的 AS 软件，例如 Keycloak、Auth0、ForgeRock 等），而是教你如何 让 Natter 这个 API 正确地和外部 AS 打交道。

7.1作用域令牌（Scoped Token）

令牌不再是"要么全给、要么不给"的开关，而应该像酒店钥匙卡一样，可以设置成"只能开 302 房间和健身房， 开不了别的房间"。在 OAuth2 里，这种限制就叫作用域（scope），它是附加在令牌上的 一个或多个字符串标签，描述这个令牌能被用来做哪些操作。

💡 什么是 scope

scope（作用域）是绑定在令牌上的字符串标签，用来限定持有这个令牌的调用方能执行哪些 API 操作。 一个令牌可以同时带多个 scope，用空格分隔，例如 "create_space post_message" 表示这个令牌只能用来创建空间和发消息，不能删除消息、不能拉黑成员。

7.1.1 给 Natter 加上作用域令牌

要给 Natter 加上 scope 支持，需要改两处代码：登录接口在签发令牌时把调用方请求的 scope 写进令牌属性， 以及一个新的访问控制过滤器，在每个受保护的接口前检查令牌是否带着这次操作所需要的 scope。

⚠️ 一个容易踩的坑：权限升级

如果任何持有令牌的调用方都能直接调用 /sessions 登录接口去换一个 scope 更大的新令牌，那 scope 限制就形同虚设——拿着"只能读消息"的令牌一样能换出"删除消息" 的令牌。解决办法是给登录接口本身也加一个 scope 要求（比如 full_access）， 只有已经拥有全权限令牌（或者直接用用户名密码做 Basic 认证）的调用方才能签发新令牌。

ch07/.../controller/TokenController.java（节选）
private static final String DEFAULT_SCOPES =
        "create_space post_message read_message list_messages " +
                "delete_message add_member";

public JSONObject login(Request request, Response response) {
    String subject = request.attribute("subject");
    var expiry = now().plus(10, ChronoUnit.MINUTES);

    var token = new TokenStore.Token(expiry, subject);
    var scope = request.queryParamOrDefault("scope", DEFAULT_SCOPES);
    token.attributes.put("scope", scope);
    var tokenId = tokenStore.create(request, token);

    response.status(201);
    return new JSONObject().put("token", tokenId);
}

public Filter requireScope(String method, String requiredScope) {
    return (request, response) -> {
        if (!method.equalsIgnoreCase(request.requestMethod()))
            return;

        var tokenScope = request.<String>attribute("scope");
        if (tokenScope == null) return; // 未走 OAuth2，放行给下一层权限检查

        if (!Arrays.asList(tokenScope.split(" "))
                .contains(requiredScope)) {
            response.header("WWW-Authenticate",
                    "Bearer error=\"insufficient_scope\"," +
                            "scope=\"" + requiredScope + "\"");
            halt(403);
        }
    };
}
spaces/permissions.py（教学示例，配合 django-oauth-toolkit）
from rest_framework.permissions import BasePermission

DEFAULT_SCOPES = ("create_space post_message read_message "
                   "list_messages delete_message add_member")

class HasScope(BasePermission):
    """要求当前请求携带的 OAuth2 access token 拥有 required_scope。"""
    required_scope: str = None

    def has_permission(self, request, view):
        # django-oauth-toolkit 会把校验通过的 token 挂在 request.auth 上
        token_scope = getattr(request.auth, "scope", None)
        if token_scope is None:
            # 没走 OAuth2（比如内部服务用 Basic 认证），交给别的权限类判断
            return True
        return self.required_scope in token_scope.split(" ")

class RequireCreateSpaceScope(HasScope):
    required_scope = "create_space"

import { createMiddleware } from 'hono/factory'
import { HTTPException } from 'hono/http-exception'

export const requireScope = (method: string, requiredScope: string) =>
  createMiddleware(async (c, next) => {
    if (c.req.method !== method) return next()

    // 校验 access token 的中间件（见 7.4 节）会把 scope 写进 context
    const tokenScope = c.get('scope') as string | undefined
    if (!tokenScope) return next() // 没有 scope，交给下一层判断

    if (!tokenScope.split(' ').includes(requiredScope)) {
      c.header('WWW-Authenticate',
        `Bearer error="insufficient_scope", scope="${requiredScope}"`)
      throw new HTTPException(403, { message: 'insufficient_scope' })
    }
    return next()
  })

7.1.2 scope 和 permission 有什么区别

到这里你可能会问：第 3 章不是已经用访问控制列表（ACL）实现了权限（permission）吗？scope 和 permission 看起来都是"限定能做什么"，为什么要搞两套？关键区别在于谁来决定。

Natter 空间里"谁对哪条消息有读/写/删权限"，是由系统管理员或者空间的创建者决定的——普通用户 改不了自己的权限，这叫强制访问控制（Mandatory Access Control，MAC）。而 scope 恰恰相反：是用户自己决定要把多少权限委托给第三方 App，这叫自主访问 控制（Discretionary Access Control，DAC）。你可以把 Google Fit 想象成一个例子： 系统管理员规定了你的账号本身能访问哪些接口（permission），但当你连接一个第三方健身 App 时， 是你自己在同意界面上勾选"只分享步数，不分享心率"（scope）。

还有一个更实际的区别：permission 通常精确到具体的对象（这条消息、那个空间），而 scope 通常只 精确到"能调用哪个操作"，至于操作范围内具体能看到哪些数据，还是要看这个用户自己的 permission。 也就是说 scope 和 permission 经常是叠加生效的两层限制——一个第三方 App 即使有 read_message scope，也只能读到用户自己有权限读的消息，不会因为 拿到令牌就突破了原有的 ACL。

7.2OAuth2 简介

让用户手动创建 scope 令牌（就像上一节那样）虽然可行，但很容易出错：用户可能不知道一个 App 到底 需要哪些 scope，要么给少了导致 App 用不了，要么干脆全给省事。更好的方式是反过来——由 App 告诉 Natter 它需要哪些 scope，再由 Natter 问用户"同意还是不同意"。这正是 OAuth2 委托授权协议 的核心思路，而承担"问用户、发令牌"这件事的专门角色，就是授权服务器（AS）。

💡 OAuth2 里的四个角色

授权服务器（AS）：认证用户、征求同意、签发令牌的中心服务。
资源拥有者（Resource Owner，RO）：也就是用户本人，他拥有被访问的数据。
客户端（Client）：想要访问 API 的第三方 App 或服务。
资源服务器（Resource Server，RS）：托管用户资源的 API——在本章里，就是 Natter 自己。Natter 不再自己发令牌，而是向 AS 求证令牌是否有效。

7.2.1 客户端的两种类型

客户端要先在 AS 上注册，拿到一个 client ID，才能申请令牌。根据它是否能安全保管密钥，OAuth2 把客户端分成两类：

  • 公开客户端（Public Client）：完全跑在用户设备里的应用，比如手机 App 或者浏览器里的 JavaScript 单页应用。用户能拆开 App 拿到里面的任何"秘密"，所以公开客户端 不能持有 client secret。
  • 机密客户端（Confidential Client）：跑在受保护服务器上、用户碰不到的应用， 比如一个传统的服务端 Web 应用。它可以持有 client secret（或者更安全的 JWT / TLS 客户端证书）， 用来向 AS 证明"我是谁"。

7.2.2 授权许可类型（Grant Type）

客户端要先拿到用户的授权许可，才能去 AS 的 token 端点换令牌。常见的许可类型有：

  • Resource Owner Password Credentials（ROPC）：用户直接把用户名密码交给 客户端，客户端拿着密码去 AS 换令牌。这几乎和你在前几章写的登录接口一样，本质上还是把密码 暴露给了第三方，不推荐用于第三方客户端，未来可能被标准废弃。
  • Authorization Code（授权码许可）：客户端把用户的浏览器带到 AS 的授权 端点，AS 直接认证用户并征求同意，成功后把一个一次性的"授权码"交给客户端，客户端再拿这个 码去换令牌。这是本章 7.3 节的重点，也是目前最推荐的方式。
  • Client Credentials：客户端用自己的身份去换令牌，不涉及任何用户， 常用于服务间调用（第 11 章会细讲）。
  • 还有一些更专门的许可类型，比如面向没有浏览器的设备的 Device Authorization Grant （第 13 章会讲）。
⚠️ 已经过时的 Implicit Grant

早期 OAuth2 还定义过一种 Implicit Grant：AS 直接从授权端点把 access token 塞进重定向 URL 的 fragment 里返回给客户端，省去了换码这一步。这是 2012 年 CORS 还没普及时的权宜之计—— 浏览器脚本当时没法跨域调用 token 端点。现在 CORS 已经广泛支持，implicit grant 不再必要， 而且令牌暴露在 URL 里更容易被恶意脚本、浏览器历史记录、Referer 头泄露，官方安全实践文档 已经不建议使用它了。

7.2.3 发现 OAuth2 端点

OAuth2 标准并没有规定 AS 的授权端点、token 端点必须叫什么路径，不同 AS 软件可能各不相同。 为了不让每个客户端都硬编码这些地址，标准定义了一个"发现文档"：向 AS 根路径下的 /.well-known/oauth-authorization-server（如果 AS 同时支持 OpenID Connect，也可能是 /.well-known/openid-configuration） 发一个 GET 请求，就能拿到一份 JSON，里面列出了所有端点地址： 

GET https://as.example.com:8443/.well-known/oauth-authorization-server

{
  "authorization_endpoint": "https://as.example.com:8443/oauth2/authorize",
  "token_endpoint": "https://as.example.com:8443/oauth2/access_token",
  "introspection_endpoint": "https://as.example.com:8443/oauth2/introspect",
  "revocation_endpoint": "https://as.example.com:8443/oauth2/token/revoke",
  "jwks_uri": "https://as.example.com:8443/oauth2/jwks"
}
⚠️ 只能从可信来源获取发现文档

因为客户端接下来会把凭证和令牌发到这份文档里列出的各个地址，所以务必只通过 HTTPS 从 受信任的 URL 获取发现文档，否则攻击者篡改发现文档就能把你的凭证和令牌都骗到自己的服务器。

7.3授权码许可（Authorization Code Grant）

虽然 OAuth2 支持好几种许可类型，但对绝大多数客户端来说，最安全、最通用的选择都是 授权码许可——不管是服务端 Web 应用、单页应用，还是手机 App、命令行工具， 官方现在都推荐统一走这条路径。下面这张图把完整流程画了出来，重点看每一步 URL 里带的参数 是怎么变化的，这正是 PKCE 要保护的地方。

7.3.1 不同客户端类型的重定向 URI

对公开客户端来说，重定向 URI 几乎是 AS 唯一能确认"授权码要发给正确的客户端"的依据，所以它必须 提前在 AS 上注册好，AS 只会重定向到预先登记过的地址——这能防止开放重定向攻击 （攻击者诱导 AS 把用户重定向到自己控制的域名，实施钓鱼）。不同类型的客户端选择也不一样：

  • 服务端 Web 应用：一个专门的服务端路由，比如 /callback，直接接收授权码。
  • 单页应用（SPA）：重定向回应用自己的页面，前端 JS 从 URL 上取出授权码， 再用 CORS 请求调用 token 端点。
  • 手机 App：两种做法——注册一个私有 URI scheme（如 myapp://callback）， 或者更安全的"已认领的 HTTPS 重定向 URI"（Android 上叫 App Links，iOS 上叫 Universal Links）， 后者需要在网站根目录发布一份 JSON 文件证明这个域名授权给这个 App 处理该路径，从而避免恶意 App 抢注同名 scheme。
  • 桌面 / 命令行应用：因为桌面系统普遍不支持"已认领的 HTTPS URI"，推荐做法是 启动一个监听在 http://127.0.0.1 随机端口上的临时本地服务器， 拿到授权码后就关掉。
🎯 私有 URI scheme 被抢注

任何 App 都可以向操作系统注册处理某个 URI scheme，如果一台设备上同时装了你的正版 App 和一个 恶意 App，两者都注册了 myapp://，AS 重定向回这个 scheme 时， 操作系统可能把授权码送到恶意 App 手里，恶意 App 就能拿着这个码去换出属于受害者的 access token。 这正是 PKCE 要防的攻击场景之一。

7.3.2 用 PKCE 加固授权码交换

在授权码穿越浏览器重定向的过程中，它有可能被同一浏览器里的恶意脚本偷走，或者出现在服务器访问 日志、浏览器历史、Referer 头里。PKCE（Proof Key for Code Exchange，念作 "pixy"）的思路很简单：客户端在发起授权请求之前，先在本地生成一个高熵的随机字符串 code_verifier，对它做 SHA-256 哈希得到 code_challenge，把 challenge（而不是 verifier 本身）带在授权 请求里发给 AS。等到真正拿授权码换令牌的时候，客户端才把原始的 code_verifier 发给 AS，AS 重新 计算一遍哈希，和当初收到的 code_challenge 比对——一致才发放令牌。攻击者即便截获了授权码， 因为算不出正确的 code_verifier，也换不出 access token。

✅ 一律使用 PKCE

PKCE 最初是为了保护公开客户端设计的，但对机密客户端同样有额外的安全收益（能防御一类利用 XSS 窃取授权码后"顶包"的理论攻击）。OAuth2 安全最佳实践现在建议所有类型的客户端 都默认加上 PKCE，即便你的 AS 不支持它，多出来的参数标准也要求 AS 直接忽略，不影响兼容性。

String addPkceChallenge(spark.Request request,
        String authorizeRequest) throws Exception {

    var secureRandom = new java.security.SecureRandom();
    var encoder = java.util.Base64.getUrlEncoder().withoutPadding();

    var verifierBytes = new byte[32];
    secureRandom.nextBytes(verifierBytes);
    var verifier = encoder.encodeToString(verifierBytes);

    request.session(true).attribute("verifier", verifier);

    var sha256 = java.security.MessageDigest.getInstance("SHA-256");
    var challenge = encoder.encodeToString(
            sha256.digest(verifier.getBytes("UTF-8")));

    return authorizeRequest +
            "&code_challenge=" + challenge +
            "&code_challenge_method=S256";
}

import { getCookie, setCookie } from "hono/cookie"
import { HTTPException } from "hono/http-exception"

app.get("/oauth/callback", async (c) => {
  const state = c.req.query("state")
  const code = c.req.query("code")
  const storedState = getCookie(c, "oauth_state")
  const codeVerifier = getCookie(c, "oauth_verifier")

  if (!state || state !== storedState) {
    throw new HTTPException(400, { message: "state mismatch" })
  }

  const tokens = await client.validateAuthorizationCode(
    "https://as.example.com:8443/oauth2/access_token",
    code!,
    codeVerifier! // arctic 用它重算 code_challenge 完成 PKCE 校验
  )
  setCookie(c, "natter_access_token", tokens.accessToken(),
    { httpOnly: true, secure: true })
  return c.redirect("/dashboard")
})

7.3.3 刷新令牌（Refresh Token）

AS 除了返回 access token，通常还会返回一个刷新令牌（refresh token）。 access token 过期后，客户端可以拿 refresh token 直接换一个新的，不用再让用户重新走一遍登录 + 同意的流程。因为 refresh token 只在客户端和 AS 之间的私密通道里传输（从不发给资源服务器）， 它的安全性比到处传递的 access token 更高。

💡 为什么要限制 access token 的有效期

Refresh token 的存在让 AS 可以把 access token 的有效期设得很短（比如几分钟到一小时），这样即使 access token 被偷，能造成的损失也被限制在很短的时间窗口内。这一点对于下一节要讲的"自包含 JWT access token"尤其重要——因为 JWT 一旦签发，在过期之前几乎无法主动撤销，靠短有效期 + 频繁刷新 才能把"撤销"这件麻烦事转嫁给客户端。

7.4校验访问令牌

前几章里，Natter 直接管理自己的令牌数据库，校验令牌只是一次本地查询。现在令牌由外部 AS 签发， Natter 该怎么知道一个 access token 到底有没有效、绑定了哪些 scope？直接共享 AS 的令牌数据库 是个坏主意——任何接进这个数据库的系统都会成为新的攻击面，一旦某个 API 有 SQL 注入漏洞，整个 令牌体系都会被牵连。OAuth2 给出了两条正统路径：Token Introspection（每次 向 AS 问一遍）和本地校验 JWT 格式的 access token（自己验签，不用问 AS）。

7.4.1 Token Introspection

Token Introspection 标准定义了一个 AS 上的 HTTP 端点：资源服务器把 access token 当参数 POST 过去，AS 回一段 JSON，告诉你这个令牌是否 active，以及 它的 scope、所属用户（sub）、过期时间等信息。RS 通常也要先在 AS 上注册成一种特殊客户端，拿到自己的 client_id/secret 才能调用这个端点。

字段含义
active令牌是否仍然有效，唯一必填字段
scope令牌的作用域，多个 scope 用空格分隔
sub资源拥有者（用户）的唯一标识
username用户的可读用户名
client_id请求这个令牌的客户端 ID
exp过期时间（UNIX 秒）

public OAuth2TokenStore(URI introspectionEndpoint,
        String clientId, String clientSecret) {
    this.introspectionEndpoint = introspectionEndpoint;

    var credentials = URLEncoder.encode(clientId, UTF_8) + ":" +
            URLEncoder.encode(clientSecret, UTF_8);
    this.authorization = "Basic " + Base64.getEncoder()
            .encodeToString(credentials.getBytes(UTF_8));

    var sslParams = new SSLParameters();
    sslParams.setProtocols(new String[] { "TLSv1.3", "TLSv1.2" });
    sslParams.setCipherSuites(new String[] {
            "TLS_AES_128_GCM_SHA256", "TLS_AES_256_GCM_SHA384",
            "TLS_CHACHA20_POLY1305_SHA256",
            "TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256",
            "TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256"
            // ...省略其余允许的密码套件
    });
    sslParams.setUseCipherSuitesOrder(true);
    sslParams.setEndpointIdentificationAlgorithm("HTTPS");

    // 只信任签发 AS 证书的那一张私有 CA，而不是所有公共 CA
    var trustedCerts = KeyStore.getInstance("PKCS12");
    trustedCerts.load(new FileInputStream("as.example.com.ca.p12"),
            "changeit".toCharArray());
    var tmf = TrustManagerFactory.getInstance("PKIX");
    tmf.init(trustedCerts);
    var sslContext = SSLContext.getInstance("TLS");
    sslContext.init(null, tmf.getTrustManagers(), null);

    this.httpClient = HttpClient.newBuilder()
            .sslParameters(sslParams).sslContext(sslContext).build();
}

@Override
public Optional<Token> read(Request request, String tokenId) {
    if (!tokenId.matches("[\\x20-\\x7E]{1,1024}")) {
        return Optional.empty();
    }
    var form = "token=" + URLEncoder.encode(tokenId, UTF_8) +
            "&token_type_hint=access_token";

    var httpRequest = HttpRequest.newBuilder()
            .uri(introspectionEndpoint)
            .header("Content-Type", "application/x-www-form-urlencoded")
            .header("Authorization", authorization)
            .POST(BodyPublishers.ofString(form)).build();

    var httpResponse = httpClient.send(httpRequest, BodyHandlers.ofString());
    if (httpResponse.statusCode() == 200) {
        var json = new JSONObject(httpResponse.body());
        if (json.getBoolean("active")) {
            return processResponse(json);
        }
    }
    return Optional.empty();
}

private Optional<Token> processResponse(JSONObject response) {
    var expiry = Instant.ofEpochSecond(response.getLong("exp"));
    var subject = response.getString("sub");
    var token = new Token(expiry, subject);
    token.attributes.put("scope", response.getString("scope"));
    token.attributes.put("client_id", response.optString("client_id"));
    return Optional.of(token);
}

src/token/introspection.ts
import { Agent, fetch } from "undici"

// 只信任签发 AS 证书的私有 CA，锁定 TLS 版本
const asAgent = new Agent({
  connect: { ca: caCertPem, minVersion: "TLSv1.2" },
})

const TOKEN_RE = /^[\x20-\x7E]{1,1024}$/

export async function introspect(token: string) {
  if (!TOKEN_RE.test(token)) return null

  const credentials = Buffer.from(
    `${env.OAUTH_CLIENT_ID}:${env.OAUTH_CLIENT_SECRET}`
  ).toString("base64")

  const res = await fetch(env.OAUTH_INTROSPECTION_ENDPOINT, {
    method: "POST",
    headers: {
      "content-type": "application/x-www-form-urlencoded",
      authorization: `Basic ${credentials}`,
    },
    body: new URLSearchParams({ token, token_type_hint: "access_token" }),
    dispatcher: asAgent,
  })
  if (res.status !== 200) return null

  const body = await res.json() as any
  if (!body.active) return null
  return { subject: body.sub, scope: body.scope ?? "", clientId: body.client_id }
}

💡 别忘了这些细节

令牌在被使用之前是"不可信输入"，务必先校验格式再拼进请求体（比如限制字符集和最大长度，通常 1KB 足够，JWT 格式的令牌可能需要放宽）。发起 introspection 调用消耗一次网络往返，可以按 令牌值短期缓存响应结果，但缓存时间越长，撤销令牌生效的延迟也越大，需要按你的威胁模型权衡。 另外，AS 和 API 必须对"用户是谁"有一致的认识——如果两边用户库不同（比如 AS 返回邮箱、 本地库用用户名），API 需要一层映射逻辑，否则 introspection 校验通过了，ACL 却查不到人。

7.4.2 加固 HTTPS 客户端配置

因为整条信任链最终都系在"RS 和 AS 之间这条 HTTPS 连接是否可信"上，Java 默认的 HTTPS 客户端 设置并不够严格：默认信任所有公共 CA（而 AS 通常只由你组织内部的私有 CA 签发证书），默认允许 一大堆为了兼容性保留的老旧密码套件和协议版本。上面 Java 代码里已经展示了如何用 SSLParameters 只允许 TLS 1.2/1.3 和前向保密的密码套件，并用 只包含私有 CA 的 KeyStore 构建专属的 TrustManager。 Django/Node 生态里没有内建等价物，但 requests/httpx 的 verify= 参数、Node 的 undici.Agent({connect:{ca,minVersion}}) 能实现同样的效果，如上面 Python/JS 代码所示。

7.4.3 令牌撤销

OAuth2 撤销标准同样定义了一个 AS 端点，但和 introspection 不同的是：只有获得这个 令牌的客户端本人，才能调用它撤销令牌——资源服务器无权代替客户端撤销令牌。所以撤销 逻辑应该写在客户端里（比如用户点击"退出登录"时），而不是资源服务器的 /sessions DELETE 接口里。

7.4.4 JWT 访问令牌：不用每次都问 AS

Token Introspection 有个明显的代价：每次请求都要多一次到 AS 的网络往返。如果 access token 本身就是一个自包含的 JWT（第 6 章学过），RS 完全可以自己验证签名、读出声明，不用打这通电话。 要注意的是：JWT access token 应该用非对称签名（AS 持有私钥签名，RS 只持有 公钥验签），而不是像第 6 章里那样用共享的 HMAC 密钥——因为一旦 AS 和 RS 不在同一个信任边界内 （比如分属不同数据中心/不同团队），任何能验证签名的一方，用对称密钥的话也同时具备了伪造签名 的能力，这就破坏了"最小权限"原则。

ch07/.../token/SignedJwtAccessTokenStore.java（节选）
public SignedJwtAccessTokenStore(String expectedIssuer,
                                 String expectedAudience,
                                 JWSAlgorithm signatureAlgorithm,
                                 URI jwkSetUri) throws MalformedURLException {
    this.expectedIssuer = expectedIssuer;
    this.expectedAudience = expectedAudience;
    this.signatureAlgorithm = signatureAlgorithm;
    this.jwkSource = new RemoteJWKSet<>(jwkSetUri.toURL());
}

@Override
public Optional<Token> read(Request request, String tokenId) {
    try {
        var verifier = new DefaultJWTProcessor<>();
        var keySelector = new JWSVerificationKeySelector<>(
                signatureAlgorithm, jwkSource);
        verifier.setJWSKeySelector(keySelector);

        var claims = verifier.process(tokenId, null); // 先验签

        if (!expectedIssuer.equals(claims.getIssuer())) {
            return Optional.empty();
        }
        if (!claims.getAudience().contains(expectedAudience)) {
            return Optional.empty();
        }

        var expiry = claims.getExpirationTime().toInstant();
        var subject = claims.getSubject();
        var token = new Token(expiry, subject);

        String scope;
        try {
            scope = claims.getStringClaim("scope");
        } catch (ParseException e) {
            // 有些 AS 把 scope 编码成字符串数组而不是空格分隔的字符串
            scope = String.join(" ", claims.getStringListClaim("scope"));
        }
        token.attributes.put("scope", scope);
        return Optional.of(token);

    } catch (ParseException | BadJOSEException | JOSEException e) {
        return Optional.empty();
    }
}

import jwt
from jwt import PyJWKClient

EXPECTED_ISSUER = "https://as.example.com:8443/"
EXPECTED_AUDIENCE = "https://natter.example.com/"

# PyJWKClient 内置了远端 JWK Set 缓存 + 定期刷新

def validate_jwt_access_token(token: str) -> dict | None:
    try:
        signing_key = _jwk_client.get_signing_key_from_jwt(token)
        claims = jwt.decode(
            token,
            signing_key.key,
            algorithms=["ES256"],       # 严格限定算法，防止算法混淆攻击
            issuer=EXPECTED_ISSUER,
            audience=EXPECTED_AUDIENCE,

        return None

    scope = claims.get("scope", "")
    if isinstance(scope, list):
        scope = " ".join(scope)

    return {"subject": claims["sub"], "scope": scope, "exp": claims["exp"]}

import { createRemoteJWKSet, jwtVerify } from "jose"

const EXPECTED_ISSUER = "https://as.example.com:8443/"
const EXPECTED_AUDIENCE = "https://natter.example.com/"

// jose 会自动缓存并按需刷新 JWK Set
const JWKS = createRemoteJWKSet(
  new URL("https://as.example.com:8443/oauth2/jwks")
)

export async function validateJwtAccessToken(token: string) {
  try {
    const { payload } = await jwtVerify(token, JWKS, {
      issuer: EXPECTED_ISSUER,
      audience: EXPECTED_AUDIENCE,
      algorithms: ["ES256"], // 严格限定算法
    })
    const scope = Array.isArray(payload.scope)
      ? payload.scope.join(" ")
      : (payload.scope as string ?? "")
    return { subject: payload.sub!, scope, exp: payload.exp! }
  } catch {
    return null
  }
}

7.4.5 加密的 JWT 访问令牌

有时候 AS 想在令牌里塞一些 RS 需要、但不想让客户端或用户本人看到的私密信息（比如用户的邮箱）。 这时候就需要加密整个 JWT。麻烦的是，JOSE 标准里的公钥加密算法都不提供"认证加密"（既保密又防 篡改），所以必须先用签名算法签一遍，再用加密算法把整个签名 JWT 包起来，形成"先签名、再加密" 的嵌套结构，签名和加密要用两把不同的密钥。 

{"sub":"alice","iss":"https://as.example.com",...}
        │  ① 用签名私钥（ES256）签名
        ▼
eyJ0eXAiOiJKV1QiLCJhbGciOiJFUzI1NiJ9.eyJzdWIi...（一个完整的签名 JWT）
        │  ② 用加密公钥（ECDH-ES）加密整个签名 JWT
        ▼
eyJ0eXAiOiJKV1QiLCJlbmMiOiJBMjU2R0NNIiwiYWxnIjo...（嵌套的加密 JWT，即 JWE(JWS(claims))）

Natter 项目里的 EncryptedJwtTokenStore.java 展示了这个思路的一个 简化版：用单个对称密钥直接对 claims 做认证加密（DirectEncrypter）， 同时把令牌 ID 记进一张本地"白名单"表以便随时撤销——这其实更接近下一小节"让 AS 直接解密令牌"的 折中方案，而不是书里描述的非对称"先签名再加密"模式，实践中要按你的信任边界选择合适的做法。

7.4.6 让 AS 直接解密令牌

另一个思路是反过来：AS 用只有自己知道的对称密钥加密 access token，RS 不再本地验证，而是继续 调用 introspection 端点让 AS 帮忙解密校验。这样做的好处是令牌格式完全由 AS 内部决定、可以 随时调整，RS 完全不用关心具体格式；坏处当然是又变回了"每次都要问 AS"的网络开销。在微服务 场景下（第 11 章会展开），这种把令牌格式封装在 AS 内部的思路往往更利于系统演进。

7.5单点登录

把认证这件事集中到 AS 之后，一个很自然的副产品就是单点登录（Single Sign-On，SSO）：客户端需要令牌时，把用户重定向到 AS；AS 认证用户、记录一个会话 Cookie。 用户之后再用另一个客户端（哪怕是完全不同厂商开发的 App，只要它们都用系统浏览器发起 OAuth 流程），AS 会看到这个已有的会话 Cookie，不用重新登录就能直接征求同意（甚至如果之前已经同意过 相同 scope，可以直接跳过同意页）。多个资源服务器也都只需要对着同一个 AS 做 token introspection，天然地统一了认证入口。

⚠️ 不要为了省事复用同一个 access token

虽然把同一个 access token 分发给多个不同 API 用起来很方便，但这会放大令牌被盗后的影响面。 应该给每个不同的 API 签发独立的 access token（哪怕它们背后是同一个 AS、同一次登录会话）。

7.6OpenID Connect

OAuth2 本身关注的是"third party 能不能替用户做某件事"，并不严格保证"用户真的刚刚登录过"， 也没有标准化的方式获取用户的姓名、邮箱这些身份信息。OpenID Connect（OIDC） 在 OAuth2 之上加了一层，补上这块拼图：一个标准的 UserInfo 接口、一套表达"用户是如何被认证的" 的声明，以及登出通知机制。用 OIDC 术语来说，AS 和这个 UserInfo API 合并成了一个角色，叫 OpenID Provider（OP）；客户端这时被称为 Relying Party（RP）。

7.6.1 ID Token

如果严格按 OAuth2 流程拿用户身份信息，客户端要走三趟：换授权码、换 access token、再拿 access token 去调 UserInfo 接口。OIDC 提供了一个捷径——ID Token：一个签名（可选加密） 的 JWT，直接在 token 端点响应里和 access token 一起返回，里面已经带上了身份和认证过程的声明。

💡 什么是 ID Token

ID Token 是一个签名过的 JWT，用来证明"这个用户刚刚在 OP 那边完成了认证"，以及告诉客户端 这个用户是谁。它和 access token 长得很像（都是 JWT），但用途完全不同——这是本节最容易混淆 也最重要的一点，7.6.3 会详细展开。

声明含义
azpAuthorized Party，ID Token 最初签发给哪个 client_id
auth_time用户完成认证的时间戳
nonce客户端在发起请求时提供的随机值，回显在 ID Token 里防重放
acr认证强度等级（Authentication Context Class Reference）
amr具体用了哪些认证方式，如 ["password","otp"]

7.6.2 加固 OIDC

如果 ID Token 是通过重定向 URL 直接返回的（implicit / hybrid 流程），它同样面临和授权码一样 的泄露风险——被同页面的恶意脚本窃取、留在浏览器历史或 Referer 头里，甚至被截获后重放冒充别的 登录请求。最简单的防御和授权码许可一样：始终使用带 PKCE 的授权码许可，这样 ID Token 只会通过客户端和 OP 之间的直接 HTTPS 调用返回，不会出现在 URL 里。如果确实要用 hybrid 流程，还可以加上随机 nonce 参数防重放，或者要求 OP 加密 ID Token。

7.6.3 把 ID Token 传给 API

🚫 千万不要用 ID Token 做访问控制

ID Token 就像是用户名——它证明"这是谁"，但不代表"这个人允许你替他做什么"。access token 才像密码/钥匙——它才是被限定了 scope、真正用来访问 API 的凭证。如果你的 API 接受 ID Token 作为访问凭证，任何拿到过你签发的 ID Token 的第三方（哪怕只是为了"用 XX 登录"这么单纯的目的） 都能拿着它伪装成用户去访问你的 API，完全绕开了 scope 限制和用户同意——这正是"如果 Google 允许 用 ID Token 调用它自己的 API，那所有支持『用 Google 登录』的网站都能未经用户同意拿他的 Google 数据"这种攻击场景。

话虽如此，有些场景下 API 确实需要参考 ID Token 里的信息（比如要求用户"最近确实做过强认证"才能 发起一笔转账）。这种情况下，ID Token 只能作为 access token 之外的补充凭证， 访问控制的决定权始终在 access token 手里，ID Token 只是拿来读取一些附加的身份/认证强度信息。

tokens/id_token.py（教学示例）
from authlib.jose import jwt as authlib_jwt
from authlib.jose.errors import JoseError

EXPECTED_ISSUER = "https://as.example.com:8443/"
EXPECTED_AUDIENCE = "thirdPartyApp"

def validate_id_token(id_token: str, access_token_subject: str,
                       access_token_client_id: str | None):
    try:
        claims = authlib_jwt.decode(id_token, key=_op_public_key)
        claims.validate()  # 校验 exp/iat 等标准声明
    except JoseError:
        raise ValueError("invalid id token")

    if claims.get("iss") != EXPECTED_ISSUER:
        raise ValueError("invalid id token issuer")
    if EXPECTED_AUDIENCE not in claims.get("aud", []):
        raise ValueError("invalid id token audience")

    azp = claims.get("azp")
    if access_token_client_id and azp and azp != access_token_client_id:
        raise ValueError("client is not authorized party")

    # 访问控制仍然只看 access token；这里只是核对两者指向同一个用户
    if claims["sub"] != access_token_subject:
        raise ValueError("subject does not match id token")

    return claims
src/token/idToken.ts
import { createRemoteJWKSet, jwtVerify } from "jose"

const OP_JWKS = createRemoteJWKSet(new URL("https://as.example.com:8443/oauth2/jwks"))
const EXPECTED_ISSUER = "https://as.example.com:8443/"
const EXPECTED_AUDIENCE = "thirdPartyApp"

export async function validateIdToken(
  idToken: string,
  accessTokenSubject: string,
  accessTokenClientId?: string,
) {
  const { payload } = await jwtVerify(idToken, OP_JWKS, {
    issuer: EXPECTED_ISSUER,
    audience: EXPECTED_AUDIENCE,
  })

  if (accessTokenClientId && payload.azp && payload.azp !== accessTokenClientId) {
    throw new Error("client is not authorized party")
  }
  // 访问控制的决定权仍然在 access token 手里，这里只核对用户是同一个人
  if (payload.sub !== accessTokenSubject) {
    throw new Error("subject does not match id token")
  }
  return payload
}

本章小结

知识点要点
作用域令牌用 scope 字符串限定令牌能做什么，用户自己决定委托多少权限给第三方（DAC），区别于中心机构统一下发的 permission（MAC）
OAuth2 四角色AS 发令牌、RO 是用户、Client 是第三方应用、RS 是被访问的 API（本章里的 Natter）
授权码许可 + PKCE几乎所有客户端都应该走带 PKCE 的授权码许可；implicit grant 和裸的 ROPC 都不推荐
校验 access tokenToken Introspection 简单但每次都要问 AS；本地校验签名 JWT 更快但要用非对称签名，定期拉取公钥（JWK Set）
刷新令牌让 access token 保持短有效期，同时不打断用户体验；也是撤销发生的关键节点
令牌撤销只有拿到令牌的客户端本人才能调用标准撤销端点，RS 无权代为撤销
单点登录OAuth2 天然带来 SSO：多个客户端共享同一个 AS 会话，多个 API 共享同一个 introspection 端点
OpenID Connect在 OAuth2 上加一层标准化的用户身份层：ID Token 证明"你是谁"，access token 才能证明"你能做什么"，两者不能混用
