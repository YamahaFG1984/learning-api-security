第 9 章

基于能力的安全与 Macaroon

第 8 章教你按"这个人是谁、他在这个空间里是什么角色"来放行请求。可要是有人只想把一条消息分享给一个完全不属于这个空间的朋友呢？身份加角色表在这种场景下不够用——这一章教你换一种思路：把权限直接编码进一个"谁拿到谁能用"的链接里。

想象你去朋友家借一把伞。一种做法是朋友把你的名字写进一份"允许进门名单"，你到了门口，门卫翻名单确认你是谁、名单上写你能进哪几个房间——这是"身份 + 访问控制列表（ACL）"，也是第 8 章的做法。另一种做法是朋友直接把伞柜的钥匙给你，钥匙本身就只能开那一个柜子，谁拿着钥匙谁就能开，没人会先问"你是谁"。第二种就是这一章的主角：基于能力（capability）的安全。Natter 里最典型的场景是分享消息链接：如果只能靠"把对方拉进空间"才能分享一条消息，那对方就顺带拿到了这个空间里所有消息的权限，这违反了"最小权限原则（POLA，principle of least authority）"。能力 URI 能做到刚好只分享这一条消息。

9.1什么是"基于能力"的安全

💡 什么是能力（capability）

一个能力，就是"对某个资源的一份不可伪造的引用，外加一组访问它的权限"，两者绑在一起、缺一不可。书里举了 UNIX 的例子：cp a.txt b.txt 靠文件名操作，运行 cp 的进程必须拥有和你本人一样大的权限，才能打开任意你能打开的文件——这叫"身份/权限"模式，权限是环境赋予的（这被称为 ambient authority，环境自带的权限）。而 cat <a.txt >b.txt 靠的是两个已经打开的文件描述符（file descriptor），cat 本身完全不需要额外权限——文件描述符就是一种能力：它既指向具体的文件，又自带这份文件的读/写权限。

把这两种模式搬到 Web API 上来看：身份模式下，任何人都可以对一个 URL 发请求，服务器再决定"这个人有没有资格"；能力模式下，如果你手里根本没有那份能力（token），你连"尝试访问"这件事都做不成——请求要么带着有效的能力,要么就没有意义。这带来一个直接的安全好处：能力天然把权限收窄到"一个具体资源",分享一份能力,不等于分享你账号下所有资源的权限,这比"把别人拉进整个空间"或者"分享用户名密码"都更贴近最小权限。

⚠️ 什么是 confused deputy（糊涂的代理人）攻击

当一个拥有较高权限的程序被骗去替攻击者做事，就是"confused deputy"攻击——这个程序被当成了攻击者的"代理人"却浑然不知。最早的例子是一个共享编译器：它有权限写任意文件，用户提交任务时可以指定"结果写到哪个文件"，有人把这个参数指向了计费记录文件，编译器就"尽职尽责"地把计费记录覆盖掉了。第 4 章讲的 CSRF 就是同一类问题：浏览器保存着你的 session cookie，只要你打开一个恶意页面，浏览器会在请求里自动带上这个 cookie——这个 cookie 就是一种"环境自带的权限（ambient authority）"，服务器分不清这个请求到底是你本人发起的，还是被恶意页面骗着发的。能力安全的核心目标之一，就是尽量消灭这种"环境自动附加的权限"，改成"每次请求都必须明确带上它需要的那份授权"。

当然，能力也不是没有代价：一份能力一旦分享出去，服务器很难说清楚"到底谁现在拥有对这个资源的访问权"，撤销起来也不像撤销一个用户角色那么直观（这也是这一章要用 Macaroon 解决的问题之一）。但只要设计得当——比如允许把能力再收窄后转发给别人、支持随时吊销底层 token——这些顾虑大多可以化解。

9.2能力 URI：把权限编码进链接里

REST 已经有一种天然适合表达能力的格式：URI。既然 URI 本来就是用来"指向一个资源"的，那就顺手让它也带上"允许对这个资源做什么"的信息——这样的 URI 叫能力 URI（capability URI）。你其实每天都在用这种链接：找回密码邮件里的那条链接、GitHub Gist 的分享链接、云盘"任何人持有此链接即可查看"的分享链接，本质上都是能力 URI。

把一个随机 token 塞进 URI，常见的有四个位置：

  • 路径（path）：/resource/abCd9..，Dropbox 的 Chooser API 就是这么做的；
  • 查询参数（query）：/resource?access_token=abCd9..，RFC 6750 给这个参数定了标准名字 access_token；
  • 片段（fragment）：/resource#tok=abCd9..，# 后面的内容浏览器默认不会发给服务器；
  • userinfo 部分：https://abCd9..@api.example.com/resource，这是当年 HTTP Basic 认证挪用的位置。
⚠️ 路径和查询参数有泄漏风险

把 token 放进路径或查询参数，最容易实现，但也最容易被服务器/代理的访问日志记录下来；如果这条链接被网页直接渲染出来给用户点，还可能通过 Referer 头或 window.referrer 泄漏给第三方站点，或者留在浏览器历史记录里。这也是当年 http://alice:secret@example.com/ 这种"用户名密码写进 URL"的写法被浏览器厂商联手封杀的原因之一——攻击者甚至能拿它伪造出 http://www.google.com:80@evil.example.com/ 这样看起来像 google.com 的钓鱼链接。

✅ 但对 REST API 来说风险小得多

上面这些坑主要发生在"用户直接在浏览器地址栏里导航"的场景。API 返回的是 JSON，不会被浏览器当页面渲染，也就不会触发 Referer 泄漏或写入浏览器历史。所以本章后面统一采用最简单的方式——把 token 放进查询参数 access_token，再靠"短生命周期 + 和用户身份绑定"来兜底剩余的风险（见 9.2.5/9.2.6 节）。

在 Natter API 里生成和校验能力 URI

要生成一个能力 URI，本质上还是复用第 5、6 章已经写好的 SecureTokenStore：创建一条 token，把"这份能力对应哪个资源路径（path）""允许做什么（perms，读/写/删的组合）"存进 token 的属性里，再把生成的 token id 拼进 URL 的查询参数。和普通认证 token 不同的是：能力 token 不需要绑定一个具体用户（username 字段可以留空），因为它本来就不代表"你是谁"，只代表"这张票能干什么"。校验的时候，反过来：先按 access_token 查出 token，再核对 token 里记的路径是不是正好等于当前请求的路径——如果对得上，就把 token 里的 perms 写进 request 的属性里，交给后面和第 8 章一样的权限检查逻辑去用。下面这段 CapabilityController 的代码已经是本章末尾"和身份绑定"之后的最终版本（多了一行校验 username），后面 9.2.5 节会专门解释这一行的作用。

public URI createUri(Request request, String path, String perms,
                     Duration expiryDuration) {
    var subject = (String) request.attribute("subject");
    var token = new Token(now().plus(expiryDuration), subject);
    token.attributes.put("path", path);
    token.attributes.put("perms", perms);

    var tokenId = tokenStore.create(request, token);

    var uri = URI.create(request.uri());
    return uri.resolve(path + "?access_token=" + tokenId);
}

public void lookupPermissions(Request request, Response response) {
    var tokenId = request.queryParams("access_token");
    if (tokenId == null) { return; }

    tokenStore.read(request, tokenId).ifPresent(token -> {
        // 拿到 token 的人还必须是当初签发时认证过的那个用户，
        // 否则一律不给权限——这是 9.2.6 节"加固能力 URI"之后的效果。
        if (!Objects.equals(token.username, request.attribute("subject"))) {
            return;
        }
        var tokenPath = token.attributes.get("path");
        if (Objects.equals(tokenPath, request.pathInfo())) {
            request.attribute("perms", token.attributes.get("perms"));
        }
    });
}

# capabilities/tokens.py
from django.utils.crypto import get_random_string
from django.utils import timezone

def create_capability_uri(request, path, perms, ttl):
    token_id = get_random_string(30)
    CapabilityToken.objects.create(
        token_id=token_id,
        # 和 Java 版一样：把当前登录用户写进去，
        # 做"能力 + 身份"双重校验，而不是让任何人都能用这张 token。
        user=request.user if request.user.is_authenticated else None,
        path=path,
        perms=perms,
        expiry=timezone.now() + ttl,
    )
    return request.build_absolute_uri(path) + f"?access_token={token_id}"


# capabilities/middleware.py
class CapabilityMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        token_id = request.GET.get("access_token")
        if token_id:
            token = CapabilityToken.objects.filter(
                token_id=token_id, expiry__gt=timezone.now(),
            ).first()
            if token and token.user_id in (None, getattr(request.user, "id", None)):
                if token.path == request.path:
                    request.perms = token.perms
        return self.get_response(request)

// src/routes/capabilities.ts
// toBase64Url 是几行的小工具函数，把字节数组编码成 URL-safe base64，这里从略
function createCapabilityUri(c: Context, path: string, perms: string, ttlMs: number) {
  const tokenId = toBase64Url(crypto.getRandomValues(new Uint8Array(20)))
  db.insert(capabilityTokens).values({
    tokenId,
    userId: c.get('subject') ?? null,
    path,
    perms,
    expiry: new Date(Date.now() + ttlMs),
  }).run()

  const url = new URL(c.req.url)
  url.pathname = path
  url.search = `?access_token=${tokenId}`
  return url.toString()
}

// src/middleware/capability.ts
export async function lookupPermissions(c: Context, next: Next) {
  const tokenId = c.req.query('access_token')
  if (tokenId) {
    const token = db.select().from(capabilityTokens)
      .where(eq(capabilityTokens.tokenId, tokenId)).get()

    // token.userId 必须和当前登录用户一致，逻辑与 Java 版完全对应
    if (token && token.expiry > new Date() &&
        (token.userId === null || token.userId === c.get('subject'))) {
      if (token.path === new URL(c.req.url).pathname) {
        c.set('perms', token.perms)
      }
    }
  }
  await next()
}

9.2.3HATEOAS：响应体自己告诉你下一步能做什么

拿到 /spaces/1 的能力 URI 后，你会发现它其实用处有限：真正要读/发消息，得访问的是子资源 /spaces/1/messages，而能力 URI 天生"专款专用"——一份能力只认它对应的那一个资源，不能像身份模式下那样"反正是同一个 token，我自己在后面拼个 /messages 就行"。可能力又是不可伪造的，客户端没法凭空"造"出一个新的能力。

💡 什么是 HATEOAS

HATEOAS（Hypertext As The Engine Of Application State）是 REST 提出者 Roy Fielding 强调的核心原则：客户端不应该自己知道"怎么拼出下一个 URL"，而应该由服务器在响应里直接把链接给你，你只管点着走。这个原则和能力 URI 是绝配——服务器可以在一次响应里返回好几个指向不同子资源、带着不同权限的能力链接，客户端全程不用自己"猜"或"拼"URL，从一个能力"顺藤摸瓜"导航到下一个能力。

具体实现上，createSpace 一口气生成四份权限不同的能力 URI：一份对空间本身的完全权限，以及对 /messages 子资源的"读写删（rwd）""读写（rw）""只读（r）"三种权限，全部作为普通字段塞进响应 JSON。这样空间主人可以把权限最大的链接留给自己和管理员，把只读链接分享给外人。findMessages 里还有一个容易漏掉的细节：返回每条消息的链接时，权限不能超过当前这次请求用的那份能力——如果访问者手里拿的本来就是只读链接，那它看到的消息链接也必须是只读的，不能凭空"升级"。

# （本质还是"身份 + ACL"思路）。要把权限编码进链接本身，
# 需要自己写 SerializerMethodField，逻辑对应 Java 的 createUri。
from datetime import timedelta
from rest_framework import serializers
from capabilities.tokens import create_capability_uri

class SpaceSerializer(serializers.Serializer):
    name = serializers.CharField()
    uri = serializers.SerializerMethodField()
    messages_rwd = serializers.SerializerMethodField()
    messages_rw = serializers.SerializerMethodField()
    messages_r = serializers.SerializerMethodField()

    def _messages_link(self, space, perms):
        request = self.context["request"]
        return create_capability_uri(
            request, f"/spaces/{space.id}/messages", perms,
            timedelta(days=100000))

    def get_uri(self, space):
        request = self.context["request"]
        return create_capability_uri(
            request, f"/spaces/{space.id}", "rwd", timedelta(days=100000))

    def get_messages_rwd(self, space):
        return self._messages_link(space, "rwd")

    def get_messages_rw(self, space):
        return self._messages_link(space, "rw")

    def get_messages_r(self, space):
        return self._messages_link(space, "r")

9.2.4面向浏览器的能力 URI

9.2 节一开始提到，查询参数里的 token 有被日志/Referer/浏览器历史泄漏的风险，这个风险对纯后端调用的 API 影响不大，但如果能力 URI 是要直接被浏览器打开、渲染成页面的（比如 Natter 的消息浏览页面），风险就实打实存在了。Waterken 服务器发明的 web-key 方案给出了解法：把 token 放进 URL 的 # 片段（fragment）里。片段有个特殊性质——浏览器默认不会把它发给服务器，也不会出现在 Referer 头或 window.referrer 里。代价是服务器看不到这个 token 了，只能靠前端 JS 自己去读、再想办法送到 API。

因为这份模板脚本本身不含任何敏感信息，且对所有能力 URI 都通用，浏览器可以把它长期缓存下来，之后打开新的能力链接就不用再多走一次"先拿模板"的请求了。项目里实际的 capability.js 就是这么写的：

function getCap(url, callback) {
    let capUrl = new URL(url);
    let token = capUrl.hash.substring(1);
    capUrl.hash = '';
    capUrl.search = '?access_token=' + token;

    return fetch(capUrl.href)
    .then(response => response.json())
    .then(callback)
    .catch(err => console.error('Error: ', err));
}

它纯粹跑在浏览器里，Django 或 Hono 项目要做同样的事，前端塞的还是这同一段脚本（顶多换成 TypeScript 写法），后端只需要老老实实提供静态文件托管。真正需要框架特定代码的，是它请求的那个 ?access_token=… 接口——也就是上一节已经对比过的 lookupPermissions/CapabilityMiddleware/lookupPermissions 中间件。如果你的前端是 SPA（单页应用），要格外小心：Vue/React 这类框架用 HTML5 history API 让路由"看起来"没有 #，但如果 token 真的不在 fragment 里，这里说的安全好处就全部作废了。

9.2.5 / 9.2.6把能力和身份结合、加固能力 URI

目前为止，所有授权都只看能力 token，不看你是谁。这带来一个新问题：Natter 有些操作（比如发消息）本身就带着"我是谁"的宣称——消息的作者字段。如果任何拿到发消息能力 URI 的人都能冒充别人发消息，审计日志就完全不可信了。另外，一份能力 URI 一旦泄漏（比如被记进了某个日志文件），任何拿到它的人都能直接用——这跟身份 token 被偷的风险是一样的。

书里给了两种把身份"接"回来的思路：一种是直接把用户名塞进能力 token 本身，问题是这样一来"分享这份能力"就等于"允许对方冒充你"；另一种更常见——保留一个传统的登录态（比如长效的登录 cookie），只用它来做身份问题的问责，不用来做授权判断。授权仍然完全靠能力 token，cookie 只负责回答"这次操作到底是谁做的"。

⚠️ 能力也挡不住 CSRF——除非把它和身份绑在一起

你可能会想："都用能力做授权了，还需要防 CSRF 吗？"答案是仍然需要。CSRF 攻击者手里如果本来就有一份合法的能力 URI（比如他自己账号下的），他完全可以诱导受害者的浏览器带着受害者的登录 cookie 去访问这个能力 URI——这时候"权限"来自攻击者的能力 token，但"身份"却被张冠李戴成了受害者，同样是一次confused deputy。

解法是把能力 token 和登录用户绑定：签发能力 URI 时，把当前认证用户写进 token 的 username 字段；校验时，除了检查路径是否匹配，还要求 token 的 username 必须等于当前请求携带 cookie 所认证出的用户。这正是本章开头那段 CapabilityController 代码里已经包含的逻辑——项目里的最终版本从一开始就带着这行校验。绑定之后，好处是双重的：

  • 能力 token 被偷，攻击者没有对应的登录 cookie 照样用不了；
  • 登录 cookie 被偷，攻击者没有对应的能力 token 也办不成事——cookie 和能力互为对方的"第二把锁"，这天然就是一种 CSRF 防护，原来第 4 章专门加的反 CSRF token 反而可以拿掉了。
⚠️ 绑定之后，分享能力就没那么"随手"了

能力和身份绑死之后，原来"直接把链接发给朋友"的分享方式就失效了——那条链接对朋友的浏览器来说没有匹配的 cookie。Natter 为此专门加了一个 /capabilities 端点，让持有一份能力的人可以主动把它"兑换"成另一个用户名下的新能力（还能顺便收窄权限），这就是下面这个 share 方法要做的事。

public JSONObject share(Request request, Response response) {
    var json = new JSONObject(request.body());

    var capUri = URI.create(json.getString("uri"));
    var path = capUri.getPath();
    var query = capUri.getQuery();
    var tokenId = query.substring(query.indexOf('=') + 1);

    var token = tokenStore.read(request, tokenId).orElseThrow();
    if (!Objects.equals(token.attributes.get("path"), path)) {
        throw new IllegalArgumentException("incorrect path");
    }

    var tokenPerms = token.attributes.get("perms");
    var perms = json.optString("perms", tokenPerms);
    if (!tokenPerms.contains(perms)) {
        Spark.halt(403);   // 只能收窄权限，不能凭空升级
    }

    var user = json.getString("user");
    var newToken = new Token(token.expiry, user);
    newToken.attributes.put("path", path);
    newToken.attributes.put("perms", perms);

    var newTokenId = tokenStore.create(request, newToken);
    var uri = URI.create(request.uri());
    var newCapUri = uri.resolve(path + "?access_token=" + newTokenId);
    return new JSONObject().put("uri", newCapUri);
}

9.3Macaroon：可以不断"加锁"的 token

能力 URI 解决了"分享单个资源"的问题，但粒度还是服务器说了算——createSpace 只准备了 rwd/rw/r 三档权限，如果用户想分享"只能看今天中午之后的消息"这种更细的条件，服务器不可能提前把所有排列组合都准备出能力 URI。Macaroon（由 Google 一组研究者在 2014 年提出）解决的正是这个问题：它允许任何人在一份 token 后面追加"caveat"（限制条件），caveat 只能让权限变得更窄，谁都没法把已经加上的限制去掉。

💡 一个更好理解的类比：购物小票背面盖章

把 macaroon 想象成一张购物小票。小票背面已经盖好了一个"官方钢印"（初始的 HMAC 签名）。任何人都可以在钢印旁边再写一条新的限制，比如"仅限今天有效"，然后用上一个钢印的花纹当模具盖一个新章——因为没有原始钢印模具（也就是服务器手里的密钥），谁都没法逆向算出上一个钢印长什么样，所以也没法把中间某条限制擦掉或者伪造一条新的。谁都能"往后加限制"，谁都不能"往前减限制"。

这背后利用的是 HMAC 的一个有趣性质：HMAC 算出来的认证标签（tag），本身又可以当作密钥去对下一段消息做 HMAC。追加一个 caveat 时，就是拿"上一个 tag"当 key，对新 caveat 的文本再做一次 HMAC-SHA256，算出新 tag，然后把旧 tag 丢掉，只把 caveat 文本和新 tag 追加到 macaroon 末尾。反复这样做，就形成一条"链"：

校验时反过来做：服务器手里有原始密钥 K，从 identifier 开始重新算一遍这条链——每遇到一个 caveat，就用刚算出来的 tag 当 key 继续往下算，最后比较算出来的 tag 和 macaroon 自带的 tag 是否一致。书里给出了这段校验逻辑的最小实现（jmacaroons 库内部做的就是同一件事，你不需要自己写这段代码，这里贴出来只是为了让你看懂它到底在干什么）：

private boolean verify(String id, List<String> caveats, byte[] tag) throws Exception {
    var hmac = Mac.getInstance("HmacSHA256");
    hmac.init(macKey);
    var computed = hmac.doFinal(id.getBytes(UTF_8));

    for (var caveat : caveats) {
        hmac.init(new SecretKeySpec(computed, "HmacSHA256"));   // 用旧 tag 当新 key
        computed = hmac.doFinal(caveat.getBytes(UTF_8));
    }
    return MessageDigest.isEqual(tag, computed);   // 常数时间比较
}
⚠️ 永远不要信任 caveat 里写的内容

因为任何人都能追加 caveat（不需要密钥），所以 caveat 只能被用来收紧权限，绝不能反过来当作"证明"去放宽权限或者授予额外访问。校验方必须自己对每一种 caveat 写好判断逻辑（比如"当前时间是不是真的早于 caveat 里写的过期时间"），而不是看到 caveat 里写着什么就直接采信。

9.3.2Macaroon Token Store 的实现

在 Java 项目里，macaroon 功能是通过真实存在、维护中的开源库 jmacaroons（Maven 坐标 com.github.nitram509:jmacaroons）实现的，本章项目的 pom.xml 里已经声明了这个依赖。MacaroonTokenStore 的设计和第 5、6 章的 HmacTokenStore 如出一辙：包一层已有的 TokenStore（这里用的是 DatabaseTokenStore），自己只负责"把底层生成的标识符签成一个 macaroon"和"验证 macaroon 签名后再委托底层查表"。

ch09/src/main/java/com/manning/apisecurityinaction/token/MacaroonTokenStore.java（节选）
public class MacaroonTokenStore implements SecureTokenStore {
    private final TokenStore delegate;
    private final Key macKey;

    public static SecureTokenStore wrap(
            ConfidentialTokenStore tokenStore, Key macKey) {
        return new MacaroonTokenStore(tokenStore, macKey);
    }

    public static AuthenticatedTokenStore wrap(
            TokenStore tokenStore, Key macKey) {
        return new MacaroonTokenStore(tokenStore, macKey);
    }

    @Override
    public String create(Request request, Token token) {
        // 先用底层 store（DatabaseTokenStore）生成一个普通标识符，
        // 再用密钥把它签成一个 macaroon —— macaroon 只是"包了一层签名"的标识符。
        var identifier = delegate.create(request, token);
        var macaroon = MacaroonsBuilder.create("",
                macKey.getEncoded(), identifier);
        return macaroon.serialize();
    }

    @Override
    public Optional<Token> read(Request request, String tokenId) {
        var macaroon = MacaroonsBuilder.deserialize(tokenId);

        var verifier = new MacaroonsVerifier(macaroon);
        verifier.satisfyGeneral(new TimestampCaveatVerifier());
        verifier.satisfyExact("method = " + request.requestMethod());
        verifier.satisfyGeneral(new SinceVerifier(request));

        if (verifier.isValid(macKey.getEncoded())) {
            return delegate.read(request, macaroon.identifier);
        }
        return Optional.empty();
    }

    @Override
    public void revoke(Request request, String tokenId) {
        var macaroon = MacaroonsBuilder.deserialize(tokenId);
        delegate.revoke(request, macaroon.identifier);
    }
}

src/lib/macaroon.ts（教学示例 · 手写 HMAC 链）
// JS/TS 生态里没有像 jmacaroons、pymacaroons 那样成熟、维护良好的
// macaroon 库（社区里有 Canonical 维护的 js-macaroon，但文档和生态都薄弱得多），
// 这里按 9.3.2 节同样的算法手写一个等价实现——核心就是反复做 HMAC-SHA256。
import { createHmac, timingSafeEqual } from 'node:crypto'

function hmac(key: Buffer, data: string): Buffer {
  return createHmac('sha256', key).update(data, 'utf8').digest()
}

export function createMacaroon(identifier: string, macKey: Buffer): string {
  const tag0 = hmac(macKey, identifier)
  return toBase64Url(JSON.stringify(
    { id: identifier, caveats: [], tag: tag0.toString('base64url') }))
}

export function readMacaroon(
  serialized: string, macKey: Buffer, checks: ((caveat: string) => boolean)[],
) {
  const { id, caveats, tag } = JSON.parse(fromBase64Url(serialized)) as
    { id: string; caveats: string[]; tag: string }

  let computed = hmac(macKey, id)
  for (const caveat of caveats) {
    computed = hmac(computed, caveat)   // 用上一步的 tag 当新的 HMAC key
    if (!checks.some((check) => check(caveat))) return null
  }
  const ok = timingSafeEqual(computed, Buffer.from(tag, 'base64url'))
  return ok ? { id, caveats } : null
}

9.3.3第一方 caveat：本地就能核实的限制条件

💡 第一方 vs 第三方，一句话区分

第一方 caveat就是一段普通字符串，API 自己就能核实（比如"必须在某个时间点之前使用""必须是 GET 请求"）。第三方 caveat（下一节讲）需要客户端去找一个外部服务证明条件成立，再把证明带回来。

校验器（verifier）需要 API 提前注册好——遇到一条不认识的 caveat，macaroon 直接判定为无效，这一点和 OAuth2 的 scope 有点像：具体支持哪些 caveat，全靠 API 自己定义。项目里注册了三种校验器：内置的 TimestampCaveatVerifier（校验形如 time < 2019-10-12T12:00:00Z 的过期时间）、用 satisfyExact 做的精确字符串匹配（把 macaroon 限制在某一种 HTTP 方法上）、以及自己实现 GeneralCaveatVerifier 接口写的 SinceVerifier（校验形如 since > 2019-10-12T12:00:00Z 的"只能看这个时间点之后的消息"）。

追加 caveat 这一侧则非常轻量——不需要任何密钥，几行代码就能做到。项目里专门写了一个独立的命令行小工具 CaveatAppender，读入一个 macaroon 字符串和若干条 caveat，逐条追加后打印出新的 macaroon：

ch09/.../token/MacaroonTokenStore.java（SinceVerifier）+ ch09/.../CaveatAppender.java
private static class SinceVerifier implements GeneralCaveatVerifier {
    private final Request request;

    private SinceVerifier(Request request) {
        this.request = request;
    }

    @Override
    public boolean verifyCaveat(String caveat) {
        if (caveat.startsWith("since > ")) {
            var minSince = Instant.parse(caveat.substring(8));
            var reqSince = Instant.now().minus(1, ChronoUnit.DAYS);
            if (request.queryParams("since") != null) {
                reqSince = Instant.parse(request.queryParams("since"));
            }
            return reqSince.isAfter(minSince);
        }
        return false;   // 不认识的 caveat 一律拒绝
    }
}

// CaveatAppender.java —— 客户端小工具：不需要服务器密钥就能加限制
public class CaveatAppender {
    public static void main(String... args) {
        var builder = new MacaroonsBuilder(deserialize(args[0]));
        for (int i = 1; i < args.length; ++i) {
            builder.add_first_party_caveat(args[i]);
        }
        System.out.println(builder.getMacaroon().serialize());
    }
}

# capabilities/caveat_checks.py —— 供 macaroon_store.py 里的 Verifier 调用
from datetime import datetime, timezone, timedelta

def check_expiry_caveat(caveat: str) -> bool:
    if caveat.startswith("time < "):
        deadline = datetime.fromisoformat(caveat[7:])
        return datetime.now(timezone.utc) < deadline
    return False

def check_since_caveat(caveat: str, request) -> bool:
    if caveat.startswith("since > "):
        min_since = datetime.fromisoformat(caveat[8:])
        req_since = request.GET.get(
            "since", datetime.now(timezone.utc) - timedelta(days=1))
        return req_since > min_since
    return False

src/lib/macaroon-client.ts（教学示例 · 浏览器端追加 caveat）
// 浏览器里用 Web Crypto（SubtleCrypto）实现同样的"用旧 tag 当新 key"，
// 完全不需要接触服务器的密钥，几行代码就能做到，和 Java 版的 CaveatAppender 对应。
async function hmacKeyFromTag(tag: Uint8Array): Promise<CryptoKey> {
  return crypto.subtle.importKey(
    'raw', tag, { name: 'HMAC', hash: 'SHA-256' }, false, ['sign'])
}

export async function addCaveat(mac: SerializedMacaroon, caveat: string) {
  const oldTag = fromBase64Url(mac.tag)
  const key = await hmacKeyFromTag(oldTag)
  const sig = await crypto.subtle.sign(
    'HMAC', key, new TextEncoder().encode(caveat))
  return {
    id: mac.id,
    caveats: [...mac.caveats, caveat],
    tag: toBase64Url(new Uint8Array(sig)),
  }
}

试一下效果：先创建一个空间拿到能力 URI，用 CaveatAppender 追加一条一分钟后过期的 time caveat，用新 token 访问没问题；一分钟之后再用同一个新 token 访问，服务器会返回 403 Forbidden——但原始那个没加过期限制的 token 仍然完全正常，因为 caveat 只影响追加了它的那一份 macaroon 副本，不会"污染"原始 token。这正是上下文相关 caveat（contextual caveat）的价值：客户端在把 token 发到一个不那么可信的信道之前，可以现场加一条"5 秒内只能 PUT 这个 URL"之类的限制，就算这份临时受限的 token 被截获，损失也被死死框住了。

9.3.4第三方 caveat：需要外部服务盖章的限制条件

第一方 caveat 已经很好用了，但有些限制条件 API 自己没法核实，比如"这个人是不是某公司的员工""这个人是不是年满 18 岁"。这时候需要引入第三方 caveat：不再是 API 自己判断，而是要求客户端去联系一个第三方服务，拿到一份discharge macaroon（免除凭证）作为"条件已满足"的证明，再和原始 macaroon 一起交给 API。两份 macaroon 用密码学方式绑在一起，API 全程不需要直接和第三方服务通信，就能确认条件确实满足了。

一条第三方 caveat 由三部分组成：一个告诉客户端"去哪里核实"的 location hint（不受签名保护，只是提示，不可信）、一个高熵的共享密钥（第三方服务将用它给 discharge macaroon 签名，这段密钥会被加密后嵌进 caveat）、以及一个公开的identifier（第三方服务凭它查出这次要核实的是什么条件，本身不能泄漏密钥）。

✅ 第三方 caveat 好在哪里

API 不需要直接和第三方服务打交道；第三方服务看不到客户端到底在访问哪个具体资源（只看到一个不透明的 identifier），保护了隐私；discharge macaroon 本身又是一份 macaroon，第三方服务还能继续在它上面加更多第一方甚至第三方 caveat（比如"这份授权只在接下来 5 分钟内有效"）。书中提到的一个典型场景是银行转账：客户端长期持有一份能发起付款的 macaroon，每一笔具体转账都要求带上一个"经过独立交易授权服务确认"的第三方 caveat，避免长期 token 被盗后被直接拿去转账。

⚠️ 生态现状：没有统一标准

第三方 caveat 目前没有关于 identifier 格式、加密算法、客户端怎么联系第三方服务的统一标准，各家实现各自为政，所以在实践中主要用在同一个团队/公司内部自己掌控两端的封闭生态里，而不是跨组织的开放场景。

本章小结

机制解决的问题关键点
能力 URI想分享一条消息，又不想把整个空间的权限都给出去权限编码进 token 本身，而不是查身份表；拿到就是有权限
HATEOAS客户端怎么知道下一步该访问哪个 URL响应体里直接给出下一跳的能力链接，不需要客户端自己拼路径
fragment / web-key能力 URI 在浏览器里可能被日志、Referer、历史记录泄漏token 放进 # 片段，前端 JS 再挪到查询参数发给 API
能力 + 身份绑定能力 URI 泄漏后任何人都能用；还要防 CSRF把 token 的 username 和登录用户绑定，cookie 与 token 缺一不可
Macaroon现成的能力 URI 权限粒度不够细用 HMAC 链追加 caveat，谁都能"收紧"权限，没人能"放宽"
第一方 caveat简单、本地就能判断的限制（过期时间、HTTP 方法）API 自己写 verifier，逐条核对字符串条件
第三方 caveat需要外部服务背书的限制（如"是否本公司员工"）客户端换取一份 discharge macaroon，绑定后一起提交
