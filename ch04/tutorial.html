第 4 章

基于会话 Cookie 的认证

从"每次请求都带用户名密码"升级到"登录一次、用 Cookie 记住我"，顺便挡住那个几乎所有 Web 开发者都踩过坑的攻击：CSRF。

第 3 章里，Natter API 的每一次请求都要带上用户名和密码（HTTP Basic 认证），就像你每次进公司大楼都要重新出示身份证、还要保安现场打电话给 HR 核实一遍。这在安全上没问题，但慢，而且体验很差——密码要在网络上跑无数次，服务器要为每次请求都做一遍昂贵的密码哈希校验，浏览器弹出的登录框丑得没法看，用户也没法主动"退出登录"。

本章要做的事情，更接近你熟悉的"办一张门禁卡"：你在前台刷一次身份证（登录），拿到一张门禁卡（session token），之后进出各个房间只需要刷卡，保安扫一眼卡片上的编号，去后台系统查一下这张卡对应谁、有没有过期，就放你进去。这就是基于 Token 的认证，而"把门禁卡装进浏览器自动携带的口袋里"这件事，就是会话 Cookie（session cookie）。

但方便是有代价的：浏览器会在你毫不知情的情况下，把这张门禁卡"借"给任何一个网站去敲 Natter 的门——这就是本章后半段要重点搞定的 CSRF（跨站请求伪造）攻击。我们会一步步看清攻击是怎么发生的，然后用 SameSite Cookie 和"哈希双重提交 Cookie"两道防线把它挡住。

4.1浏览器中的认证

要理解为什么需要 Cookie，得先看看浏览器直接用 HTTP Basic 认证调用 API 会遇到什么麻烦。假设我们要给 Natter 做一个简单的网页界面：一个"创建社交空间"的表单，用 JavaScript 的 fetch 把表单数据打包成 JSON 发给 API。

💡 为什么不能直接用 HTML 表单提交？

标准的 HTML <form> 只会把数据编码成 application/x-www-form-urlencoded 或 multipart/form-data，Natter API 只认 JSON。所以浏览器必须用 JavaScript 拦截表单提交，自己拼一个 JSON 请求发出去，而不能让浏览器用默认方式直接提交表单。

// src/main/resources/public/natter.js（书中 4.1 节，创建空间的最初版本）
const apiUrl = 'https://localhost:4567';

function createSpace(name, owner) {
    let data = {name: name, owner: owner};
    fetch(apiUrl + '/spaces', {
        method: 'POST',
        credentials: 'include',           // 让浏览器带上 Cookie / HTTP 认证信息
        body: JSON.stringify(data),
        headers: { 'Content-Type': 'application/json' }
    })
    .then(response => {
        if (response.ok) { return response.json(); }
        else { throw Error(response.statusText); }
    })
    .then(json => console.log('Created space: ', json.name, json.uri))
    .catch(error => console.error('Error: ', error));
}

window.addEventListener('load', function(e) {
    document.getElementById('createSpace')
        .addEventListener('submit', processFormSubmit);
});

function processFormSubmit(e) {
    e.preventDefault();               // 阻止浏览器用默认方式提交表单
    let spaceName = document.getElementById('spaceName').value;
    let owner = document.getElementById('owner').value;
    createSpace(spaceName, owner);
    return false;
}

如果你把这个 HTML 文件直接用 file:// 方式在浏览器里打开，会发现请求被浏览器拦下来了。原因是浏览器的同源策略（Same-Origin Policy，SOP）：JavaScript 默认只能向"和自己同源"的服务器发请求。

💡 什么是"同源"

一个 URL 的"源（origin）"由协议 + 主机名 + 端口三部分组成，三者都完全一致才算同源。比如 https://api.example.com:8443/a 和 https://api.example.com:8443/b 同源（路径不参与判断），但和 http://api.example.com:8443/a（协议不同）或 https://www.example.com:8443/a（主机名不同）都不同源。file:// 打开的本地文件永远和任何 HTTPS 网站都不同源。

解决办法很简单：让 Natter API 服务器自己把这些 HTML/JS 文件也一起托管出去，这样页面和 API 就是同一个源了。Spark 只需要一行配置： 

// Main.java —— 必须是 main 方法的第一行
Spark.staticFiles.location("/public");

这样 src/main/resources/public/ 目录下的文件就能通过 https://localhost:4567/natter.html 直接访问，和 API 同源。

同源之后，请求确实能发出去了——但因为 JS 代码没有主动带用户名密码，服务器返回 401 加一个 WWW-Authenticate: Basic 响应头，浏览器就会弹出那个丑陋的原生登录框，让用户输入用户名密码。这暴露了 HTTP Basic 认证在浏览器场景下的几个硬伤：

⚠️ HTTP Basic 认证在浏览器里的缺点
  • 密码在每一次请求里都要传一遍，暴露面被放大很多倍；如果是微服务架构，每个微服务都得安全地处理这份密码。
  • 密码哈希校验很贵（上一章讲过，故意设计成约 100ms），如果每次请求都验一遍密码，每个 CPU 核心每秒只能撑住约 10 次请求。
  • 浏览器原生登录框丑，也没法自定义样式和交互。
  • 用户没有清晰的"退出登录"方式——关掉浏览器窗口通常都没用，在公共电脑上这是个实打实的安全问题。

这些问题指向同一个方向：我们需要一种"登录一次、后面用一个轻量令牌代替密码"的机制——这就是下一节的 Token-based authentication。

4.2基于 Token 的认证

核心思路很简单：新增一个专门的登录端点，客户端把用户名密码只发这一次；登录成功后，服务器生成一个随机字符串（token），把它交给客户端。之后客户端每次请求都带上这个 token 代替用户名密码，服务器去一个"token 存储"里查一下这个 token 对应谁、有没有过期。

💡 什么是 Token / Session Token

Token 就是一个足够随机、猜不出来的字符串，通常有有效期。用户登录一次拿到它，之后拿它换取访问权限，直到过期或主动登出。用来标识"用户正在和网站交互"的短期 token，常被叫做 session token、session cookie，或者干脆叫 session。

4.2.1 Token 存储的抽象接口

这一章到第 6 章会陆续实现好几种不同的 token 存储方式（Cookie、数据库、自包含的加密 token……），所以书里先定义一个通用接口 TokenStore，把"怎么存 token"和"怎么用 token"解耦开。

ch04/src/main/java/.../token/TokenStore.java
public interface TokenStore {

    String create(Request request, Token token);
    Optional<Token> read(Request request, String tokenId);
    void revoke(Request request, String tokenId);

    class Token {
        public final Instant expiry;
        public final String username;
        public final Map<String, String> attributes;

        public Token(Instant expiry, String username) {
            this.expiry = expiry;
            this.username = username;
            // 多线程会同时读写，所以用并发安全的 Map
            this.attributes = new ConcurrentHashMap<>();
        }
    }
}
accounts/tokens.py（教学示例：抽象 token 存储）
from abc import ABC, abstractmethod
from dataclasses import dataclass, field
from datetime import datetime

@dataclass
class Token:
    expiry: datetime
    username: str
    attributes: dict = field(default_factory=dict)

class TokenStore(ABC):
    """对应 Java 的 TokenStore 接口。
    Django 内置的 SessionStore 就是这里 create/read/revoke
    的一种具体实现（见下一节）。"""

    @abstractmethod
    def create(self, request, token: Token) -> str: ...

    @abstractmethod
    def read(self, request, token_id: str) -> Token | None: ...

    @abstractmethod
    def revoke(self, request, token_id: str) -> None: ...
src/tokens/store.ts
export interface Token {
  expiry: Date;
  username: string;
  attributes: Record<string, string>;
}

export interface TokenStore {
  create(c: Context, token: Token): Promise<string>;
  read(c: Context, tokenId: string): Promise<Token | null>;
  revoke(c: Context, tokenId: string): Promise<void>;
}

4.2.2 实现基于 Token 的登录

有了抽象接口，登录端点的实现出乎意料地简单：复用第 3 章已经写好的 HTTP Basic 认证过滤器（UserController）去验证用户名密码，登录端点本身只管从请求属性里取出已经通过认证的用户名，塞进一个新 token，存进 TokenStore，把 token ID 返回给客户端。

ch04/src/main/java/.../controller/TokenController.java（login 方法）
public JSONObject login(Request request, Response response) {
    // subject 属性是 UserController 的 HTTP Basic 过滤器
    // 验证密码通过后设置的
    String subject = request.attribute("subject");
    var expiry = now().plus(10, ChronoUnit.MINUTES);

    var token = new TokenStore.Token(expiry, subject);
    var tokenId = tokenStore.create(request, token);

    response.status(201);
    return new JSONObject().put("token", tokenId);
}

from django.contrib.auth import authenticate, login
from django.http import JsonResponse
from django.views.decorators.http import require_POST
from django.contrib.auth.decorators import login_not_required
import base64

@require_POST
def session_login(request):
    # 复用 HTTP Basic：手动解析 Authorization 头
    auth = request.META.get("HTTP_AUTHORIZATION", "")
    if not auth.startswith("Basic "):
        return JsonResponse({"error": "unauthorized"}, status=401)

    raw = base64.b64decode(auth[6:]).decode()
    username, _, password = raw.partition(":")
    user = authenticate(request, username=username, password=password)
    if user is None:
        return JsonResponse({"error": "unauthorized"}, status=401)

    login(request, user)                 # 创建 session，写入 Set-Cookie
    request.session.set_expiry(60 * 10)  # 10 分钟过期
    return JsonResponse({"token": request.session.session_key}, status=201)

4.3会话 Cookie

Token 存哪儿？浏览器场景下最经典的答案是 Cookie：登录响应带一个 Set-Cookie 头，浏览器记住它，之后每次请求到同一个网站都会自动在 Cookie 请求头里带上，服务器拿这个值去存储里查是谁。

💡 Cookie 违反 REST 的"无状态"原则吗？

严格说是的——服务器要为每个客户端保存状态。但用 Cookie 只标记"这个人是谁、登没登录"，副作用很小，而且 Cookie 自带很多其他技术拿不到的安全属性（比如自动按域名隔离、可以标记为仅 HTTPS 传输），所以书里认为这是一个"划算的违规"。

Spark 底层用的 Jetty servlet 容器自带 session 支持：调用 request.session(true) 会返回当前请求关联的 session，如果不存在就新建一个，并自动加上 Set-Cookie 头；传 false 则只在已存在时返回，否则给 null。CookieTokenStore 就是把 TokenStore 接口薄薄地包在这套机制上。

4.3.1 避免会话固定攻击（session fixation）

☠ 攻击是什么样的：会话固定

如果登录时"沿用已有 session"而不是"强制生成一个新 session"，攻击者就可以：① 自己先访问网站拿到一个合法但未登录的 session token；② 想办法把这个 token 塞进受害者的浏览器（比如利用 XSS，或者诱导受害者点击带 session 参数的链接）；③ 等受害者用这个 token 登录后，token 关联的用户名从"攻击者"变成了"受害者"——但 token 本身没变，攻击者手里那份原始 token 现在也能访问受害者的账户了。

防御思路很直接：登录成功后，一律作废任何已存在的旧 session，重新生成一个全新的、攻击者不可能预测到的 session。这样即便攻击者提前塞入了一个 token，登录那一刻它就失效了。这是 4 个必须掌握的核心机制里的第②个。

ch04/src/main/java/.../token/CookieTokenStore.java（create 方法节选）
@Override
public String create(Request request, Token token) {

    var session = request.session(false);
    if (session != null) {
        session.invalidate();          // ① 先作废旧 session（如果有）
    }
    session = request.session(true);   // ② 再创建一个全新的、随机的 session

    session.attribute("username", token.username);
    session.attribute("expiry", token.expiry);
    session.attribute("attrs", token.attributes);

    return Base64url.encode(sha256(session.id()));
}
accounts/views.py
from django.contrib.auth import login as django_login

def session_login(request, user):
    # Django 的 login() 内部已经会调用 cycle_key()，
    # 但显式写出来更能说明这里在做什么：
    if request.session.session_key:
        request.session.cycle_key()    # 保留旧数据但换一个新的 session_key
    django_login(request, user)        # 写入认证信息，触发 Set-Cookie
    request.session.set_expiry(60 * 10)
src/tokens/cookieStore.ts
async function create(c: Context, token: Token): Promise<string> {
  const oldSessionId = getCookie(c, "session_id");
  if (oldSessionId) {
    await db.delete(sessions).where(eq(sessions.id, oldSessionId));
    deleteCookie(c, "session_id");     // ① 作废旧 session
  }

  const newSessionId = crypto.randomUUID();   // ② 生成全新、不可预测的 id
  await db.insert(sessions).values({
    id: newSessionId,
    username: token.username,
    expiry: token.expiry,
  });

  setCookie(c, "session_id", newSessionId, {
    httpOnly: true, secure: true, sameSite: "Strict", path: "/",
  });
  return sha256Hex(newSessionId);
}

4.3.2 Cookie 的安全属性

Spark（准确说是底层的 Jetty）给 JSESSIONID Cookie 默认加了几个安全属性，这也是本章要求覆盖的第①个核心机制——理解每个属性是干什么的：

属性作用
Secure只在 HTTPS 连接上发送，网络窃听者拿不到明文 Cookie。
HttpOnlyJavaScript（document.cookie）读不到这个 Cookie，即使页面被 XSS，攻击脚本也偷不走它。
SameSite只有"同站"发起的请求才会带上这个 Cookie，是 4.4 节防 CSRF 的第一道防线。
Domain不设置时是 host-only（只发给完全一致的主机名），设置了会连子域名一起发——子域名一旦被攻破就会连带泄露 Cookie，能不设就不设。
Path限制 Cookie 在哪些路径下发送，安全收益有限（可以被隐藏 iframe 绕过）。
Expires / Max-Age登录用的会话 Cookie 建议都不设置，让浏览器关闭标签页就丢弃它，避免公用电脑上的残留登录。
✅ 最佳实践：__Host- 前缀

把 Cookie 命名为 __Host-session 这种带 __Host- 前缀的名字，浏览器会强制要求它必须同时具备 Secure 属性、且不能设置 Domain（即必须是 host-only）。这样即使某个子域名被攻破，也没法伪造覆盖你的主域名 Cookie，是对抗子域名劫持（sub-domain hijacking）的一个简单又有效的手段。

curl 实测登录响应长这样，可以直接看到这些属性：

4.3.3 校验会话 Cookie

光签发 Cookie 还不够，还得有一道过滤器在每个请求进来时检查它：如果 Cookie 有效且没过期，就把用户名写进请求的 subject 属性，后面的权限检查才能认出"这是谁"。 

// TokenController.java（4.3.3 节的初版，暂时还没有 CSRF 防护——见下一节）
public void validateToken(Request request, Response response) {
    // WARNING: 这里还没有校验 CSRF token，见 4.4 节
    tokenStore.read(request, null).ifPresent(token -> {
        if (now().isBefore(token.expiry)) {
            request.attribute("subject", token.username);
            token.attributes.forEach(request::attribute);
        }
    });
}

⚠️ 但这版本还有一个大洞

只要浏览器带着 Cookie，请求就能通过——问题是浏览器不管这个请求是谁发起的，只要目标网站是 Natter，就会自动带上 Cookie。任何一个恶意网站都可以借用户的浏览器，悄悄发一个带 Cookie 的请求到 Natter，而这正是下一节要解决的 CSRF 问题。

4.4防止 CSRF 攻击

设想这样一个场景：你刚登录完 Natter，收到市场部小美发来的一条消息，说点这个链接能拿 Manning 图书 8 折优惠。你满怀期待地点了进去，页面告诉你"优惠已过期"，你有点失望地回到 Natter，却发现自己的账号已经给好几个朋友群发了骚扰消息——而这一切，都是你从来没有主动做过的操作。

☠ 攻击是什么样的：CSRF

那个"优惠链接"网页里藏了一段 JavaScript，趁你浏览器还处于登录状态，偷偷向 Natter API 发起了一个跨站请求（比如 POST /spaces/1/messages）。因为 Cookie 是浏览器自动附带的，Natter 服务器收到的请求里带着你的 JSESSIONID，看起来和你自己发的请求毫无区别，于是就照单全收了。同源策略只挡住了"恶意网站读取响应内容"，并没有挡住"发出这个请求"本身。

⚠️ 重要前提：GET 请求必须"无副作用"

几乎所有 CSRF 防护手段都假设 GET 请求是安全的、不会修改任何数据。如果你的 API 允许用 GET 请求执行删除、转账之类的操作，那么任何一个 <img src="..."> 标签就能触发 CSRF，本节讲的所有防护都救不了你。

4.4.1 SameSite Cookie

第一道防线很简单：给 Cookie 加上 SameSite=Strict（或 Lax）属性。浏览器就只会在"同站"发起的请求里带上这个 Cookie，跨站请求（比如从恶意网站发出的）根本不会附带 Cookie。

💡 "同站"和"同源"不是一回事

SameSite 判断的是可注册域（registerable domain，也叫 eTLD+1）是否相同，不看协议和端口。api.example.com 和 www.example.com 算同站，但 example.com 和 example.org 不算。Strict 模式下连"用户主动点击一个跨站链接"都不带 Cookie；Lax 模式对这种"顶层导航点击"网开一面，但仍然挡住脚本发起的跨站请求。

⚠️ SameSite 不是万能的

SameSite 的保护范围包含所有子域名，只要其中一个子域名被攻破（比如子域名劫持），攻击者就能绕过这层防护；而且不是所有历史浏览器和框架都完整支持它。所以书里把 SameSite 当作"纵深防御"的第一层，紧接着要上第二层更硬核的防护——双重提交 Cookie。

4.4.2 基于哈希的双重提交 Cookie

更强的思路是：让调用方"证明自己知道 session Cookie 的值"。传统 Web 应用的做法是在表单里塞一个隐藏字段，但 JSON API 没有表单。API 世界的等价做法叫双重提交 Cookie（double-submit cookie）：登录时额外返回第二个 Cookie（不加 HttpOnly，JS 可以读到），要求客户端把它同时读出来、放进一个自定义请求头（比如 X-CSRF-Token）里再发一次。服务器检查这两份是否一致。

传统双重提交 Cookie 有个弱点：如果攻击者能设法覆盖（overwrite）掉这第二个 Cookie（比如通过子域名攻破），就能自己填一个已知值，再在请求头里带上同样的值，照样能骗过校验。Natter 用的是更稳的变体——哈希绑定：这个 CSRF token 不是随机生成的，而是 session Cookie 的 SHA-256 哈希值。这样一来，除非攻击者能读到（或猜到）真正的 session 值，否则算不出正确的哈希，覆盖第二个 Cookie 也没用。

☠ 别用普通的字符串比较

校验哈希值相不相等时，如果用普通的 == / .equals()，很多语言的实现会在发现第一个不匹配字符时就提前退出循环，这个"提前退出"的时间差可以被攻击者远程测量出来，一个字符一个字符地把正确值试出来（时序攻击 / timing attack）。必须使用常数时间比较函数，比如 Java 的 MessageDigest.isEqual、Python 的 hmac.compare_digest、Node.js 的 crypto.timingSafeEqual。

4.4.3 Natter 里的双重提交实现

具体落地上，CookieTokenStore.create() 不再直接把 session id 作为 token 返回给客户端，而是返回它的 SHA-256 哈希（用 URL-safe Base64 编码成字符串）；read() 则要求调用方传入这个哈希值，重新计算一遍当前 session 的哈希，用常数时间比较两者是否一致。这是本章要求覆盖的第③个核心机制。

ch04/src/main/java/.../token/CookieTokenStore.java（read 方法，含哈希校验）
@Override
public Optional<Token> read(Request request, String tokenId) {
    var session = request.session(false);
    if (session == null) {
        return Optional.empty();
    }

    var provided = Base64url.decode(tokenId);
    var computed = sha256(session.id());

    if (!MessageDigest.isEqual(computed, provided)) {   // 常数时间比较
        return Optional.empty();
    }

    var token = new Token(session.attribute("expiry"),
            session.attribute("username"));
    token.attributes.putAll(session.attribute("attrs"));
    return Optional.of(token);
}

static byte[] sha256(String tokenId) {
    var sha256 = MessageDigest.getInstance("SHA-256");
    return sha256.digest(tokenId.getBytes(StandardCharsets.UTF_8));
}

# Django 内置 CsrfViewMiddleware 默认是"随机值双重提交"，
# 可以打开 CSRF_USE_SESSIONS=True 让 token 与 session 绑定；
# 这里手写一个哈希绑定版本，逻辑上对应 Java 的 CookieTokenStore：
import hashlib, hmac, base64

def compute_csrf_token(session_key: str) -> str:
    digest = hashlib.sha256(session_key.encode()).digest()
    return base64.urlsafe_b64encode(digest).rstrip(b"=").decode()

class HashDoubleSubmitCsrfMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        if request.method not in ("GET", "HEAD", "OPTIONS"):
            provided = request.headers.get("X-CSRF-Token")
            expected = compute_csrf_token(request.session.session_key or "")
            if not provided or not hmac.compare_digest(provided, expected):
                return JsonResponse({"error": "unauthorized"}, status=401)
        return self.get_response(request)

src/middleware/csrf.ts
import { createHash, timingSafeEqual } from "node:crypto";
import { getCookie } from "hono/cookie";
import type { MiddlewareHandler } from "hono";

function sha256(input: string): Buffer {
  return createHash("sha256").update(input).digest();
}

export const csrfDoubleSubmit: MiddlewareHandler = async (c, next) => {
  const sessionId = getCookie(c, "session_id");
  const provided = c.req.header("X-CSRF-Token");

  if (!sessionId || !provided) {
    return c.json({ error: "unauthorized" }, 401);
  }

  const computed = sha256(sessionId);
  const providedBuf = Buffer.from(provided, "base64url");

  if (providedBuf.length !== computed.length ||
      !timingSafeEqual(computed, providedBuf)) {   // 常数时间比较
    return c.json({ error: "unauthorized" }, 401);
  }
  await next();
};

4.5构建 Natter 登录 UI

有了后端能力，前端补一个登录页：一个用户名 + 密码的表单，提交后用 fetch 把凭证以 Authorization: Basic ... 的形式发到 /sessions，成功后把返回的 token 写进 csrfToken Cookie（注意这个 Cookie 是 JS 自己写的，不能带 HttpOnly，因为后面还要靠 JS 读出来放进请求头），再跳转回主页。

⚠️ 别让浏览器弹原生登录框

如果 API 在 401 响应里带了 WWW-Authenticate: Basic 头，浏览器会自动弹出丑陋的原生登录框，盖过我们自己做的登录页。解决办法是 requireAuthentication 只管 halt(401)，不要再设置这个响应头。

// UserController.java
public void requireAuthentication(Request request, Response response) {
    if (request.attribute("subject") == null) {
        halt(401);   // 故意不设置 WWW-Authenticate，避免触发浏览器原生登录框
    }
}
// src/main/resources/public/login.js（真实项目文件，节选）
function login(username, password) {
    let credentials = 'Basic ' + btoa(username + ':' + password);

    fetch(apiUrl + '/sessions', {
        method: 'POST',
        headers: {
            'Content-Type': 'application/json',
            'Authorization': credentials
        }
    })
    .then(res => {
       if (res.ok) {
         res.json().then(json => {
            // csrfToken 不能标 HttpOnly，因为下面 natter.js 还要读它
            document.cookie = 'csrfToken=' + json.token +
                ';Secure;SameSite=strict';
            window.location.replace('/natter.html');
         });
       }
    })
    .catch(error => console.error('Error logging in: ', error));
}

主页 natter.js 在发起业务请求前，从 document.cookie 里手动解析出 csrfToken，塞进 X-CSRF-Token 请求头；如果服务器返回 401，就跳回登录页：

// src/main/resources/public/natter.js（真实项目文件，节选）
function getCookie(cookieName) {
    var cookieValue = document.cookie.split(';')
        .map(item => item.split('=')
            .map(x => decodeURIComponent(x.trim())))
        .filter(item => item[0] === cookieName)[0]
    if (cookieValue) { return cookieValue[1]; }
}

function createSpace(name, owner) {
    let data = {name: name, owner: owner};
    let csrfToken = getCookie('csrfToken');

    fetch(apiUrl + '/spaces', {
        method: 'POST',
        credentials: 'include',
        body: JSON.stringify(data),
        headers: {
            'Content-Type': 'application/json',
            'X-CSRF-Token': csrfToken
        }
    })
    .then(response => {
        if (response.ok) { return response.json(); }
        else if (response.status === 401) {
            window.location.replace('/login.html');
        } else { throw Error(response.statusText); }
    })
    .then(json => console.log('Created space: ', json.name, json.uri))
    .catch(error => console.error('Error: ', error));
}

登录之后，浏览器的开发者工具里能同时看到两块 Cookie：服务器设置的 JSESSIONID（带 HttpOnly，JS 读不到）和前端自己设置的 csrfToken（不带 HttpOnly，专门给 JS 读）。这正是"真正的会话密钥"和"只用来证明你能读到会话密钥的哈希值"之间的分工。

4.6实现登出

想象你在朋友家借用电脑登录了 Natter，用完了想退出，好让朋友看不到你的私信。仅仅在浏览器里删掉 Cookie 是不够的——万一删除失败（比如 Path/Domain 没对上），或者 Cookie 被某个配置不当的网络缓存留了一份，旧 token 依然有效。所以登出必须在服务器端把 token 吊销掉，这是本章要求覆盖的第④个核心机制。

先给 TokenStore 接口加一个 revoke 方法。对 CookieTokenStore 来说，实现就是校验完 CSRF token（防止攻击者恶意登出别人）之后调用 session.invalidate()——它会把 session 从服务器端存储里删掉，并在响应里加一个"过期时间在过去"的 Set-Cookie，让浏览器立刻清掉这块 Cookie。

ch04/src/main/java/.../token/CookieTokenStore.java + controller/TokenController.java
// CookieTokenStore.java
@Override
public void revoke(Request request, String tokenId) {
    var session = request.session(false);
    if (session == null) return;

    var provided = Base64url.decode(tokenId);
    var computed = sha256(session.id());
    if (!MessageDigest.isEqual(computed, provided)) {
        return;                       // CSRF token 不对，拒绝吊销
    }
    session.invalidate();             // 服务器端删除 + 让浏览器清 Cookie
}

// TokenController.java
public JSONObject logout(Request request, Response response) {
    var tokenId = request.headers("X-CSRF-Token");
    if (tokenId == null)
        throw new IllegalArgumentException("missing token header");

    tokenStore.revoke(request, tokenId);
    response.status(200);
    return new JSONObject();
}

from django.contrib.auth import logout as django_logout
from django.views.decorators.http import require_http_methods

@require_http_methods(["DELETE"])
def session_logout(request):
    provided = request.headers.get("X-CSRF-Token")
    expected = compute_csrf_token(request.session.session_key or "")
    if not provided or not hmac.compare_digest(provided, expected):
        return JsonResponse({"error": "missing token header"}, status=400)

    django_logout(request)         # request.session.flush()，
                                    # 服务器端删记录 + 响应里带过期 Cookie

import { deleteCookie, getCookie } from "hono/cookie";

sessions.delete("/sessions", async (c) => {
  const tokenId = c.req.header("X-CSRF-Token");
  if (!tokenId) {
    return c.json({ error: "missing token header" }, 400);
  }

  const sessionId = getCookie(c, "session_id");
  if (sessionId) {
    const computed = sha256Hex(sessionId);
    if (computed === tokenId) {
      await db.delete(sessions).where(eq(sessions.id, sessionId)); // 删数据库记录
    }
  }
  deleteCookie(c, "session_id", { path: "/" });   // 清 Cookie
  return c.json({}, 200);
});

本章小结

机制解决的问题关键实现
Token / 会话避免每次请求都传密码，减少暴露面和计算开销TokenStore 抽象 + CookieTokenStore
Cookie 安全属性限制 Cookie 的使用范围和传输方式Secure / HttpOnly / SameSite / __Host- 前缀
登录时重建 session防止会话固定攻击先 invalidate() 旧 session，再 session(true) 建新 session
SameSite Cookie让跨站请求默认不携带 CookieSameSite=Strict/Lax
哈希双重提交 Cookie即使 SameSite 被绕过，也要求调用方证明自己"知道"session 值CSRF token = SHA-256(session id)，常数时间比较
登出让用户能主动、可靠地结束会话服务器端 revoke + 校验 CSRF token 后 invalidate()
✅ 记住这几条
  • 会话 Cookie 认证只适合和 API 同源的第一方浏览器客户端；跨域、非浏览器客户端要看第 5 章的方案。
  • 登录成功后必须让旧 session 失效、生成新 session，否则会话固定攻击有机可乘。
  • 会话 Cookie 一律加 Secure、HttpOnly，能加 SameSite 就加，命名尽量带 __Host- 前缀。
  • 只要用 Cookie 做认证，就必须显式防 CSRF——不要以为同源策略已经帮你挡住了跨站请求本身，它只挡住了"读响应"。
  • 涉及机密值比较的地方一律用常数时间比较函数，普通的 == 会给时序攻击留后门。
