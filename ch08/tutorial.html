第 8 章

基于身份的访问控制

当访问控制列表（ACL）膨胀到几十万条时，该怎么给权限"分类打包"？

想象你在管理一栋写字楼的门禁系统。最原始的做法是给每个员工、每一扇门单独登记一条"谁能进哪扇门"的记录——这就是第 3 章讲过的访问控制列表（ACL）。公司只有十个人、五扇门的时候这毫无问题，可一旦公司涨到一千人、一百个房间，你要维护的记录就变成了十万条，而且每次有人离职、换部门，你都要在这堆记录里逐条修改。现实中更常见的做法是"分类管理"：把员工划进"财务部""研发部"这样的组，或者干脆给一个人发一张写着"经理"字样的门禁卡，保安只看卡上的头衔而不用记住这个人到底是谁。

这一章要讲的，就是 API 世界里这几种"分类打包"权限的方式：把用户组织成组（group），用基于角色的访问控制（RBAC）把权限打包成"角色"再发给用户，以及更进一步、能结合时间、地点等上下文动态裁决的基于属性的访问控制（ABAC）。它们都属于同一个大类——基于身份的访问控制（IBAC，Identity-Based Access Control）：先确认"你是谁"，再根据"你是谁"来判断你能做什么。第 9 章会介绍不依赖身份、而是依赖"你手里有什么凭证"的另一套思路。

💡 什么是 IBAC（基于身份的访问控制）

API 先认证请求者的身份（用户名、JWT 里的 subject 等），再查这个身份被授予了哪些权限，最后决定放行还是拒绝。本章讲的组、角色、属性，都是"把权限组织起来再关联到身份"的不同方式，核心步骤永远是"认证 → 查身份对应的权限 → 裁决"。

8.1用户与组

最直接的简化办法是把相关的用户收进一个"组"里，权限不再直接发给某个人，而是发给组。组和用户之间是多对多的关系：一个用户可以属于多个组（比如同时是"研发部"和"项目经理"），一个组也可以包含很多用户；如果组的成员本身允许是"主体（subject）"——也就是用户或者别的组，那组还可以嵌套组，形成层级结构，比如"项目经理组"整体作为"员工组"的成员。

组最大的好处是：新员工入职时，你只需要把他加进"软件工程师"组，而不用逐条回忆他需要哪些权限；他换岗位时，把他从旧组移出、塞进新组即可。要在 Natter 的数据库里实现"组"，只需要一张记录成员关系的表：

CREATE TABLE group_members(
    group_id VARCHAR(30),
    user_id VARCHAR(30) REFERENCES users(user_id)
);
CREATE INDEX group_member_user_idx ON group_members(user_id);

用户登录成功之后，就可以顺便查一下他属于哪些组，把结果作为一个新的请求属性存起来，后面的访问控制逻辑随时可以取用。这一步很关键——书里特别强调：认证阶段该收集的用户属性（比如组），一定要在认证阶段就收集好，而不要在鉴权阶段临时又发起一次身份相关的查询，否则一旦以后把认证换成 LDAP 或 OpenID Connect（组信息会随着 ID Token 一起下发），你的鉴权逻辑就得跟着大改。

⚠️ 认证和鉴权要分层

把"查用户属于哪些组"和"判断这些组有没有权限"揉进同一条 SQL 当然更省一次查询，但这样做违反了认证与鉴权的分层原则：鉴权逻辑不应该关心属性是从数据库表查出来的还是从 LDAP、JWT 里读出来的。分开两步，即使以后换了身份来源，鉴权代码也完全不用动。

8.1.1 LDAP 组

大公司通常用一个中央目录服务——LDAP（轻量级目录访问协议）——统一管理全公司的用户，LDAP 天生就支持组的概念，分两种：静态组（groupOfNames，显式列出每个成员的 member 属性）和动态组（groupOfURLs，成员由一条 LDAP 搜索条件动态算出）。要查一个用户属于哪些静态组，本质上是拿这个用户的"专有名称"（distinguished name，DN）去搜所有 member 属性等于它的组条目。

注意第 ④ 步的搜索过滤条件里用的是 {0} 占位符，而不是直接把用户名拼进字符串——这是为了避免 LDAP 注入：如果直接拼接，攻击者在用户名里塞入 *)(uid=* 这样的 LDAP 特殊字符，就可能让搜索条件的语义被篡改，搜出不该搜到的条目，原理和 SQL 注入完全一致（第 2 章）。JNDI 提供的参数化搜索会自动帮你转义这些特殊字符。

🚨 LDAP 注入长什么样

假设过滤条件被拼成 (&(objectClass=groupOfNames)(member=uid=USERNAME,...))，如果 USERNAME 直接来自用户输入且没有转义，攻击者输入 *)(member=* 之类的字符串就可能让查询匹配到所有组，从而伪造出自己属于 admins 组的假象。永远用库提供的参数化接口，绝不要手工拼接目录查询字符串。

public void authenticate(Request request, Response response) {
    var credentials = getCredentials(request);
    if (credentials == null) return;

    var username = credentials[0];
    var password = credentials[1];
    var dn = "uid=" + username + ",ou=people," + baseDn;

    try {
        var directory = bind(dn, password);   // 用用户自己的密码验证身份
        request.attribute("subject", username);
        directory.close();

        // 用预先建立好的服务账号连接去搜索该用户所在的组
        var searchControls = new SearchControls();
        searchControls.setSearchScope(SearchControls.SUBTREE_SCOPE);
        searchControls.setReturningAttributes(new String[] { "cn" });

        var groups = new ArrayList<String>();
        var results = connection.search("ou=groups," + baseDn,
                "(&(objectClass=groupOfNames)(member={0}))",
                new Object[]{ dn },              // 参数化，避免 LDAP 注入
                searchControls);
        while (results.hasMore()) {
            var result = results.next();
            groups.add((String) result.getAttributes()
                .get("cn").get(0));
        }
        request.attribute("groups", groups);
    } catch (AuthenticationException e) {
        // 密码错误，不设置 subject，视为未认证
    }
}

src/middleware/ldapAuth.ts（ldapjs，教学示例）
import { Client } from "ldapjs";
import type { MiddlewareHandler } from "hono";

export const ldapAuth: MiddlewareHandler = async (c, next) => {
  const auth = c.req.header("Authorization");
  if (!auth?.startsWith("Basic ")) return c.text("Unauthorized", 401);
  const [username, password] = atob(auth.slice(6)).split(":");
  const userDn = `uid=${username},ou=people,dc=example,dc=com`;

  // 用用户自己的密码 bind，验证身份
  const userClient = new Client({ url: process.env.LDAP_URL! });
  await new Promise((resolve, reject) =>
    userClient.bind(userDn, password, (err) => (err ? reject(err) : resolve(null)))
  );
  userClient.unbind();

  // 用服务账号连接搜索该用户所在的组（filter 参数会被 ldapjs 转义，避免注入）
  const svcClient = new Client({ url: process.env.LDAP_URL! });
  await new Promise((resolve, reject) =>
    svcClient.bind(process.env.LDAP_BIND_DN!, process.env.LDAP_BIND_PW!,
      (err) => (err ? reject(err) : resolve(null)))
  );

  const groups: string[] = [];
  svcClient.search("ou=groups,dc=example,dc=com", {
    filter: `(&(objectClass=groupOfNames)(member=${userDn}))`,
    scope: "sub", attributes: ["cn"],
  }, (err, res) => {
    res.on("searchEntry", (entry) => groups.push(String(entry.attributes[0].values[0])));
    res.on("end", () => svcClient.unbind());
  });

  c.set("subject", username);
  c.set("groups", groups);
  await next();
};

8.2基于角色的访问控制

组能让管理用户更轻松，但没有完全解决问题：大多数组系统仍然允许给单个用户直接发权限，你想弄清楚"谁能干什么"，还是得把每个用户的权限和他所在的每个组的权限都翻一遍；而且组往往是全公司统一定义的（LDAP 里可能只有一个笼统的"软件工程师"组），未必贴合某个具体 API 的权限颗粒度需求。基于角色的访问控制（RBAC）在用户和权限之间插入了一层新的间接层——角色：权限不再直接发给用户或组，而是发给角色，用户再被分配到角色。

这样做的好处很直接：给某人"moderator"这个称呼，比让所有人都记住"moderator 具体能读、能删、不能写"要简单得多；以后想调整 moderator 的权限，也只需要改一处角色定义，不用挨个改用户或组的权限记录。RBAC 和组虽然在数学上能互相模拟，但实践中差异明显：组主要用来组织用户，角色主要用来组织权限；组往往是全公司统一定义的，角色通常是某个 API 自己定义的；大多数 RBAC 系统不允许绕过角色直接给用户发权限，这让"谁能干什么"变得容易审计；角色的定义（哪个角色有哪些权限）和角色的分配（谁拥有哪个角色）也是分开管理的，这是一种有效的职责分离。

8.2.1 角色映射到权限

把角色落到具体权限上，通常有两种做法。第一种是彻底抛弃"权限"这个概念，直接在每个 API 操作上标注允许调用的角色——Java EE / JAX-RS 就是这么做的，用 @RolesAllowed("moderator") 这样的注解描述限制。这种方式简单直接，但把角色和代码耦合死了，改角色要改代码重新发布。

💡 顺带一提：注解式角色（Natter 未采用）

Java EE 风格大致是这样：@RolesAllowed({"owner", "moderator"}) public Response listMembers() { … }。Natter 项目没有引入 JAX-RS，所以这里只作为对照思路介绍，不再单独展开三栏代码对比。

Natter 采用的是第二种做法：保留显式的权限字符（r/w/d），额外建一张表把角色映射到权限组合，这样管理员也能在不碰代码的情况下审查"这个角色到底能干什么"：

CREATE TABLE role_permissions(
    role_id VARCHAR(30) NOT NULL PRIMARY KEY,
    perms VARCHAR(3) NOT NULL
);
INSERT INTO role_permissions(role_id, perms)
    VALUES ('owner', 'rwd'),
           ('moderator', 'rd'),
           ('member', 'rw'),
           ('observer', 'r');
GRANT SELECT ON role_permissions TO natter_api_user;
角色权限位含义
ownerr, w, d社交空间的创建者，读写删全权限
moderatorr, d可以读帖、删除违规帖子，但不能自己发帖
memberr, w普通成员，可以读帖发帖，不能删帖
observerr只能看，不能发言

8.2.2 静态角色

决定了角色对应什么权限之后，还要决定"哪个用户拥有哪个角色"，最常见的做法是静态配置——加一张表把某个用户在某个社交空间里的角色记下来。因为 Natter 的角色是限定在单个社交空间内的（一个空间的 owner 管不了另一个空间），所以主键是 (space_id, user_id)：

CREATE TABLE user_roles(
    space_id INT NOT NULL REFERENCES spaces(space_id),
    user_id VARCHAR(30) NOT NULL REFERENCES users(user_id),
    role_id VARCHAR(30) NOT NULL REFERENCES role_permissions(role_id),
);
CREATE INDEX user_roles_idx ON user_roles(space_id, user_id);
💡 什么是安全域（realm）

当用户、组或角色的作用范围被限定在应用的某个子集内（比如"这个角色只在这一个社交空间里有效"），这个子集就叫一个安全域。Natter 里每个社交空间就是一个独立的安全域。

创建社交空间时，创建者会被自动授予该空间里的全部角色；邀请新成员加入时，请求里带上想给对方的角色，服务端要先校验这是不是一个合法角色名，再写入 user_roles 表。

ch08/.../controller/SpaceController.java（节选）
private static final Set<String> DEFINED_ROLES =
        Set.of("owner", "moderator", "member", "observer");

public JSONObject addMember(Request request, Response response) {
  var json = new JSONObject(request.body());
  var spaceId = Long.parseLong(request.params(":spaceId"));
  var userToAdd = json.getString("username");
  var roles = json.optJSONArray("roles");
  if (roles == null) {
    roles = new JSONArray().put("member");     // 默认给 member 角色
  }
  if (!DEFINED_ROLES.containsAll(roles.toList())) {
    throw new IllegalArgumentException("invalid role");
  }
  for (var role : roles.toList()) {
    database.updateUnique(
            "INSERT INTO user_roles(space_id, user_id, role_id)" +
                    " VALUES(?, ?, ?)", spaceId, userToAdd, role);
  }
  response.status(200);
  return new JSONObject()
          .put("username", userToAdd)
          .put("roles", roles);
}

class SpaceMembership(models.Model):

        ("member", "member"), ("observer", "observer"),

# views.py
class AddMemberView(APIView):
    permission_classes = [IsAuthenticated]

    def post(self, request, space_id):
        username = request.data["username"]
        role = request.data.get("role", "member")
        if role not in dict(SpaceMembership.ROLE_CHOICES):
            raise ValidationError("invalid role")

        user = User.objects.get(username=username)
        SpaceMembership.objects.update_or_create(
            space_id=space_id, user=user, defaults={"role": role})
        return Response({"username": username, "role": role})

8.2.3 确定用户角色

请求进来之后，要先查这个用户在当前空间里的角色，再查该角色对应哪些权限，最后才能判断这次操作是否被允许。因为角色高度绑定具体 API（不像组那样在认证阶段就能拿到），Natter 把"角色 → 权限"这两步查询合并成一条 SQL，放进一个独立的 lookupPermissions 过滤器里，在真正的权限校验之前先跑一遍、把结果缓存进请求属性，避免同一个请求里的多次权限检查重复查库。这也正是实现"只有 moderator 才能删帖"这类静态角色规则的地方：删除操作要求权限位包含 d，而只有 owner 和 moderator 的角色对应的 perms 里带 d。

ch08/.../controller/UserController.java（节选）
public void lookupPermissions(Request request, Response response) {
    requireAuthentication(request, response);
    var spaceId = Long.parseLong(request.params(":spaceId"));
    var username = (String) request.attribute("subject");

    var query = new QueryBuilder(
            "SELECT rp.perms " +
                    "  FROM role_permissions rp JOIN user_roles ur" +
                    "    ON rp.role_id = ur.role_id" +
                    " WHERE ur.space_id = ? AND ur.user_id = ?",
            spaceId, username);

    var perms = String.join("",
            database.findAll(String.class, query.build()));
    request.attribute("perms", perms);      // 存进请求属性，避免重复查库
}

public Filter requirePermission(String method, String permission) {
    return (request, response) -> {
        if (!method.equalsIgnoreCase(request.requestMethod())) {
            return;
        }
        var perms = request.<String>attribute("perms");
        if (!perms.contains(permission)) {
            halt(403);
        }
    };
}

# permissions.py
ROLE_PERMS = {"owner": "rwd", "moderator": "rd", "member": "rw", "observer": "r"}

class HasSpacePermission(BasePermission):
    required = "r"   # 子类覆盖，例如删除接口要求 "d"

    def has_permission(self, request, view):
        space_id = view.kwargs["space_id"]
        try:
            membership = SpaceMembership.objects.get(
                space_id=space_id, user=request.user)
        except SpaceMembership.DoesNotExist:
            return False
        return self.required in ROLE_PERMS[membership.role]

class CanDeleteMessage(HasSpacePermission):
    required = "d"   # 只有 owner / moderator 的角色带 'd'

# views.py —— 对应“只有 moderator 才能删帖”
class MessageDetailView(APIView):
    permission_classes = [IsAuthenticated, CanDeleteMessage]

    def delete(self, request, space_id, msg_id):
        Message.objects.filter(space_id=space_id, msg_id=msg_id).delete()
        return Response(status=200)
src/middleware/requireRole.ts（Hono，教学示例）
const ROLE_PERMS: Record<string, string> = {
  owner: "rwd", moderator: "rd", member: "rw", observer: "r",
};

export function requirePermission(perm: "r" | "w" | "d"): MiddlewareHandler {
  return async (c, next) => {
    const spaceId = Number(c.req.param("spaceId"));
    const username = c.get("subject");

    const row = await db.query.userRoles.findFirst({
      where: and(eq(userRoles.spaceId, spaceId), eq(userRoles.userId, username)),
    });
    if (!row || !ROLE_PERMS[row.roleId].includes(perm)) {
      return c.text("Forbidden", 403);
    }
    await next();
  };
}

// routes/messages.ts —— “只有 moderator（或 owner）才能删帖”
app.delete(
  "/spaces/:spaceId/messages/:msgId",
  requirePermission("d"),
  async (c) => { /* 执行删除 */ }
);

8.2.4 动态角色

静态角色分配最常见，但有些系统支持更灵活的动态角色：比如呼叫中心的客服只在自己排班的时间段内才被授予"可以访问客户档案"的角色，下班之后角色自动失效。动态角色目前没有统一标准，通常靠数据库查询或者 Prolog、OWL 这类逻辑规则来实现。当你发现需要的规则已经不只是"给谁发了什么角色"这么简单，而是要结合时间、地点等上下文时，就该考虑下一节的 ABAC 了。

8.3基于属性的访问控制

RBAC 已经能覆盖大多数场景，但有些策略天生就没法用静态角色表达。还是呼叫中心的例子：除了要求客服在排班时间内，你可能还想要求客服当前正在和这个客户通话才能看他的档案——客户是谁，可能是通过来电号码或者客户在按键菜单里输入的账号动态判断出来的，而且理想情况下应该只放行"通话期间 + 通话结束后 5 分钟"这个窗口，这比任何静态角色都精细得多，也更贴近最小权限原则。

ABAC（基于属性的访问控制）就是为了应对这种动态场景而生的：每次请求都实时收集一组属性，分成四大类——主体（发起请求的用户，比如用户名、所属组）、资源（被访问的对象，比如 URI、密级标签）、操作（比如 HTTP 方法）、环境（比如时间、IP 地址）——喂给策略引擎，引擎给出允许或拒绝的裁决。

下面是 Natter 里收集属性、触发裁决的代码：一个 Spark 过滤器把请求里能拿到的信息按四类打包，交给一个抽象方法 checkPermitted 去评估，如果结果是"不允许"就直接 403。

ch08/.../controller/ABACAccessController.java
public abstract class ABACAccessController {

    public void enforcePolicy(Request request, Response response) {
        var subjectAttrs = new HashMap<String, Object>();
        subjectAttrs.put("user", request.attribute("subject"));
        subjectAttrs.put("groups", request.attribute("groups"));

        var resourceAttrs = new HashMap<String, Object>();
        resourceAttrs.put("path", request.pathInfo());
        resourceAttrs.put("space", request.params(":spaceId"));

        var actionAttrs = new HashMap<String, Object>();
        actionAttrs.put("method", request.requestMethod());

        var envAttrs = new HashMap<String, Object>();
        envAttrs.put("timeOfDay", LocalTime.now());
        envAttrs.put("ip", request.ip());

        var permitted = checkPermitted(subjectAttrs, resourceAttrs,
                actionAttrs, envAttrs);
        if (!permitted) {
            halt(403);
        }
    }

    abstract boolean checkPermitted(
            Map<String, Object> subject, Map<String, Object> resource,
            Map<String, Object> action, Map<String, Object> env);

    public static class Decision {
        private boolean permit = true;   // 默认允许
        public void deny() { permit = false; }   // 显式拒绝会覆盖默认值
        public void permit() { /* 显式允许被忽略，除非已经 deny */ }
        boolean isPermitted() { return permit; }
    }
}

from datetime import datetime

class Decision:
    def __init__(self):
        self.permit = True          # 默认允许

    def deny(self):
        self.permit = False         # deny 覆盖默认值

    def permit_(self):
        pass                        # 显式允许被忽略

def gather_attributes(request, space_id):
    return {
        "subject": {
            "user": request.user.username,
            "groups": list(request.user.groups.values_list("name", flat=True)),
        },
        "resource": {"path": request.path, "space": space_id},
        "action": {"method": request.method},
        "environment": {"time": datetime.now().time(), "ip": request.META.get("REMOTE_ADDR")},
    }

class ABACMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        space_id = request.resolver_match.kwargs.get("space_id") if request.resolver_match else None
        attrs = gather_attributes(request, space_id)
        decision = Decision()
        for rule in POLICY_RULES:      # 一组 (attrs, decision) -> None 的规则函数
            rule(attrs, decision)
        if not decision.permit:
            return JsonResponse({"error": "forbidden"}, status=403)

interface Decision {
  permit: boolean;
  deny(): void;      // 覆盖默认值
  permitExplicit(): void;  // 显式允许被忽略
}

function newDecision(): Decision {
  return {
    permit: true,
    deny() { this.permit = false; },
    permitExplicit() {},
  };
}

export const enforcePolicy: MiddlewareHandler = async (c, next) => {
  const subject = { user: c.get("subject"), groups: c.get("groups") };
  const resource = { path: c.req.path, space: c.req.param("spaceId") };
  const action = { method: c.req.method };
  const environment = { timeOfDay: new Date(), ip: c.req.header("x-forwarded-for") };

  const decision = newDecision();
  for (const rule of policyRules) {
    rule({ subject, resource, action, environment }, decision);
  }

  if (!decision.permit) return c.text("Forbidden", 403);
  await next();
};

8.3.1 合并多个决策

一旦规则不止一条，就必然会遇到"没有规则命中怎么办"和"规则之间意见不一致怎么办"这两个问题。最安全的做法是默认拒绝：必须至少有一条规则明确允许、且没有任何规则拒绝，请求才能通过。但如果 ABAC 是叠加在已有的 RBAC/ACL 之上、只是想额外收紧一些边界场景，用默认允许 + deny 优先会更省事——这正是 Natter 采用的策略：所有请求默认放行，交给底层已经实现好的 RBAC 去把关，ABAC 规则只负责在特定条件下追加拒绝。上面 Decision 类的实现就是这个思路：permit 初始为 true，任何一次 deny() 调用都会把它扳成 false 且不可逆，而调用 permit() 什么也不做——因为"允许"本来就是默认值，真正有意义的只有"拒绝"这个动作。

8.3.2 实现 ABAC 决策

ABAC 规则直接写死在 Java 代码里当然可以，但业务规则一旦变复杂，用专门的规则引擎或 DSL（领域特定语言）来表达会清晰得多。本书用 Red Hat 的 Drools 规则引擎来实现，规则文件是独立的 .drl 文本，格式是"when（条件）… then（动作）…"，很像自然语言。Natter 用它加了一条书里没有在 RBAC 层面实现的规则：禁止 moderator 在非工作时间（9 点到 17 点之外）执行删除操作——哪怕这个人本来就有 d 权限。

💡 Drools 的工作方式

把各类属性对象"插入"到一次会话（KieSession）的工作内存里，规则引擎会自动尝试匹配每条规则的 when 部分；一旦某条规则的所有条件都满足，就会执行它的 then 部分。这里的规则文件里用了一个全局变量 decision，规则通过调用它的 deny()/permit() 来影响最终结果，和上一节的合并逻辑完全对应。

ch08/.../controller/DroolsAccessController.java + src/main/resources/accessrules.drl
// DroolsAccessController.java
public class DroolsAccessController extends ABACAccessController {
    private final KieContainer kieContainer;

    public DroolsAccessController() {
        this.kieContainer = KieServices.get().getKieClasspathContainer();
    }

    @Override
    boolean checkPermitted(Map<String, Object> subject, Map<String, Object> resource,
                           Map<String, Object> action, Map<String, Object> env) {
        var session = kieContainer.newKieSession();
        try {
            var decision = new Decision();
            session.setGlobal("decision", decision);
            session.insert(new Subject(subject));
            session.insert(new Resource(resource));
            session.insert(new Action(action));
            session.insert(new Environment(env));
            session.fireAllRules();
            return decision.isPermitted();
        } finally {
            session.dispose();
        }
    }
    // Subject/Resource/Action/Environment 只是包了一层 HashMap，
    // 方便 Drools 按类型匹配不同类别的属性
}

// accessrules.drl
package com.manning.apisecurityinaction.rules;
global Decision decision;

rule "deny moderation outside office hours"
    when
        Action( this["method"] == "DELETE" )
        Environment( this["timeOfDay"].hour < 9
            || this["timeOfDay"].hour > 17 )
    then
        decision.deny();
end
policy/rules.py（django-rules，教学示例）
import rules
from datetime import time

@rules.predicate
def is_delete(action):
    return action["method"] == "DELETE"

@rules.predicate
def outside_office_hours(environment):
    t = environment["time"]
    return t < time(9, 0) or t > time(17, 0)

# 等价于 Drools 规则里 when 部分的两个条件用 && 连起来
deny_moderation_outside_hours = is_delete & outside_office_hours

def rule_office_hours(attrs, decision):
    if deny_moderation_outside_hours(
        action=attrs["action"], environment=attrs["environment"]
    ):
        decision.deny()

# 挂进 8.3.1 里定义的 POLICY_RULES 列表
POLICY_RULES = [rule_office_hours]

// src/policy/opa.ts —— Hono 端只负责把属性 POST 给 OPA，规则本身跑在 OPA 里
export async function checkWithOPA(input: {
  subject: object; resource: object; action: object; environment: object;
}): Promise<boolean> {
  const res = await fetch("http://opa:8181/v1/data/natter/authz/allow", {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ input }),
  });
  const { result } = await res.json();
  return result === true;
}

export const enforcePolicy: MiddlewareHandler = async (c, next) => {
  const allowed = await checkWithOPA({
    subject: { user: c.get("subject"), groups: c.get("groups") },
    resource: { path: c.req.path, space: c.req.param("spaceId") },
    action: { method: c.req.method },
    environment: { timeOfDay: new Date().toISOString(), ip: c.req.header("x-forwarded-for") },
  });
  if (!allowed) return c.text("Forbidden", 403);
  await next();
};

8.3.3 策略代理与 API 网关

规则一旦变多，散落在每个服务自己的代码里就很难统一管理，于是出现了专门的组件：策略代理（policy agent）以插件形式挂进已有的应用服务器、Web 服务器或反向代理；或者作为独立的网关拦截 HTTP 层的请求。比如 Open Policy Agent（OPA）就是用一种专门的 DSL（Rego）描述策略，既能作为 REST 服务被远程调用，也能作为 Go 库直接嵌入。

这一类架构最大的价值是把"鉴权"和"业务逻辑"彻底解耦：业务代码不用关心策略细节，安全团队也能独立于业务发布节奏去调整策略。本章不为这一层单独写三栏代码对比——它更多是部署形态和基础设施的选择，而不是某个 Web 框架内的具体写法；不管后端用 Spark、Django 还是 Hono，都可以把它放在同一个策略代理或网关后面。

8.3.4 分布式策略与 XACML

另一种思路是把策略定义完全集中到一台独立的策略服务器上，各个策略代理通过 REST API 向它请求裁决，这样安全团队就能在一个地方审查、调整全公司所有 API 的规则。这个方向最经典的标准是 XACML（eXtensible Access-Control Markup Language），它定义了一套基于 XML 的策略语言，虽然这套 XML 语法近年用得越来越少，但它定义的参考架构影响深远，被后续很多 ABAC 系统（包括 NIST 的建议）借鉴。

💡 XACML 的四个角色

PEP（策略执行点）像门卫一样拦截请求，负责放行或拒绝；PDP（策略决策点）装着真正的规则引擎，负责给出裁决；PIP（策略信息点）负责从各种数据源取属性值并缓存；PAP（策略管理点）是给管理员用的策略编辑界面。四者可以部署在同一台机器上，也可以分布在不同服务里。

8.3.5 ABAC 最佳实践

ABAC 的灵活性也是一把双刃剑：规则一多就很容易失控，作者提到自己经历过一次生产事故——某系统用 XPath 表达式匹配 XML 消息做鉴权，另一个团队悄悄改了消息结构，导致大量规则悄无声息地不再匹配，结果放行了不该放行的请求，好几周都没人发现，因为测试用的还是旧格式的消息。为了少踩这样的坑，书里给出几条建议：

  • 把 ABAC 叠加在 RBAC 这类更简单的机制之上，做纵深防御——ABAC 规则写错，也不至于门户大开。
  • 给 API 端点建立自动化测试，策略一改就能立刻发现权限有没有被意外放宽。
  • 策略定义要放进版本控制系统，方便回滚，并且要有正规的评审流程。
  • 想清楚哪些策略该集中管理、哪些该留给各个 API 自己决定——过度集中会拖慢变更速度，反而可能因为"改起来太麻烦"而让过宽的策略长期留着不改，违反最小权限原则。
  • 尽早、持续地测量 ABAC 裁决带来的性能开销。
✅ 一句话记住 ABAC

ABAC 不是用来替代 RBAC 的，而是用来补足 RBAC 表达不了的"运行时上下文"规则；默认允许、deny 优先，是把 ABAC 安全地叠加在已有权限体系之上的关键设计。

模型核心思路优点局限 / 注意点
组 Group 把用户归类，权限（或角色）发给组而不是个人；组可嵌套组 组织用户方便，LDAP 天然支持，新人入职/离职只需改组成员 仍常常允许给个人单独发权限，颗粒度未必贴合具体 API 需求
