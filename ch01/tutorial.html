第 1 章

什么是 API 安全？

在动手写一行代码之前，先搞清楚“安全”到底是什么意思，以及一个 API 都会在哪些地方被攻破。

打开你手机里的任意一个 App——不管是聊天软件、外卖软件还是记步软件——它几乎都在悄悄地和远程服务器 上的 API 通信：下载新消息、上传你的数据、代表你执行各种操作。打开浏览器的开发者工具随便逛一个网页， 你也会看到后台密密麻麻地发出几十个 API 请求，服务端可能又由几十个微服务通过内部 API 相互调用才拼出 这个页面。就连你家里的智能音箱、冰箱、电表，现在也在通过 API 和云端对话。API 无处不在，这既让软件变 得更强大，也让攻击面变得更大——你越依赖 API 完成关键任务，一旦它被攻破，你受到的伤害就越大。

💡 什么是 GDPR

GDPR（《通用数据保护条例》）是欧盟 2018 年生效的一部数据保护法律，要求企业必须 用技术和管理手段妥善保护用户的个人数据，数据泄露必须在 72 小时内报告，违规最高可被罚款 2000 万欧元 或全球年营业额的 4%。本书后面会讲到的很多安全机制，正是满足这类合规要求的技术基础。

这一章不写代码，目标只有一个：在你动手加固 Natter 这个示例 API 之前，先在脑子里搭好一张“安全是什么、 安全机制都长什么样”的地图。后面每一章都会往这张地图里添砖加瓦。

1.1类比：考驾照

先讲一个和 API 完全无关的小故事，帮你建立直觉。

下班路上，你在公园里遇到老朋友 Alice，她正牵着自己的宠物羊驼散步。你们打了个招呼，聊了几句就各自 离开——你完全不需要看她的身份证就知道她是 Alice，因为你们有长期的交往历史，彼此“认识”。

接着你赶到驾考中心。考官走出来，第一件事是让你出示驾照，仔细核对照片和你本人是否一致。考官从没见过 你，而“冒充别人来替考”在这个场景下是完全合理的担忧，所以他需要一个正式的、难以伪造的凭证来确认你就是 你自称的那个人。

💡 身份识别（identify）≠ 身份认证（authenticate）

认出 Alice，靠的是“长期熟悉”这种非正式的信任关系；核实驾照，靠的是一个由权威机构签发、难以伪造的 凭证，这才是正式的身份认证。同一个 API 里，不同的操作也可以要求不同强度的身份确认： 查看公开信息也许不需要登录，转账操作则需要严格得多的认证。

没考过驾照的你只好坐火车回家。你想蒙混进头等车厢蹭个座，结果被列车员拦住，要求出示车票——普通座车票 换不来头等舱的座位。回到家，Alice 邀请你去新开的夜店，你满怀期待地走到门口，看门人却把你拦下：“今晚不 行。”而这时一位名人走过来，直接被请了进去。

💡 两种“谁能干什么”的思路

名人能直接进场，靠的是身份（先确认你是谁，再查你有没有权限）——这叫 基于身份的访问控制。车票能进对应的车厢，靠的是车票本身携带的权限（不管拿票的人是谁， 有票就能进）——这叫基于能力凭证（capability）的访问控制。两种思路各有取舍，第 8、9 章会详细展开。

你决定出去度假散心，临走前把家里温室大棚的钥匙留给邻居 Bob，让他帮忙照看你收藏的食虫植物。结果你 不知道的是，Bob 拿着这把钥匙在你家后院办了一场热闹的派对——好在酒水提前喝光了，没人闯进你锁着的房子 和威士忌收藏室。度假回来，你调出家里的监控录像，认出了 Bob，找他对质，他也无法抵赖，只能买了一盆新 植物赔罪。

💡 什么是审计日志（audit log）

监控录像就是现实版的审计日志：记录“谁在什么时候做了什么”，让你在出问题之后能够 查清责任、拿出证据，并且让当事人无法轻易抵赖（这个属性叫不可否认性）。钥匙只能开 大棚和后院，开不了正屋，这体现的是“最小权限”——只给别人完成任务所必需的那一小部分权限。

这个小故事里已经埋下了本章要讲的几乎所有概念：识别用户、验证身份、决定谁能做什么、记录发生了什么。 接下来我们把这些概念套回到 API 的世界里。

1.2什么是 API？

早年间，“API”通常指一个软件库暴露出来、可以被静态或动态链接进另一个程序的一组函数（比如做 3D 图形的 OpenGL，或者某个网络库）。这类 API 现在依然存在，但越来越多的 API 是通过互联网以 RESTful Web 服务的形式对外提供的——本书也是围绕这一类 API 展开的。

抽象地说，API 是软件系统内部或系统之间的一道边界：它定义了一组“别人可以调用的操作”。 比如一个相册服务可以提供一个 API，允许调用方列出相册、查看照片、添加评论；一个在线图片网站和一个文档 编辑器都可以复用同一个 API，把图片嵌入到各自的产品里。如图 1-1 所示，用户通过各种客户端（网页、手机 App、IoT 设备）向 API 发起请求，API 处理业务逻辑，可能还要调用其他“后端 API”才能完成任务，最后把结果 返回给客户端。

💡 API 和 UI 有什么不同

UI（用户界面）也是一种边界，但它是为“人”设计的，追求好看好用；API 是为“程序”设计的，追求格式 规整、易于解析。同一份数据，UI 会包装成漂亮的页面，API 则会给出一份干净的 JSON。

常见的 API 风格

  • RPC（远程过程调用）：把远程调用伪装成本地函数调用，通常用紧凑的二进制格式， 效率高，但客户端往往需要安装专用的桩代码（stub）。Google 的 gRPC 是现代代表，老式的 SOAP（基于 XML）现在仍能在不少企业系统里见到。
  • RMI（远程方法调用）：RPC 的面向对象变体，让你像调用本地对象方法一样调用远程 对象，CORBA、EJB 是典型代表，但因为过于复杂，现在已经比较少见。
  • REST（表述性状态转移）：由 Roy Fielding 提出，强调统一的消息格式和少量通用 操作，用超链接在资源之间导航，以降低客户端和服务端之间的耦合。这也是本书采用的主要风格。
  • 查询型 API：比如 SQL 数据库或 Facebook 的 GraphQL，只暴露少量操作，但配合一套 强大的查询语言，让客户端可以精确指定自己想要什么数据。

本书接下来会围绕运行在 HTTP 之上、大体遵循 REST 风格的 API 展开——这也是目前最主流的 API 形态—— 但书里讲到的安全原则对其他风格的 API 同样适用。

1.3API 安全的语境

API 安全并不是一门孤立的学科，它站在三个更大的安全领域的交叉点上：

  • 信息安全（InfoSec）：关注信息从产生、存储、传输、备份到最终销毁的全生命周期保护。
  • 网络安全（Network security）：关注网络中数据流动的保护，以及防止未经授权访问 网络本身。
  • 应用安全（AppSec）：确保软件系统在设计和实现上能够抵御攻击与滥用。

从信息安全，你会学到如何定义安全目标、识别威胁、用访问控制保护 API、用密码学保护信息；从网络安全， 你会学到防火墙、负载均衡、反向代理这些基础设施的角色，以及如何用 HTTPS 保护传输中的数据；从应用安全， 你会学到安全编码技巧、常见的软件安全漏洞，以及如何妥善管理系统和用户凭证。

💡 什么是 HTTPS

HTTPS 就是跑在安全连接（TLS，也叫 SSL）之上的 HTTP。普通 HTTP 的请求和响应对 任何能监听网络的人都是明文可见的，HTTPS 则会把内容加密隐藏起来。第 3 章会讲如何为 API 开启 HTTPS。

一次典型的 API 部署

你几乎不会把 API 服务器直接暴露在公网上。一个请求在真正到达你写的业务代码之前，通常要先穿过好几层 基础设施：

  • 防火墙在网络层做粗粒度过滤，比如只放行 80、443 端口的流量，其余一律拦截。
  • 负载均衡器把流量分摊到多台服务器上，避免有的机器忙死、有的闲着。
  • 反向代理 / 网关替 API 服务器分担一些昂贵的工作，比如终结 TLS 连接（SSL termination）、校验请求携带的身份凭证、做限流。其中专门用来把多个后端 API 统一包装成一个对外 API 的反向代理，叫 API 网关。

此外还有几种更专门化的组件：Web 应用防火墙（WAF）在更高的层面上检查 HTTP 流量， 能识别并拦截常见的 Web 攻击；入侵检测 / 防御系统（IDS/IPS）监控内部网络里的可疑 活动模式，发现异常就报警甚至主动拦截。这些组件之间常有职责重叠，很多负载均衡器也能做反向代理的活， 很多反向代理也能兼任 API 网关。

⚠️ 网关不是万能的

把认证、限流这些工作交给网关处理确实很常见，也很方便，但网关配置不当同样会引入新的风险，而且 再强大的网关也救不了写得千疮百孔的业务代码。理解这些安全机制的原理，才能判断一个网关产品是否真的 适合你，以及它的边界在哪里——这正是本书要从零手写这些机制、而不是直接甩给你一个网关配置文件的原因。

1.4API 安全的构成要素

既然 API 本来就只暴露你允许的那些操作，为什么还需要专门谈“安全”？原因主要有三点：第一，同一个 API 往往要服务权限完全不同的用户，比如普通用户和管理员，如果没有访问控制，任何人都能做任何事；第二，单看 每个操作都没问题，组合起来却可能出问题——比如一个银行 API 分别提供“取款”和“存款”接口，各自都会检查 额度，但“存款”接口没法判断这笔钱是不是真的从一个合法账户转出的，更安全的做法是提供一个原子的“转账” 接口；第三，实现细节本身可能藏着漏洞，比如没有限制输入大小，攻击者发一个超大的请求体就能把服务器内存 吃满，造成拒绝服务。

☠️ 最小化的拒绝服务（DoS）例子

假设 API 的“上传头像”接口对请求体大小没有任何限制。攻击者只需要写个脚本，反复发送几百 MB 的 POST 请求体，服务器为了解析这些请求会不断分配内存，最终耗尽资源、无法响应正常用户——这就是最简单 的一种拒绝服务（Denial of Service, DoS）攻击：让合法用户没法正常使用服务。

安全没有唯一标准答案，也和具体场景强相关：对医疗系统来说，让人查到“某人是不是本系统用户”是严重的 隐私泄露；但对社交网络来说，这恰恰是核心功能。所以设计一个安全的 API，通常要考虑以下几件事：

  • 需要保护的资产（assets）有哪些；
  • 对这些资产而言，重要的安全目标（security goals）是什么；
  • 有哪些安全机制（mechanisms）可以用来实现这些目标；
  • API 运行的环境是什么样的，环境里存在哪些威胁。

资产

对大多数 API 来说，资产首先是信息：用户名、地址、支付卡信息、数据库里的各种数据，尤其是性取向、 政治倾向这类敏感个人信息。其次是物理资产，比如服务器硬件本身——虽然数据中心的门禁和监控让物理入侵的 风险很低，但攻击者完全可能通过操作系统或软件的漏洞远程拿到硬件的控制权。简单说：只要有人会因为它被 破坏而受到真实或者“感觉上”的损害（无论是直接的经济损失，还是抽象的声誉损失），它就该被当作资产来保护。

除了 CIA，视场景不同，可问责性（追溯谁做了什么）和不可否认性 （当事人无法抵赖）也常常同样重要。安全目标可以被看作一种非功能性需求（NFR），和性能、可靠性目标放在 一起考虑，但它有个天生的难点：很难证明一个目标“从未被违反过”，因为这是在证明一个否命题。

一种让安全目标变得可测试的办法，是把抽象目标细化成具体约束。比如一个即时通讯 API，功能需求是 “用户能读取自己的消息”；为了保住机密性，你可以加上约束：“用户只能读取自己的消息”“用户必须先登录才能 读消息”。有了这样的约束，你就能写出具体的测试用例：创建两个用户，检查用户 A 读不到用户 B 的消息；检查 未登录用户读不到任何消息。

✅ 安全不是一次性的事

就像你不会只测一次性能就一劳永逸，安全目标和假设也需要被定期回顾。比如实现登录功能之后，你会给 每个用户签发一个临时的会话 Cookie——这个 Cookie 本身就是一项新资产，需要被保护起来（第 4 章会讲）。

环境与威胁模型

安全目标离不开具体环境。一个只在自行车俱乐部内部使用、记录比赛成绩的小 API，大概率不需要防范 国家级情报机构，但确实需要防止骑手偷偷篡改自己或别人的成绩。威胁就是任何可能让你的 安全目标落空的事件；你所认定的、和自己 API 相关的那一整套威胁，叫威胁模型，识别它们 的过程叫威胁建模。

💡 威胁建模的五个步骤

① 画出系统的主要组件；② 标出各部分之间的信任边界（同一个信任边界内的东西由同一 个所有者控制，比如同一个数据中心，或者同一个操作系统账户下运行的进程）；③ 画箭头表示数据在各组件间 如何流动；④ 逐一检查每个组件和每条数据流，尤其要重点关注跨越信任边界的数据流，看看 有没有可能破坏安全目标的地方；⑤ 把找到的威胁记录下来，持续跟踪和修复。

下面是一个虚构的“披萨点餐 API”的数据流图（DFD）示例。Web 浏览器和手机 App 各自处于自己的信任边界 内（外部实体用直角方框表示），点餐 API 运行在数据中心内某个操作系统账户下，数据库进程（DBMS）和它的 数据文件又分别运行在另一个账户下——同一个数据中心里也可以嵌套出好几层信任边界。

要系统性地找出威胁，一个很流行的方法是 STRIDE：

缩写威胁类别含义典型对应机制
SSpoofing 仿冒冒充别人的身份身份认证
TTampering 篡改修改不该由你修改的数据完整性校验 / 访问控制

1.5安全机制总览

威胁可以通过应用安全机制来对抗。几乎每一个设计良好的 API，都会用到下面这五类机制：

  • 加密（Encryption）：防止数据在传输中或落盘后被未授权者读取或篡改。
  • 身份认证（Authentication）：确认用户和客户端真的是他们自称的那个身份。
  • 访问控制（Access control / Authorization）：确保每一个请求都经过恰当的授权。
  • 审计日志（Audit logging）：记录所有操作，支撑事后追责和实时监控。
  • 限流（Rate-limiting）：防止某个用户（或一群用户）耗尽资源、拖垮服务可用性。

这五个机制通常会按顺序，像一串过滤器一样套在你的业务逻辑外面——一个请求要依次穿过它们，只有全部 通过才能真正进入你写的处理函数：

1.5.1 加密

加密保护的是“API 之外”的数据：一是传输中的数据（用 TLS/HTTPS，第 3 章讲）， 二是静态数据，也就是落在磁盘上的数据（数据库加密相关内容会在第 5 章略有涉及）。 现代加密算法不仅能防止数据被偷看，还能防止数据被悄悄篡改。

1.5.2 身份识别与认证

认证要验证的与其说是“用户本身”，不如说是关于用户身份的一个个声明（比如用户名）， 验证声明是否为真，靠的是用户出示的凭证。常见的认证因素分三类：

因素类型例子弱点
你知道什么（Something you know）密码容易设得太弱，或被写在便签上
你有什么（Something you have）手机、硬件密钥可能丢失或被盗
你是什么（Something you are）指纹、虹膜等生物特征识别错误率往往偏高
✅ 什么是双因素 / 多因素认证（2FA / MFA）

任何单一因素都可能被攻破，所以更安全的系统会要求两种及以上不同类型的因素同时 通过验证——比如密码（你知道什么）+ 手机 App 生成的动态验证码（你有什么）。注意：用两个密码登录仍然 只算“单因素”，因为两个都属于“你知道什么”。

1.5.3 访问控制与授权

本书里“访问控制”和“授权”基本混用。它主要有两种思路：基于身份的访问控制先确认 用户是谁，再根据身份和规则判断能不能访问某个资源；基于能力凭证（capability）的访问控制 则把权限直接编码进一个不可伪造的令牌里——拿到令牌就等于拿到了对应的权限，不需要额外核实持有人的身份， 有点像一把物理钥匙：谁拿着钥匙谁就能开门。第 8、9 章会分别详细讲这两种模式。

💡 一个反直觉的例子：维基百科几乎没有访问控制

维基百科允许任何人查看、编辑甚至创建页面，几乎不设访问控制，靠的是强大的版本回滚能力和公开的 编辑历史（也就是审计日志）来兜底——恶意修改可以被轻易撤销，社区规范和“谁改了什么都看得见”这件事本身 就形成了约束。当然，遇到持续的破坏或编辑战，维基百科也会对个别页面临时加上访问限制。

1.5.4 审计日志

一份好的审计日志应该能回答：谁做的、用什么客户端做的、什么时候做的、做了什么类型的操作（读还是改）、 操作了哪个资源、成功了没有（失败原因是什么）、同一时间段还做了哪些别的操作。审计日志既要防篡改，本身 往往又包含个人敏感信息（PII），所以它自己也是需要被机密性保护的资产——这正好呼应了图 1-5 里“开发和 测试会不断发现新资产”的说法。

1.5.5 限流

限流的目标是保护可用性，对抗拒绝服务攻击。攻击者可以靠发送海量请求、超大请求， 或者故意发得很慢来长时间占用连接，耗尽 CPU、内存、连接数等有限资源。防御的核心思路是识别出“某个客户端 （或一群客户端）用掉了超过自己份额的资源”，然后加以限制。

💡 限流（rate-limiting）vs 配额（quota）vs 节流（throttling）

限流通常在用户登录之前就生效，按 IP 或整体请求速率限制；配额 是登录之后针对具体账号的业务规则，比如“每人每天最多发 5 条帖子”；节流则是限流触发 之后的一种柔性处理方式——不是直接掐断连接，而是排队处理或者提示客户端“慢一点”，如果客户端不听， 后续请求才会被拒绝。因为限流本身要足够“便宜”（不能比正常处理请求消耗更多资源），它经常被放在负载 均衡器、反向代理或专门的网关里高效实现，而不是塞进每一个 API 里各写一遍。
