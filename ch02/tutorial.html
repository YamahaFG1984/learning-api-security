安全的 API 开发

从零写一个能创建"社交空间"的 REST API，然后亲手攻破它，再亲手修好它。

假设你有一个绝妙的创业点子：做一个新的社交网络，叫 Natter——面向咖啡叙旧小组、 读书会这类小圈子的社交 App。种子轮融资到账了，用户等着注册，可投资人反复追问一句话："你们的 API 安全吗？" 光靠嘴上保证是没用的，你需要真的把安全做进代码里。

这一章我们就从零搭一个足够小、但足够真实的 REST API：创建一个"社交空间"（social space）。 然后我们会亲手把它攻破——用一段精心构造的用户名，把整张数据库表删掉；再用一个伪装的 HTML 表单，骗浏览器执行我们塞进去的 JavaScript。破坏完之后，再一步步把它修好。比起直接背"要用参数化 查询""要校验输入"这类结论，先看一眼攻击者到底能干什么、为什么能得手，再看防御措施为什么有效， 记忆会牢固得多——这也是本书接下来所有章节的套路：先攻破，再加固。

2.1Natter API 概览

Natter 的核心概念是"社交空间"（space）：任何人都可以创建一个空间，邀请朋友加入，空间里的成员 可以互相发消息。创建空间的人自动成为这个空间的第一个"版主"（moderator），拥有额外的管理权限， 比如删除违规消息。围绕这个模型，Natter 拆成了两个 REST API：

  • Natter API：给普通用户用，负责创建空间、发消息、查消息。
  • Moderation API：给版主用，负责删除违规消息。

两个 API 都用 JSON 通过 HTTP 对外提供服务，背后共用同一个数据库，通过 SQL（在 Java 里是 JDBC）读写数据。

💡 REST 是什么

REST（Representational State Transfer）是一种设计 HTTP API 的风格：用 URI 表示"资源"（比如 某个空间 /spaces/3），用 HTTP 方法表示"动作"（POST 创建、GET 查询、DELETE 删除），用状态码表示结果。 本章我们只实现"创建一个新空间"这一个操作，即 POST /spaces，其余操作留作练习。

本书原书用 Java 11 + Spark Java（一个轻量级 Web 微框架，跟 Apache Spark 大数据平台 完全无关）来写这个 API，数据库用内存版 H2，通过 Dalesbred 库简化 JDBC 调用。为了方便 同时熟悉 Python 和 TypeScript 生态的读者对照学习，本教程会在每个关键知识点上额外给出 Django（Python）和 Hono.js（TypeScript）的等价实现——三者要解决的是 同一个安全问题，只是语法不同。

Natter 的数据库只有两张表：spaces（社交空间）和 messages（消息）。

CREATE TABLE spaces(
    space_id INT PRIMARY KEY,
    name VARCHAR(255) NOT NULL,

CREATE TABLE messages(

2.2开发 REST API：创建 Space

写一个 API 操作，通常都可以拆成三步：解析输入 → 执行操作 → 准备输出。Natter 的"创建空间"操作也不例外：先从请求体的 JSON 里取出空间名和 拥有者，再往数据库插入一条记录并生成一个新的空间 ID，最后返回一个 201 Created 加上新资源的地址。

💡 什么是 Controller

Controller（控制器）是响应用户请求的那部分代码，名字来自 MVC（Model-View-Controller）模式。 在一个典型的 REST API 里，controller 负责把 HTTP 请求翻译成对数据/业务逻辑的操作，再把结果 翻译回 HTTP 响应。把安全相关的横切逻辑（认证、限流……）放到框架的过滤器（filter）里，而不是 散落在每个 controller 里，会让安全审查容易得多——第 3 章开始你会大量用到这个套路。

下面是 SpaceController 里创建空间的核心逻辑（这是本章末尾修复完所有漏洞后的 最终版本，我们会在 2.4、2.5 节逐步讲清楚每一处校验为什么存在）：

ch02/src/main/java/.../controller/SpaceController.java
public class SpaceController {

  private final Database database;

  public SpaceController(Database database) {
    this.database = database;
  }

  public JSONObject createSpace(Request request, Response response) {
    var json = new JSONObject(request.body());
    var spaceName = json.getString("name");
    var owner = json.getString("owner");

    return database.withTransaction(tx -> {
      var spaceId = database.findUniqueLong(
          "SELECT NEXT VALUE FOR space_id_seq;");

      database.updateUnique(
          "INSERT INTO spaces(space_id, name, owner) " +
              "VALUES(?, ?, ?);", spaceId, spaceName, owner);

      response.status(201);
      response.header("Location", "/spaces/" + spaceId);

      return new JSONObject()
          .put("name", spaceName)
          .put("uri", "/spaces/" + spaceId);
    });
  }
}

def create_space(request):
    body = json.loads(request.body)
    space_name = body["name"]
    owner = body["owner"]

    space = Space.objects.create(name=space_name, owner=owner)

    response = JsonResponse(

    return response
src/routes/spaces.ts（教学示例）
import { Hono } from 'hono'
import { db } from '../db'
import { spaces } from '../db/schema'

const app = new Hono()

app.post('/spaces', async (c) => {
  const body = await c.req.json()
  const spaceName: string = body.name
  const owner: string = body.owner

  const [row] = await db
    .insert(spaces)
    .values({ name: spaceName, owner })
    .returning({ id: spaces.id })

  c.header('Location', `/spaces/${row.id}`)
  return c.json({ name: spaceName, uri: `/spaces/${row.id}` }, 201)
})

2.3接入 REST 端点

写好 controller 只是一半，还需要告诉框架"哪个 HTTP 请求该交给哪个方法处理"，这就是 路由（route）。在 Spark 里，路由和框架提供的"过滤器"（filter）是分开的两套机制： 路由负责匹配、调用业务逻辑；过滤器负责在请求处理的前后插入横切逻辑，比如统一设置响应头。 Spark 有三种过滤器：

  • before 过滤器：在请求被处理之前运行，适合做校验、设默认值。
  • after 过滤器：在请求正常处理完之后运行，如果处理过程抛了异常就不会执行。
  • afterAfter 过滤器：无论请求正常完成还是抛出异常（触发了异常处理器），最后都会执行——所以最适合用来设置那些"任何响应都必须带上"的安全响应头，我们会在 2.6 节用到它。

2.4注入攻击：防止 SQL 注入

我们刚才写的 createSpace 是修好之后的版本。原书第一版故意写了一个有漏洞的 版本，用字符串拼接的方式构造 SQL： 

// ⚠️ 危险写法，千万不要抄进真实项目！
database.updateUnique(
    "INSERT INTO spaces(space_id, name, owner) " +
        "VALUES(" + spaceId + ", '" + spaceName +
        "', '" + owner + "');");
☠️ 什么是 SQL 注入

当用户输入被直接拼进要执行的 SQL 语句里时，数据库没有办法区分"这是数据"还是"这是命令的一部分"。 攻击者只要在输入里塞入 SQL 语法片段，就可能让数据库执行他想要的任意语句——这就是 SQL 注入（SQL injection），OWASP Top 10 常年排名第一的漏洞类型，也是"注入攻击" 这个更大类别（包括 LDAP 注入、命令注入、日志注入……）里最常见的一种。

用一个单引号试探一下，服务器直接报 500：

$ curl -i -d '{"name": "test'"'"'space", "owner": "demo"}' \
  http://localhost:4567/spaces
HTTP/1.1 500 Server Error
{"error":"internal server error"}

# 服务器日志：
org.h2.jdbc.JdbcSQLException: Syntax error in SQL statement
"INSERT INTO spaces(space_id, name, owner)
 VALUES(4, 'test'space', 'demo[*]');"

单引号提前把字符串"闭合"了，导致 SQL 语法出错。但如果攻击者精心构造一个语法合法的 输入呢？把 owner 设成 '); DROP TABLE spaces; --：

之后任何人再创建空间都会报错，因为表已经不存在了：

org.h2.jdbc.JdbcSQLException: Table "SPACES" not found;

2.4.1 用预处理语句（PreparedStatement）防止注入

转义特殊字符是一种直觉上的修补方式，但不可靠——不同数据库的特殊字符集不一样，版本升级也可能 改变规则。真正可靠的办法是让用户输入永远不参与 SQL 语句的"拼接"，而是通过 预处理语句（prepared statement）把 SQL 结构和数据分开发送：SQL 语句里只写占位符 （?），真正的参数值单独传给数据库驱动，数据库永远不会把参数值当成语法 去解析。

✅ 最佳实践

预处理语句应该是你防止 SQL 注入的第一道也是最重要的一道防线，而且几乎没有性能代价 （数据库可以缓存编译好的语句模板）。如果你在用 ORM 或其他数据库抽象层，一定要确认它底层真的用了 预处理语句，而不是自己在拼字符串。

2.4.2 用最小权限缓解 SQL 注入

预处理语句是第一道防线，但还有第二道值得加上：即便真的出现了注入漏洞，也不应该让攻击者能删表。 这就是最小权限原则（principle of least authority，POLA）——给每个用户和进程 刚好够用的权限，不多给一分。Natter API 平时只需要往 spaces/ messages 表里 SELECT/INSERT/ DELETE（版主删消息），从来不需要 DROP TABLE 的权限。

📐 原则：最小权限（POLA）

系统里的每个用户和进程都应该只拥有完成本职工作所需要的最少权限——既不多，也不少。这不能阻止 SQL 注入发生，但能把注入攻击造成的损失控制在你明确允许的操作范围之内。

⚠️ 别忘了原始漏洞里的坑

spaceId 是程序自己从数据库序列生成的数字，相对安全；但 spaceName 和 owner 直接来自用户输入。任何请求参数——不管是 JSON body、 URL 查询参数、还是 HTTP 头——只要最终会拼进 SQL、日志、命令行、HTML 里，都要当成潜在的注入点看待， 不能因为它"看起来不像用户能改的字段"就掉以轻心。

2.5输入校验

预处理语句解决了"输入会不会被当成代码执行"的问题，但没有解决"输入本身是不是合理"的问题。数据库表 结构里 owner VARCHAR(30) 已经限制了长度，但如果你只依赖数据库约束来 兜底，会有两个问题：一是数据库报错通常很难看（500 而不是友好的 400），二是很多约束根本没法用数据库 schema 表达（比如"用户名必须在公司 LDAP 目录里存在"）。所以校验应该在进入业务逻辑之前 就完成。

📐 原则：优先定义"允许什么"，而不是"禁止什么"

校验输入时应该用允许列表（allowlist）——精确描述哪些输入是合法的，其余一律拒绝； 而不是拒绝列表（denylist）——列举哪些输入是非法的，其余都放行。拒绝列表的问题在于， 你几乎不可能穷举所有恶意输入的花样，一旦漏掉一种，攻击者就能绕过去。

对 Natter 来说：空间名不能超过 255 个字符（对应数据库列的长度），用户名不能超过 30 个字符，并且 只能是字母开头、后面跟字母或数字（用正则表达式 [a-zA-Z][a-zA-Z0-9]{1,29} 描述这个"允许列表"）。

⚠️ 小心 ReDoS（正则表达式拒绝服务）

有些正则表达式在匹配特定输入时会触发大量回溯，导致 CPU 占用飙升，这种攻击叫 ReDoS（Regular Expression Denial of Service）。经典例子是 ^(a|aa)+$ 这种"一个字符串有多种方式匹配同一个重复模式"的写法。 写正则时尽量保证每一段重复结构对任意输入只有唯一的匹配方式，拿不准的话就换成更简单的字符串操作。

    throw new HTTPException(400, { message: 'invalid input' })
  }
  const { name: spaceName, owner } = parsed.data
  // ... 校验通过后才进入数据库写入逻辑
})
💡 输入校验之外：为什么 Java 不用太担心缓冲区溢出

如果用 C/C++ 这类没有内存安全保护的语言，忘记检查输入长度可能导致缓冲区溢出， 进而演变成远程代码执行（RCE）。Java、Python、TypeScript 这些内存安全的语言运行时会自动做边界 检查，不会有这类内存破坏问题；但反序列化不受信任的数据仍然可能触发 RCE（比如某些 Java 反序列化库 的历史漏洞），所以处理 XML、二进制协议这类复杂格式时依然要格外小心，优先用简单、规范明确的格式 （比如 JSON）并使用成熟的解析库。

2.6安全输出：防止 XSS

校验完输入还不够——如果你把没校验通过的原始输入原样"回显"给客户端，而客户端恰好是一个网页浏览器， 就可能触发另一类攻击：跨站脚本攻击（Cross-Site Scripting，XSS）。我们的 API 目前 有三个问题都会助长这个攻击：

  1. 报错信息里带上了 Java 异常的类名和堆栈细节，帮攻击者摸清你用的技术栈。
  2. 校验失败时，把用户提交的原始（未转义的）内容原样塞进了错误信息里返回。
  3. 默认的错误响应 Content-Type 是 text/html，而不是 application/json。
💡 什么是 XSS

XSS 是指攻击者想办法让自己的脚本，在受害者浏览器里以"目标网站"的身份执行。浏览器的同源策略 （same-origin policy）默认允许同源脚本读取该站点的 cookie、操作页面 DOM、发起该站点的网络请求； 一旦 XSS 得手，攻击者的脚本就能拿到这些能力。XSS 分三种：存储型（persistent）—— 恶意脚本被存进了服务器数据，之后任何人访问都会触发；反射型（reflected）——恶意 脚本藏在一次请求里，服务器把它原样"反射"回响应中；DOM 型——发生在浏览器端 JS 动态拼接 HTML 的过程中。哪怕你的 API 只返回 JSON，只要浏览器最终会把响应当 HTML 解释，就仍然可能 中招——接下来我们就现场演示一次。

攻击者可以构造一个自动提交的 HTML 表单，利用 enctype="text/plain" 让 浏览器把表单字段拼成看起来像 JSON 的纯文本，绕过"浏览器不能直接发 application/json 表单"的限制： 

<!DOCTYPE html>
<html>
<body>
<form id="test" action="http://localhost:4567/spaces"
      method="post" enctype="text/plain">
    <input type="hidden" name='{"x":"'
           value='","name":"x", "owner":"&lt;script&gt;alert(&apos;XSS!&apos;);
&lt;/script&gt;"}' />
</form>
<script type="text/javascript">
document.getElementById("test").submit();
</script>
</body>
</html>

来自 ch02/xss.html——受害者只要打开这个页面，脚本就会自动提交表单。

2.6.1 防止 XSS

防御手段没有单独一招就能解决问题，需要几层一起上：

  • 对输入严格把关：要求 POST 请求必须带 Content-Type: application/json，HTML 表单没法伪造出这个头，上面的攻击手法直接失效。
  • 只用规范的 JSON 库生成输出，不要手动拼字符串。
  • 每个响应都显式设置正确的 Content-Type，尤其是错误响应——这些最容易被忽略。
  • 永远不要把 Accept 请求头的值直接抄进响应的 Content-Type，而要显式指定你实际产出的类型。

此外，给所有响应加上几个标准安全响应头，即便真出现了 XSS，也能限制它能干的事：

响应头作用说明
X-Content-Type-Options: nosniff 禁止浏览器"嗅探"内容类型 没有这个头，浏览器可能无视你的 Content-Type，自己猜内容是 HTML/JS 并执行。
X-Frame-Options: DENY 禁止响应被嵌入 iframe 防止"拖拽劫持"（clickjacking）之类的攻击，新版浏览器建议改用 CSP 的 frame-ancestors。
X-XSS-Protection: 0 关闭浏览器内置的 XSS 过滤器 这类过滤器自身也被发现过安全问题，OWASP 现在建议直接设为 0，完全关闭。
Cache-Control: no-store 禁止缓存响应内容 避免敏感数据被浏览器或中间代理缓存下来。
Content-Security-Policy 限制脚本、iframe 等能加载的来源 对纯 API 响应推荐 default-src 'none'; frame-ancestors 'none'; sandbox，即便被注入也几乎什么都做不了。
✅ 为什么这些头要放进 afterAfter 过滤器

回顾图 2-3：只有 afterAfter 过滤器保证无论请求正常处理还是抛出异常都会执行。如果把安全响应头放 在普通的 after 过滤器里，一旦请求过程抛了异常（比如校验失败），这些头就会被漏掉——而错误响应恰恰 是最容易被拿来做 XSS 的地方。

ch02/src/main/java/.../Main.java
before(((request, response) -> {
    if (request.requestMethod().equals("POST") &&
    !"application/json".equals(request.contentType())) {
        halt(415, new JSONObject().put(
            "error", "Only application/json supported"
        ).toString());
    }
}));

afterAfter((request, response) -> {
    response.type("application/json;charset=utf-8");
    response.header("X-Content-Type-Options", "nosniff");
    response.header("X-Frame-Options", "DENY");
    response.header("X-XSS-Protection", "0");
    response.header("Cache-Control", "no-store");
    response.header("Content-Security-Policy",
            "default-src 'none'; frame-ancestors 'none'; sandbox");
    response.header("Server", "");
});
core/middleware.py + settings.py（教学示例）
# core/middleware.py
from django.http import JsonResponse

class EnforceJsonContentTypeMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        if (request.method == "POST"
                and request.content_type != "application/json"):
            return JsonResponse(
                {"error": "Only application/json supported"},
                status=415,
            )
        response = self.get_response(request)
        response["X-Content-Type-Options"] = "nosniff"
        response["X-Frame-Options"] = "DENY"
        response["Cache-Control"] = "no-store"
        response["Content-Security-Policy"] = (
            "default-src 'none'; frame-ancestors 'none'; sandbox"
        )
        return response
# settings.py：Django 内置的同类安全设置（覆盖大部分场景）

最后一步是让错误响应不再泄露异常细节和用户输入。就算加了上面这些安全头，也不该把未经处理的用户 输入直接塞进响应——安全头有可能被后来的改动不小心删掉，防御要分层，不能只靠一道。

private static void badRequest(Exception ex,
    Request request, Response response) {
  response.status(400);
  // 只回传 ex.getMessage()，不回传异常类名/堆栈，
  // 而且 message 本身也不该再拼用户的原始输入（见 2.5 节）
  response.body(new JSONObject()
      .put("error", ex.getMessage()).toString());
}

  if (err instanceof HTTPException) {

本章小结

机制要防的攻击 / 风险核心手段
解析 / 执行 / 输出三段式 逻辑混乱、安全检查散落各处 把 controller 拆成"解析输入 → 执行操作 → 准备输出"三步，安全相关的横切逻辑放进过滤器
预处理语句（PreparedStatement） SQL 注入——攻击者用输入改写你的 SQL 语句 SQL 结构和用户输入分开发送，用占位符 ? 代替字符串拼接
最小权限（POLA） 注入一旦得手，破坏范围失控 数据库账号只授予业务实际需要的 SELECT / INSERT / DELETE，绝不授予 DROP / ALTER
输入校验 越界数据、格式错误的数据进入业务逻辑 用允许列表（而非拒绝列表）校验长度和字符集，正则要避免 ReDoS
正确的 Content-Type + 安全响应头 反射型 XSS——浏览器把 API 响应当 HTML 执行 强制校验请求 Content-Type，响应始终显式声明 application/json，加上 X-Content-Type-Options 等安全头
克制的错误响应 信息泄露、把用户输入原样回显造成 XSS 错误信息不带异常类名/堆栈，也不拼接未经处理的用户输入
