第 12 章

保护物联网通信

当 API 的另一端不再是数据中心里的服务器，而是散落在田间地头、靠电池供电的传感器时，安全该怎么做？

前面十一章讲的所有 API，客户端和服务器基本都跑在体面的环境里：机房有门禁，电脑有像样的 CPU 和内存，网络是可靠的 TCP。这一章要换一个场景——物联网（IoT，Internet of Things）设备。 想象一下：一个装在灌溉阀门上的湿度传感器，靠一颗纽扣电池撑一年，芯片内存以 KB 计算（不是 GB），常年放在没人看守的野外，通过低功耗无线（比如蓝牙 BLE）把数据发给附近的网关，网关再转 成 MQTT 消息发到云端，云端再转成一次 HTTP 请求写进数据库。这条链路上，我们熟悉的"直接对着 服务器建一条 HTTPS 连接"根本不存在——设备资源不够跑标准 TLS 的那套证书验证逻辑，网络本身 也不是可靠的 TCP，而且消息中途要经过好几个网关，每一跳都可能是攻击者的切入点。这一章要解决 两个问题：怎么在这样的设备上做传输层加密（也就是 DTLS 和预共享密钥），以及 怎么让加密"穿透"中间那些网关，做到只有真正的接收方才能看懂消息内容（也就是 端到端安全）。最后再聊聊这些资源受限的设备要怎么管理、分发和更新它们的密钥。

💡 什么是"受限设备"（constrained device）

受限设备是指 CPU、内存、网络带宽或电力明显弱于一台普通服务器甚至智能手机的设备——内存 可能只有几十 KB，而不是几 GB。RFC 7228 专门定义了这类设备的分级。本章的很多设计取舍， 根源都是"这段代码要能塞进一颗几毛钱的芯片里，还要尽量少费电"。

12.1传输层安全：把 TLS 搬到 UDP 上

普通 Web API 几乎都建立在 TCP 之上：TCP 负责保证字节按顺序、不丢失地到达，TLS 在这之上 加一层加密和身份验证。但 TCP 对受限设备并不友好：

  • TCP 协议栈本身代码量不小，在寸土寸金的设备闪存里是笔不小的开销；
  • TCP 的可靠性要求发送方把消息缓存起来，直到收到确认——这对内存本就紧张的设备是负担， 而且很多传感器数据是"实时流"，丢了一条重发也没意义，新数据很快就会覆盖它；
  • TCP 报文头至少 16 字节，对本来只有几个字节的传感器读数来说，这个开销占比高得离谱；
  • TCP 不支持组播，没法一次把消息发给一大批设备；
  • 设备为了省电经常休眠，一休眠 TCP 连接就断了，醒来后重新握手成本很高。

所以很多物联网协议（比如受限应用协议 CoAP）干脆放弃 TCP，直接跑在更简单、"发了就不管" 的 UDP 之上。但 UDP 本身不提供任何加密，于是就有了 DTLS。

12.1.1 Datagram TLS（DTLS）

💡 什么是 DTLS

Datagram TLS 是 TLS 的一个变种，设计给基于 UDP 的协议使用而不是基于 TCP 的协议。它提供 和 TLS 一样的加密与身份验证，唯一的差别是：UDP 报文本来就可能丢失、重复或乱序到达，DTLS 必须自己在协议里处理这些情况（比如给每条记录加上显式的序号），而不能像 TCP+TLS 那样假设 "字节流一定按顺序完整到达"。

Java 对 DTLS 的支持停留在很底层的 SSLEngine API——它只是一个纯粹的 协议状态机，不像 SSLSocket 那样帮你把网络收发都封装好，你需要自己写 循环，不断调用 wrap()（把待发送的应用数据打包成 DTLS 报文）和 unwrap()（把收到的 DTLS 报文解出应用数据），并根据 engine.getHandshakeStatus() 返回的 NEED_WRAP / NEED_UNWRAP / NEED_TASK 状态决定下一步做什么。本章配套代码里的 DtlsDatagramChannel 类把这套循环封装好了，业务代码只需要调用它的 bind() / connect() / send() / receive()。下面是服务端和客户端最核心的部分：

ch12/src/main/java/com/manning/apisecurityinaction/DtlsServer.java

public class DtlsServer {
    public static void main(String... args) throws Exception {
        try (var channel = new DtlsDatagramChannel(getServerContext())) {
            channel.bind(54321);
            var buffer = ByteBuffer.allocate(2048);
            while (true) {
                channel.receive(buffer);
                buffer.flip();
                var data = UTF_8.decode(buffer).toString();
                logger.info("Received: {}", data);
                buffer.compact();
            }
        }
    }

    private static SSLContext getServerContext() throws Exception {
        var sslContext = SSLContext.getInstance("DTLS");
        var keyStore = KeyStore.getInstance("PKCS12");
        keyStore.load(new FileInputStream("localhost.p12"), "changeit".toCharArray());
        var keyManager = KeyManagerFactory.getInstance("PKIX");
        keyManager.init(keyStore, "changeit".toCharArray());
        sslContext.init(keyManager.getKeyManagers(), null, null);
        return sslContext;
    }
}
⚠️ 这段示例代码没有处理丢包重传

书里明确提醒：这个 DtlsDatagramChannel 只是用来演示 DTLS 握手和收发 流程，如果客户端和服务器隔着真实网络（而不是本机回环），丢包是大概率事件，这段代码并不会重发。 生产环境要么用 CoAP 这类已经把重传逻辑做好的高层协议，要么直接用专门的 DTLS 库（比如 mbedTLS、 WolfSSL），不要在生产系统里 裸用这段教学代码。

💡 这一节和 Django / Hono.js 有什么关系？

几乎没有关系——这是纯粹的传输层/协议层内容。DTLS 跑在 UDP 上，而 Django、Hono.js 这类 Web 框架是建立在 TCP + HTTP 之上的，它们根本不会去处理 UDP 握手这件事。真实项目里，这一层 通常交给专门的嵌入式 TLS 库（C 语言居多）或者网关设备去做，应用框架拿到的已经是解密后的 业务数据。所以这一节我们只展示 Java 原书代码，不去编造 Django/Hono 里并不存在的 DTLS API。

12.1.2 面向受限设备的密码套件

普通 Web 服务器的 TLS 密码套件推荐（比如 Mozilla 的建议）是为了在数据中心里追求"又快又安全" 设计的，但直接照搬到受限设备上会出问题：

  • 一个套件比如 ECDHE-RSA-AES256-SHA384 要同时实现椭圆曲线密钥交换、 RSA 签名、AES 加解密、SHA-384 哈希——每多一种算法就多一份代码体积；
  • AES-GCM 在带硬件加速的服务器芯片上很快，但在软件里实现容易出错，一旦 nonce（每条消息 用于加密的"一次性数字"）不小心重复使用，安全性会灾难性地崩溃；
  • SHA-384/SHA-512 这类为 64 位架构优化的哈希函数，在常见的 8/32 位单片机上反而慢；
  • 带前向保密的套件都要同时实现签名算法和密钥交换算法，代码量进一步膨胀。
☠️ 为什么 DTLS 特别容易踩 AES-GCM 的 nonce 重用坑

AES-GCM 只要同一个 nonce 被用来加密两条不同的消息，安全性就几乎归零。TLS 1.3 之后靠"nonce 由记录序号推导"来避免意外重用，但前提是序号必须严格递增、不重复。DTLS 因为跑在不可靠的 UDP 上，必须容忍重传、乱序甚至重复的报文，这就让"序号绝对不重复"这个前提变得脆弱得多。所以本章 建议在 DTLS 场景下优先选 AES-CCM 或 ChaCha20-Poly1305，而不是 AES-GCM——前者只需要一个 AES 加密电路就能完成全部操作，代码体积小；后者是纯软件实现也能跑得 很快的流密码，即使 nonce 意外重复，泄露的信息也比 GCM 少得多。

选择优点要注意什么
AES-CCM / CCM_8只需要 AES 加密电路，代码体积小，硬件安全芯片常自带支持 _CCM_8 认证标签只有 64 位，容易被暴力破解伪造，配合限流使用
ChaCha20-Poly1305纯软件实现性能好，无需 AES 硬件加速，适合没有安全芯片的设备 Java 12+ 才原生支持，nonce 依然不能重复（只是后果比 GCM 轻）
裸公钥（Raw Public Key）省掉复杂的 X.509 证书解析和校验代码 公钥要在设备出厂时就手工分发好，不能像证书一样临时验证

12.2预共享密钥（PSK）

有些设备连椭圆曲线签名、密钥交换这类公钥算法都跑不动。这时可以放弃证书体系，改用 预共享密钥：客户端和服务器提前（比如出厂时）就约定好同一把对称密钥，握手时 只需要证明"我确实持有这把密钥"，完全不涉及签名和证书解析，代码体积能大幅缩小。

💡 什么是 PSK（Pre-Shared Key）

PSK 是提前直接分发给客户端和服务器双方的一把对称密钥。因为双方用的是同一把密钥，PSK 天然提供"双向"认证——服务器信任客户端，客户端也顺带验证了服务器（毕竟只有真服务器才会算出 正确的握手 HMAC）。这一点和证书认证不同：证书里有客户端的"名字"，而 PSK 只是一个不透明的 标识符，服务器必须自己维护"这个 PSK 属于哪个设备"的映射关系。

ch12/.../PskServer.java 用的是 Bouncy Castle 的底层 DTLS API （不是标准 SSLEngine，因为 Java 内置的 SSLEngine 目前不支持 AES-CCM）：

var psk = loadPsk(args[0].toCharArray());
var crypto = new BcTlsCrypto(new SecureRandom());
var server = new PSKTlsServer(crypto, getIdentityManager(psk)) {
    @Override
    protected ProtocolVersion[] getSupportedVersions() {
        return ProtocolVersion.DTLSv12.only();
    }
    @Override
    protected int[] getSupportedCipherSuites() {
        return new int[] {
                CipherSuite.TLS_PSK_WITH_AES_128_CCM,
                CipherSuite.TLS_PSK_WITH_AES_128_CCM_8,
                CipherSuite.TLS_PSK_WITH_CHACHA20_POLY1305_SHA256
        };
    }
};
// ...等待第一个 UDP 包到达后 connect()，再用 DTLSServerProtocol 完成握手

static TlsPSKIdentityManager getIdentityManager(byte[] psk) {
    return new TlsPSKIdentityManager() {
        public byte[] getHint() { return null; }          // 不给客户端提示
        public byte[] getPSK(byte[] identity) { return psk; }  // 所有客户端返回同一把 PSK（教学简化）
    };
}

static byte[] loadPsk(char[] password) throws Exception {
    var keyStore = KeyStore.getInstance("PKCS12");
    keyStore.load(new FileInputStream("keystore.p12"), password);
    return keyStore.getKey("aes-key", password).getEncoded();
}
⚠️ PSK 不是密码，不能随便挑一个"好记的"字符串

PSK 在协议上允许任意长度，但必须是一个高熵、随机生成的值（比如 128 位的随机字节）， 绝不能用密码那种"人能记住"的字符串。原因很简单：攻击者只要抓到一次完整的握手，就能离线 对 PSK 做字典/暴力破解，不像密码那样有服务器端限流保护。

☠️ 裸 PSK 没有前向保密

用书里 PskClient.java 里那样的裸 PSK 套件（比如 TLS_PSK_WITH_AES_128_CCM），会话密钥完全由 PSK + 双方随机数推导， 一旦这把 PSK 泄露，攻击者只要之前录下过握手报文，就能把这台设备历史上所有的 通信内容全部解密。如果数据敏感、设备又扛得住一点公钥运算，应该选带 ECDHE 的 PSK 套件（比如 TLS_ECDHE_PSK_WITH_AES_128_CCM_SHA256），双方各自 生成一次性的临时密钥对，参与会话密钥推导，PSK 泄露也翻不出旧会话的内容——这正是"前向保密"。

💡 这一节的三栏代码去哪了？

和 DTLS 一样，PSK 密码套件是 TLS/DTLS 协议内部的握手细节，和 Django、Hono.js 这类跑在 HTTP 之上的 Web 框架没有直接对应关系——它们既不会去协商密码套件，也不会自己维护 PSK 身份表。 顺带一提：Python 标准库 ssl 模块从 3.13 版本起新增了 SSLContext.set_psk_client_callback() / set_psk_server_callback()，可以在基于 TCP 的 TLS 连接上使用 PSK 认证，但它依然不支持 DTLS（Python 的 ssl 模块本身 就只能包装流式 socket），所以这里不勉强凑三栏对比，只展示真实的 Java 源码。

12.3端到端安全

DTLS/PSK 只能保证"这一跳"是加密的。可现实中的物联网消息经常要经过好几跳、好几种协议： 传感器用 BLE 把数据发给附近的网关，网关翻译成 MQTT 转发给消息队列，另一个服务再把它翻译成 一次 HTTP POST 发给云端 API。每一跳单独用 TLS 加密没问题，问题在于：数据在每个中间 网关上都会被解密出来，因为网关得先看懂内容才能决定怎么转发。这就让每个网关都成了 有价值的攻击目标——只要攻破一个，就能看到、甚至篡改流经它的所有数据。

✅ 端到端安全不是取代传输层安全

两者要一起用：传输层的 DTLS/TLS 保护的是这一跳的所有内容，包括协议头；端到端加密只保护 应用数据本身，不保护外层协议头（比如 MQTT 主题名）。缺了传输层加密，中间网络也能被窃听或 篡改协议头；缺了端到端加密，攻陷任意一个中间节点就能看到明文业务数据。

12.3.1 COSE：给二进制格式的"JOSE"

受限设备通常不用 JSON——数字用十进制字符串写出来太浪费空间了，业界更常用 CBOR（Concise Binary Object Representation）这种紧凑的二进制格式，数据模型和 JSON 基本对应（对象、数组、字符串、数字），但省去了大量文本编码的开销。对应 JOSE 的 CBOR 版本 就是 COSE（CBOR Object Signing and Encryption）：一样能做签名、加密，只是 算法集合更贴近受限设备（比如支持 AES-CCM），同时去掉了一些有已知弱点的老算法。

💡 COSE 里的 HKDF 是用来解决什么问题的

COSE 的认证加密算法都要求一个较短的 nonce，短到不适合每次随机生成（重复概率不可忽略）。 COSE 的做法是：不直接拿主密钥去加密，而是每条消息都生成一个随机数（nonce），配合 HKDF 从主密钥派生出这一条消息专用的密钥。这样即使随机数意外重复，泄露的也只是 "两条消息用了同一把派生密钥"，而不会直接导致主密钥或大量历史消息暴露。COSE 还允许把发送方 （PartyU）、接收方（PartyV）的身份标识一起混入密钥派生，这样"把 Bob 发给 Alice 的消息原样 重放给 Alice"（反射攻击）也会因为派生出错误的密钥而失败。

ch12/.../CoseEncryptionExample.java（节选）
Security.addProvider(new BouncyCastleProvider());
var keyMaterial = PskServer.loadPsk("changeit".toCharArray());

var recipient = new Recipient();
var keyData = CBORObject.NewMap()
        .Add(KeyKeys.KeyType.AsCBOR(), KeyKeys.KeyType_Octet)
        .Add(KeyKeys.Octet_K.AsCBOR(), keyMaterial);
recipient.SetKey(new OneKey(keyData));
recipient.addAttribute(HeaderKeys.Algorithm,
        AlgorithmID.HKDF_HMAC_SHA_256.AsCBOR(), Attribute.PROTECTED);

var nonce = new byte[16];
random.nextBytes(nonce);
recipient.addAttribute(HeaderKeys.HKDF_Context_PartyU_nonce,
        CBORObject.FromObject(nonce), Attribute.PROTECTED);

var message = new EncryptMessage();
message.SetContent("Hello, World!");
message.addAttribute(HeaderKeys.Algorithm,
        AlgorithmID.AES_CCM_16_128_128.AsCBOR(), Attribute.PROTECTED);
message.addRecipient(recipient);
message.encrypt();

System.out.println(Base64url.encode(message.EncodeToBytes()));
iot/cose_demo.py（教学示例，简化版，不是完整 COSE/RFC 8152 实现； 完整实现可参考 pycose 库）
import os
import cbor2
from cryptography.hazmat.primitives.ciphers.aead import AESCCM

key_material = load_psk("changeit")        # 32 字节主密钥（来自 keystore）
aesccm = AESCCM(key_material[:16], tag_length=16)

# 用一个随机 nonce 代表 COSE 里"每条消息独立派生密钥"的思路
nonce = os.urandom(13)                     # AES-CCM 要求 7~13 字节 nonce
payload = cbor2.dumps({"sensor": "F5671434", "reading": 1234})

ciphertext = aesccm.encrypt(nonce, payload, associated_data=b"partyU-nonce")
envelope = cbor2.dumps({"nonce": nonce, "ciphertext": ciphertext})

# 接收方用同一把 key_material 解密
plaintext = aesccm.decrypt(nonce, ciphertext, associated_data=b"partyU-nonce")
reading = cbor2.loads(plaintext)
src/iot/cose.ts（教学示例，简化版，不是完整 COSE 实现； 更贴近规范可参考 cose-js）
import crypto from "node:crypto";
import cbor from "cbor";

const keyMaterial = loadPsk("changeit");        // 32 字节主密钥
const nonce = crypto.randomBytes(13);           // AES-CCM nonce 7~13 字节

const payload = cbor.encode({ sensor: "F5671434", reading: 1234 });

const cipher = crypto.createCipheriv(
  "aes-128-ccm",
  keyMaterial.subarray(0, 16),
  nonce,
  { authTagLength: 16 },
);
cipher.setAAD(Buffer.from("partyU-nonce"));
const ciphertext = Buffer.concat([cipher.update(payload), cipher.final()]);
const authTag = cipher.getAuthTag();

const envelope = cbor.encode({ nonce, ciphertext, authTag });

12.3.2 COSE 的替代方案：NaCl

如果不需要跨厂商互操作，COSE 支持的算法组合太多反而是负担（书里作者数过，COSE 算法注册表 里有 61 种算法变体）。这种情况下可以直接用 NaCl（Networking and Cryptography Library，第 6 章已经用过）——它把"该用什么算法"这个决定权从开发者手里拿走，帮你选好一套经过 专家审查、组合安全的算法。如果设备能做一点公钥运算，NaCl 的 CryptoBox 还能提供带发送方认证的公钥加密：

ch12/.../NaclCborExample.java
var senderKeys = CryptoBox.keyPair();
var recipientKeys = CryptoBox.keyPair();
var cborMap = CBORObject.NewMap()
        .Add("foo", "bar")
        .Add("data", 12345);

var sent = CryptoBox.encrypt(senderKeys.getPrivate(),
        recipientKeys.getPublic(), cborMap.EncodeToBytes());

var recvd = CryptoBox.fromString(sent.toString());
var cbor = recvd.decrypt(recipientKeys.getPrivate(),
        senderKeys.getPublic());
System.out.println(CBORObject.DecodeFromBytes(cbor));
iot/nacl_box.py（教学示例，使用 PyNaCl / libsodium 绑定）
from nacl.public import PrivateKey, Box
import cbor2

sender_keys = PrivateKey.generate()
recipient_keys = PrivateKey.generate()

cbor_payload = cbor2.dumps({"foo": "bar", "data": 12345})

box = Box(sender_keys, recipient_keys.public_key)
sent = box.encrypt(cbor_payload)        # nonce 由 PyNaCl 自动生成并附带在结果里

recv_box = Box(recipient_keys, sender_keys.public_key)
plaintext = recv_box.decrypt(sent)
print(cbor2.loads(plaintext))
src/iot/naclBox.ts（教学示例，使用 tweetnacl）
import nacl from "tweetnacl";
import cbor from "cbor";

const senderKeys = nacl.box.keyPair();
const recipientKeys = nacl.box.keyPair();

const cborPayload = cbor.encode({ foo: "bar", data: 12345 });
const nonce = nacl.randomBytes(nacl.box.nonceLength);

const sent = nacl.box(cborPayload, nonce, recipientKeys.publicKey, senderKeys.secretKey);

const opened = nacl.box.open(sent, nonce, senderKeys.publicKey, recipientKeys.secretKey);
console.log(cbor.decode(Buffer.from(opened)));

12.3.3 抗误用的认证加密（SIV-AES）

无论用 COSE 还是 NaCl，前提都是设备能可靠地生成随机 nonce。但很多受限设备恰恰缺乏好的 随机数来源（没有可靠时钟、没有硬件随机数发生器），一旦 nonce 意外重复，普通的认证加密算法会 灾难性失败。抗误用认证加密（MRAE，Misuse-Resistant Authenticated Encryption） 就是为这种场景设计的：即使 nonce 不小心重复了，损失也很小——攻击者最多只能知道"这两条消息内容 完全一样"，既不会泄露明文，也不会让攻击者伪造消息。

✅ 什么时候选 SIV-AES

如果设备缺乏可靠的随机数来源，或者你不放心自己/团队能不能把 nonce 管理得万无一失，SIV-AES 是比 AES-CCM/ChaCha20-Poly1305 更保险的选择：即使 nonce 真的重复了，也只会轻微降级，不会像 AES-GCM 那样直接泄露明文或允许伪造消息。代价是它需要对消息做两遍处理（先算 MAC 再加密）， 比单遍的 AEAD 算法慢一些。

12.4密钥分发与管理

普通 API 用公钥基础设施（PKI，第 10 章讲过）解决密钥分发问题：每个设备有自己的密钥对和 CA 签名的证书。但对做不了公钥运算的受限设备，只能退回对称密钥，而对称密钥必须让通信双方 都持有同一份——这在设备数量庞大时就成了一个需要专门方案的问题。

12.4.1 一次性密钥预配

最简单的做法是在设备出厂（或组织采购设备）时，一次性把密钥写入设备的只读存储，同时把加密 后的密钥连同设备序列号存进一个中心目录（比如 LDAP），供 API 服务器按需查询。工厂里通常会用 硬件安全模块（HSM）来安全地生成和保管这批主密钥。

另一种做法是不给每台设备存一把完全随机的密钥，而是用 HKDF 从一把主密钥加上设备的唯一标识 （序列号、MAC 地址）派生出设备专属密钥。这样服务器不需要把成千上万台设备的密钥都存进数据库， 只要知道主密钥和设备标识，现算就行——微软 Azure IoT Hub 的设备批量注册用的就是类似思路。

12.4.2 密钥分发服务器

比"一锤子买卖"更灵活的方案是用一台密钥分发服务器：设备先用出厂时的初始 密钥完成一次注册，之后分发服务器会定期用旧密钥加密、发给设备一把新密钥。这样设备不需要自己 生成随机数（很多受限设备缺乏好的熵源），也能定期换密钥。也可以借助已有的协议来做这件事，比如 草案中的 OAuth2 扩展支持在签发访问令牌的同时分发一把对称密钥（第 13 章还会继续聊 OAuth2 在 物联网里的用法）。

12.4.3 为前向保密做棘轮（ratcheting）

如果设备一直用同一把密钥，密钥一旦泄露，攻击者不但能解密以后的通信，连之前录下来的历史 消息也能一并解密。棘轮提供了一种纯对称密码学的解决办法：每隔一段时间（比如 每天、每小时，或者每发 10 条消息），用一个单向函数把旧密钥"转"成一把新密钥，然后彻底丢弃旧 密钥。因为这个函数只能往前推、不能往后退，即使将来某把新密钥泄露，也没法从它反推出更早的 旧密钥，历史消息依然安全。

ch12/.../RatchetExample.java
private static byte[] ratchet(byte[] oldKey) throws Exception {
    var cipher = Cipher.getInstance("AES/CTR/NoPadding");
    var iv = new byte[16];
    Arrays.fill(iv, (byte) 0xFF);          // 保留全 1 的 IV 专门用于棘轮，绝不用来加密消息
    cipher.init(Cipher.ENCRYPT_MODE,
            new SecretKeySpec(oldKey, "AES"), new IvParameterSpec(iv));
    return cipher.doFinal(new byte[32]);   // 加密 32 个全零字节，输出即为新密钥
}

var key = PskServer.loadPsk(args[0].toCharArray());
for (int i = 0; i < 10; ++i) {
    var newKey = ratchet(key);
    Arrays.fill(key, (byte) 0);            // 旧密钥用完立刻清零
    key = newKey;
}

from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes

def ratchet(old_key: bytes) -> bytes:
    iv = b"\xff" * 16                       # 保留全 1 的 IV 专门用于棘轮
    encryptor = Cipher(algorithms.AES(old_key), modes.CTR(iv)).encryptor()
    return encryptor.update(b"\x00" * 32) + encryptor.finalize()

key = load_psk("changeit")
for _ in range(10):
    new_key = ratchet(key)
    key = new_key                           # 旧 key 应尽快从内存中清除
src/iot/ratchet.ts（教学示例）
import crypto from "node:crypto";

function ratchet(oldKey: Buffer): Buffer {
  const iv = Buffer.alloc(16, 0xff);        // 保留全 1 的 IV 专门用于棘轮
  const cipher = crypto.createCipheriv("aes-256-ctr", oldKey, iv);
  return Buffer.concat([cipher.update(Buffer.alloc(32)), cipher.final()]);
}

let key = loadPsk("changeit");
for (let i = 0; i < 10; i++) {
  const newKey = ratchet(key);
  key.fill(0);                              // 旧 key 尽快清零
  key = newKey;
}
⚠️ 棘轮双方必须在同一个时刻"转"

棘轮只有在客户端和服务器都清楚"什么时候该转"的前提下才有效，否则两边会算出不同的密钥。 通常约定在固定的时间点（每天/每小时）或固定的消息数之后转动。按消息数棘轮还有个额外好处： 如果服务器发现某台设备发来的消息数量比预期多（棘轮提前触发了），这往往说明设备密钥已经被 别人拿去用了——可以当作一种入侵检测信号。

12.4.4 后妥协安全性（post-compromise security）

前向保密回答的是"密钥泄露后，过去的消息还安全吗"，而 后妥协安全性回答的是相反的问题："密钥泄露后，未来的消息还能 恢复安全吗"。棘轮机制对这个问题无能为力——攻击者一旦拿到当前的棘轮密钥，就能顺着同一个单向 函数把后续所有密钥都算出来。

☠️ 前向保密 ≠ 后妥协安全，这是最容易混淆的一对概念

前向保密保护的是"过去"，后妥协安全保护的是"未来"，二者互不包含。单靠棘轮只能拿到前向 保密；要拿到后妥协安全，要么依赖安全硬件（TPM、TEE、安全元件芯片），让攻击者即便攻陷了 运行环境也拿不到裸密钥本身；要么依赖一次不被攻击者干扰的密钥交换——比如双方各自生成一次性 公私钥对，做一次 Diffie-Hellman 交换，把结果混入下一次棘轮。只要有那么一次交换没被主动 中间人攻击拦截篡改，安全性就能重新建立起来。

现实中，达到严格的后妥协安全性成本相当高（要么加硬件，要么加复杂的密码学协议），多数物联网 项目更该把预算优先花在"从一开始就避免设备被攻陷"上；只有面向特别敏感数据或高价值资产的设备， 才值得为后妥协安全专门投入。
