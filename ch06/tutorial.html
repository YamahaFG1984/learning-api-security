第 6 章

自包含 Token 与 JWT

Natter 的用户涨到了几百万，数据库里那张 token 表快扛不住了——这一章教你怎么把"谁登录了、什么时候过期"这些状态直接塞进 token 本身，让服务器不用再查库就能验证身份，以及这么做要付出什么安全代价。

第 5 章里，Natter 用的是数据库 token：登录时服务器生成一个随机 ID，存进数据库， 再把这个 ID 作为 token 发给客户端。以后每次请求，服务器都要拿着这个 ID 去数据库里查一遍， 看看这个 token 是谁的、有没有过期、有没有被撤销。这就像去健身房办了张会员卡——卡本身只是一串编号， 前台每次都要刷卡查电脑里的会员记录才知道你是谁、卡还有没有效。

这一章要讲的自包含 token（self-contained token）换了个思路：与其让服务器每次都去 "查电脑"，不如直接把会员信息（姓名、到期日）印在卡面上，再用防伪水印保证没人能改。服务器拿到卡， 看一眼卡面、验一下水印，就知道这张卡是不是真的、有没有过期，完全不用联网查库。这正是 JWT （JSON Web Token，读作 "jot"）要解决的问题。但"把数据印在卡面上"也带来了新麻烦：卡片本身可能被偷看 （信息泄露），卡片一旦发出去就很难作废（撤销困难）。这一章会带你一步步实现自包含 token， 并且看清楚它到底在用什么换什么。

💡 什么是 JWT

JSON Web Token（JWT）是一种标准化的自包含安全 token 格式。它把一组关于用户的"声明" （claims，比如用户名、过期时间）编码成一个 JSON 对象，再加上一个描述格式的 header， 整体用密码学手段防篡改（还可以加密）。因为是标准，几乎所有编程语言都有现成的 JWT 库， 很多 Web 框架也内置了对它的支持。

6.1把 token 状态存在客户端

自包含 token 的核心想法很简单：不把 token 的状态（用户名、过期时间等）存进数据库， 而是直接把这些字段序列化成一个 JSON 对象，再做 Base64url 编码，编码结果本身就是 token ID。 服务器收到 token 后，只要解码、解析 JSON，就能拿回这次会话的所有属性，完全不用查库。

本章项目里的 JsonTokenStore 就是这么干的：用短字段名节省空间，比如 sub 表示 subject（用户名）、exp 表示过期时间——这两个字段名不是随便起的， 正是 6.2 节要讲的 JWT 标准字段。

⚠️ 光有 Base64 编码，等于没上锁

Base64 只是编码，不是加密，更不是签名——任何人都能解码看到内容，也能任意修改后重新编码。 如果 JsonTokenStore 单独使用，攻击者登录一次拿到自己的 token 后， 照样能在浏览器里把 {"sub":"alice",...} 改成 {"sub":"admin",...}， 再重新 Base64 编码发回去——服务器会照单全收。甚至不需要登录，攻击者可以凭空编一个 token。 

// 一个尚未加保护的 JSON token 解码后长这样：
{"sub":"test","exp":1559582129,"attrs":{}}

6.1.1 用 HMAC 保护 JSON token

解决办法并不新鲜：复用第 5 章为数据库 token 写的 HmacTokenStore。 服务器用一把只有自己知道的密钥，对编码后的 JSON 算一个 HMAC 认证标签（authentication tag）， 拼在 token 后面。客户端可以看到、也可以照抄这个 token，但改不出一个能通过验证的新标签—— 因为算标签需要密钥，而密钥从来没有离开过服务器。

💡 HMAC 到底防住了什么

HMAC（Hash-based Message Authentication Code）是一种带密钥的哈希算法。验证时服务器用同一把密钥 对拿到的 token 内容重新算一遍标签，和 token 里带的标签做恒定时间比较—— 只要有一位不一样就拒绝。这能防住"伪造 token"（spoofing）和"篡改 token"（tampering）， 但注意：它不加密，任何人拿到 token 都能直接 Base64 解码看到里面的明文内容。

要开启这套保护，只需要把 DatabaseTokenStore 换成 JsonTokenStore，再用 HmacTokenStore 包一层：

ch06/src/main/java/com/manning/apisecurityinaction/token/JsonTokenStore.java（节选）+ Main.java 装配代码
public class JsonTokenStore implements TokenStore {
    @Override
    public String create(Request request, Token token) {
        var json = new JSONObject();
        json.put("sub", token.username);
        json.put("exp", token.expiry.getEpochSecond());
        json.put("attrs", token.attributes);

        var jsonBytes = json.toString().getBytes(UTF_8);
        return Base64url.encode(jsonBytes);   // 只编码，还没签名
    }

    @Override
    public Optional<Token> read(Request request, String tokenId) {
        try {
            var decoded = Base64url.decode(tokenId);
            var json = new JSONObject(new String(decoded, UTF_8));
            var expiry = Instant.ofEpochSecond(json.getInt("exp"));
            var username = json.getString("sub");
            var attrs = json.getJSONObject("attrs");

            var token = new Token(expiry, username);
            for (var key : attrs.keySet()) {
                token.attributes.put(key, attrs.getString(key));
            }
            return Optional.of(token);
        } catch (JSONException e) {
            return Optional.empty();
        }
    }
}

import base64, hashlib, hmac, json, time

def b64url_encode(data: bytes) -> str:
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode()

def b64url_decode(s: str) -> bytes:
    padding = "=" * (-len(s) % 4)
    return base64.urlsafe_b64decode(s + padding)

MAC_KEY = settings.HMAC_SECRET_KEY  # 32 字节随机密钥，存在环境变量里

def create_token(username: str, expiry: int, attrs: dict) -> str:
    payload = {"sub": username, "exp": expiry, "attrs": attrs}
    body = b64url_encode(json.dumps(payload).encode())
    tag = hmac.new(MAC_KEY, body.encode(), hashlib.sha256).digest()
    return f"{body}.{b64url_encode(tag)}"

def read_token(token: str) -> dict | None:
    try:
        body, tag_b64 = token.rsplit(".", 1)
        expected = hmac.new(MAC_KEY, body.encode(), hashlib.sha256).digest()
        provided = b64url_decode(tag_b64)
        if not hmac.compare_digest(expected, provided):  # 恒定时间比较
            return None
        payload = json.loads(b64url_decode(body))
        if payload["exp"] < time.time():
            return None
        return payload
    except Exception:
        return None
src/tokens/jsonStore.ts（教学示例，用 Node crypto）
import { createHmac, timingSafeEqual } from "node:crypto";

const MAC_KEY = process.env.HMAC_SECRET_KEY!; // 32 字节随机密钥

function b64url(buf: Buffer) {
  return buf.toString("base64url");
}

export function createToken(sub: string, exp: number, attrs: object) {
  const body = b64url(Buffer.from(JSON.stringify({ sub, exp, attrs })));
  const tag = createHmac("sha256", MAC_KEY).update(body).digest();
  return `${body}.${b64url(tag)}`;
}

export function readToken(token: string) {
  const [body, tagB64] = token.split(".");
  if (!body || !tagB64) return null;

  const expected = createHmac("sha256", MAC_KEY).update(body).digest();
  const provided = Buffer.from(tagB64, "base64url");
  if (expected.length !== provided.length ||
      !timingSafeEqual(expected, provided)) {
    return null; // 篡改或伪造
  }
  const payload = JSON.parse(Buffer.from(body, "base64url").toString());
  if (payload.exp < Date.now() / 1000) return null;
  return payload;
}

6.2JSON Web Token

上面手写的 "HMAC + JSON" 方案，其实就是一个简化版的 JWT。JWT 在 2015 年被标准化， 在此基础上加了三样东西：一个描述算法等元数据的标准 header；一组含义固定的 标准 claims（比如 exp、sub）；以及一大堆可选的签名 / 加密算法。 因为是标准，几乎每种语言都有现成的库，很多网关、认证服务器、SDK 都能直接读懂 JWT—— 第 7 章要讲的 OpenID Connect 就是用 JWT 来传递用户身份的。

⚠️ JOSE header 是个"雷区"

JOSE（JSON Object Signing and Encryption，JWT 所依赖的标准家族）把"用什么算法验证"这个决定， 写在了 header 里由发送方自己声明——这违反了"永远不要信任未经验证的声明"这条基本原则， 因为你必须先读 header 才能知道怎么验证，可读 header 本身还没被验证过。 2015 年安全研究员 Tim McLean 就发现很多 JWT 库存在漏洞：攻击者可以把 alg 改成 none，库就直接跳过签名验证！更安全的做法是把算法和密钥绑定存在服务器上 （key-driven cryptographic agility），而不是相信 token 自己说的算法。 Nimbus 库通过要求你显式传入 JWSVerifier 对应的算法，从设计上堵住了这个漏洞。

6.2.1 标准 JWT claims

为了跨系统互通，JWT 定义了一组三字母的标准字段：

Claim名称作用
issIssuer谁签发了这个 JWT，通常是认证服务的 URI
audAudience这个 JWT 是给谁用的（一个或一组 API 的标识），接收方必须检查自己在不在列表里
iatIssued-At签发时间
nbfNot-Before在此时间之前无效
expExpiry过期时间，过期后必须拒绝
subSubject这个 token 是关于谁的，通常是用户名
jtiJWT ID唯一 ID，可用于检测重放（replay）

其中只有 iss、iat、sub 是在陈述事实，其余字段都是在给"这个 token 能怎么用"设限制，目的是防重放攻击（replay attack）：攻击者截获一个合法 token， 过后拿去重放，冒充发送者。设置较短的 exp 能缩小重放的时间窗口；aud 和 iss 能防止 token 被拿去别的 API 上重放，或者被"反射"回签发者自己（reflection attack）。

6.2.2 生成并校验标准 JWT

本章开始用真正的 JWT 库——Nimbus JOSE + JWT（Apache 2.0 协议的成熟 Java 库）。 签发时用 JWSSigner 计算签名，校验时用 JWSVerifier；两者都要配合具体的 JWSAlgorithm（比如 HMAC-SHA256 对应 HS256）一起使用，并且始终显式传入 要校验的 audience，确保这个 JWT 就是签给你这个 API 的。

ch06/src/main/java/com/manning/apisecurityinaction/token/SignedJwtTokenStore.java（节选）
public class SignedJwtTokenStore implements TokenStore {
    private final JWSSigner signer;
    private final JWSVerifier verifier;
    private final JWSAlgorithm algorithm;
    private final String audience;

    @Override
    public String create(Request request, Token token) {
        var claimsSet = new JWTClaimsSet.Builder()
                .subject(token.username)
                .audience(audience)
                .expirationTime(Date.from(token.expiry))
                .claim("attrs", token.attributes)
                .build();

        var header = new JWSHeader(JWSAlgorithm.HS256);
        var jwt = new SignedJWT(header, claimsSet);
        try {
            jwt.sign(signer);
            return jwt.serialize();
        } catch (JOSEException e) {
            throw new RuntimeException(e);
        }
    }

    @Override
    public Optional<Token> read(Request request, String tokenId) {
        try {
            var jwt = SignedJWT.parse(tokenId);
            if (!jwt.verify(verifier)) {
                throw new JOSEException("Invalid signature");
            }
            var claims = jwt.getJWTClaimsSet();
            if (!claims.getAudience().contains(audience)) {
                throw new JOSEException("Incorrect audience");
            }
            var expiry = claims.getExpirationTime().toInstant();
            var subject = claims.getSubject();
            var token = new Token(expiry, subject);
            var attrs = claims.getJSONObjectClaim("attrs");
            attrs.forEach((key, value) ->
                    token.attributes.put(key, (String) value));
            return Optional.of(token);
        } catch (ParseException | JOSEException e) {
            return Optional.empty(); // 从不暴露失败原因
        }
    }
}

import time

SECRET = settings.JWT_HMAC_SECRET  # 与 HMAC 方案共用一把对称密钥
AUDIENCE = "https://api.natter.example"

def create_jwt(username: str, expiry_ts: int, attrs: dict) -> str:
    claims = {
        "sub": username,
        "aud": AUDIENCE,
        "exp": expiry_ts,
        "attrs": attrs,

app.use("/spaces/*", async (c, next) => {

6.3加密敏感属性

数据库放在数据中心里，有防火墙和门禁保护，相对安全。可一旦把状态挪到客户端， token 里的任何个人信息——姓名、生日、职位、工作地点——都可能因为 token 泄露、被钓鱼、 或者被 XSS 偷走而暴露。有些属性甚至需要对用户本人保密（比如暴露了 API 内部实现细节的字段）。 这时候只签名不够了，还得加密。

💡 分组密码与工作模式

AES（Advanced Encryption Standard）是目前最主流的加密算法，属于分组密码（block cipher）：一次只能加密固定大小（16 字节）的一块数据。要加密更长的数据，需要选一种 工作模式（mode of operation）把多个分组拼起来。模式选错了后果很严重—— 书里举了个经典例子（"ECB 企鹅"）：用不安全的 ECB 模式加密一张图片，企鹅的轮廓在密文里依然清晰可见； 换成 CTR 模式，密文就变成完全看不出规律的噪声。

6.3.1 认证加密：光加密还不够

很多加密算法只保证机密性（别人读不到），不保证完整性 （别人改不了）。举个例子：如果你知道一个用 CTR 模式加密的 token 解密后是 user=brian 开头，即使你解不开密文，也能通过"翻转比特"的方式， 把它改成解密后是 user=admin——这就是密码学里说的选择密文攻击 （chosen ciphertext attack）。用 STRIDE 模型来说：单纯加密防的是"信息泄露"， 防不住"伪造"和"篡改"。

🕵️ 反面教材：UnauthenticatedEncryptionStore

项目源码里专门留了一个 UnauthenticatedEncryptionStore 类，用 AES/CTR 模式加密 token，但没有做任何完整性校验。它存在的唯一目的是给你演示"只加密不认证"有多危险—— 文档注释里明确写着"应该用 EncryptedTokenStore 或 EncryptedJwtTokenStore 代替它"。永远不要在生产代码里单独使用纯加密方案。

正确做法是使用认证加密（authenticated encryption）：把加密算法和 MAC 算法组合起来， 同时保证机密性和完整性。

方案机密性（防偷看）完整性（防篡改/伪造）结论
只签名（HMAC / 签名 JWT） ✗ 任何人可解码明文 ✓ 无法伪造或篡改 适合公开信息的 token，不能放敏感字段
只加密（如未认证的 AES/CTR） ✓ 无密钥读不到明文 ✗ 可被选择密文攻击篡改 反面教材，不要单独使用
认证加密 / AEAD（NaCl SecretBox、AES-GCM、JWE） ✓ 无密钥读不到明文 ✓ 篡改会被检测 推荐方案：机密性 + 完整性一步到位

6.3.2 用 NaCl 做认证加密

密码学细节很容易出错，所以近年来的趋势是用高层封装库把这些细节藏起来。 最有名的就是 Daniel Bernstein 设计的 NaCl（读作 "salt"）。本章用它的纯 Java 实现 Salty Coffee，核心是 SecretBox 类——一行代码做认证加密，一行代码解密验证。

ch06/src/main/java/com/manning/apisecurityinaction/token/EncryptedTokenStore.java
public class EncryptedTokenStore implements TokenStore {
    private final TokenStore delegate;
    private final Key encryptionKey;

    @Override
    public String create(Request request, Token token) {
        var tokenId = delegate.create(request, token);
        return SecretBox.encrypt(encryptionKey, tokenId).toString();
    }

    @Override
    public Optional<Token> read(Request request, String tokenId) {
        var box = SecretBox.fromString(tokenId);
        var originalTokenId = box.decryptToString(encryptionKey);
        return delegate.read(request, originalTokenId);
    }

    @Override
    public void revoke(Request request, String tokenId) {
        var box = SecretBox.fromString(tokenId);
        var originalTokenId = box.decryptToString(encryptionKey);
        delegate.revoke(request, originalTokenId);
    }
}

tokens/encrypted_store.py（用 cryptography 库的 AESGCM，标准 AEAD 实现）
import os, json
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

# 256-bit 密钥，与 HMAC/签名密钥分开保存（专钥专用原则）
ENC_KEY = settings.AES_GCM_KEY  # 32 字节
aesgcm = AESGCM(ENC_KEY)

def encrypt_token(inner_token_id: str) -> str:
    nonce = os.urandom(12)  # 96-bit nonce，绝不能重用
    ciphertext = aesgcm.encrypt(nonce, inner_token_id.encode(), None)
    # GCM 的 ciphertext 已经内含认证标签
    return b64url_encode(nonce) + "." + b64url_encode(ciphertext)

def decrypt_token(token: str) -> str | None:
    try:
        nonce_b64, ct_b64 = token.split(".")
        nonce = b64url_decode(nonce_b64)
        ciphertext = b64url_decode(ct_b64)
        plaintext = aesgcm.decrypt(nonce, ciphertext, None)  # 篡改会抛异常
        return plaintext.decode()
    except Exception:
        return None  # 从不透露具体失败原因，防止 padding oracle 之类的信息泄露

const ENC_KEY = await crypto.subtle.importKey(
  "raw",
  Buffer.from(process.env.AES_GCM_KEY!, "base64"), // 256-bit 密钥
  "AES-GCM",
  false,

export async function encryptToken(innerTokenId: string): Promise {
  const nonce = crypto.getRandomValues(new Uint8Array(12)); // 绝不重用
  const ciphertext = await crypto.subtle.encrypt(
    { name: "AES-GCM", iv: nonce },
    ENC_KEY,
    new TextEncoder().encode(innerTokenId),
  );
  return `${b64url(nonce)}.${b64url(new Uint8Array(ciphertext))}`;
}

export async function decryptToken(token: string): Promise {
  try {
    const [nonceB64, ctB64] = token.split(".");
    const plaintext = await crypto.subtle.decrypt(
      { name: "AES-GCM", iv: b64urlDecode(nonceB64) },
      ENC_KEY,
      b64urlDecode(ctB64), // GCM 篡改会让 decrypt 直接抛异常
    );
    return new TextDecoder().decode(plaintext);
  } catch {
    return null; // 统一失败提示
  }
}

6.3.3 加密的 JWT（JWE）

NaCl 的 SecretBox 简单又安全，但它的编码格式不是标准，只适合"自产自销"—— 同一个 API 自己签发、自己校验。如果 token 要被多个团队、多种语言写的服务共享，标准格式就更有价值， 这就是 JOSE 里的 JSON Web Encryption（JWE）。

⚠️ GCM 的 nonce 千万不能重复

JOSE 目前提供两类认证加密算法：A128GCM 等（AES-GCM）和 A128CBC-HS256 等（AES-CBC + HMAC，即 Encrypt-then-MAC）。GCM 速度快，但如果同一个密钥下 nonce 重复了一次， 攻击者就能反推出 MAC 密钥，之后可以随意伪造 token——后果是灾难性的。本书作者更偏好直接加密场景下用 CBC+HMAC 组合，因为 nonce 复用的容错性更好；但如果每次加密都能保证生成全新的随机 nonce（比如 Web Crypto、AESGCM 库默认都是这样），GCM 依然是又快又好的选择。

ch06/src/main/java/com/manning/apisecurityinaction/token/EncryptedJwtTokenStore.java（节选）
public class EncryptedJwtTokenStore implements TokenStore {
    private final SecretKey encKey;

    @Override
    public String create(Request request, Token token) {
        var claimsBuilder = new JWTClaimsSet.Builder()
                .subject(token.username)
                .audience("https://localhost:4567")
                .expirationTime(Date.from(token.expiry));
        token.attributes.forEach(claimsBuilder::claim);

        var header = new JWEHeader(JWEAlgorithm.DIR,
                EncryptionMethod.A128CBC_HS256);
        var jwt = new EncryptedJWT(header, claimsBuilder.build());
        try {
            var encrypter = new DirectEncrypter(encKey);
            jwt.encrypt(encrypter);
        } catch (JOSEException e) {
            throw new RuntimeException(e);
        }
        return jwt.serialize();
    }

    @Override
    public Optional<Token> read(Request request, String tokenId) {
        try {
            var jwt = EncryptedJWT.parse(tokenId);
            var decryptor = new DirectDecrypter(encKey);
            jwt.decrypt(decryptor);   // 解密同时验证认证标签

            var claims = jwt.getJWTClaimsSet();
            if (!claims.getAudience().contains("https://localhost:4567")) {
                return Optional.empty();
            }
            var expiry = claims.getExpirationTime().toInstant();
            var token = new Token(expiry, claims.getSubject());
            // ... 提取其余自定义 claim
            return Optional.of(token);
        } catch (ParseException | JOSEException e) {
            return Optional.empty(); // 绝不透露解密失败的具体原因
        }
    }
}

from jwcrypto import jwe, jwt as jwcrypto_jwt, jwk
import json, time

# JWK 格式的对称密钥，alg 元数据和密钥绑在一起（key-driven agility）
ENC_KEY = jwk.JWK(kty="oct", k=b64url_encode(settings.AES_KEY_BYTES))

def create_encrypted_jwt(username: str, exp: int, attrs: dict) -> str:
    claims = {
        "sub": username,
        "aud": "https://api.natter.example",
        "exp": exp,
        **attrs,
    }
    token = jwcrypto_jwt.JWT(
        header={"alg": "dir", "enc": "A128CBC-HS256"},
        claims=claims,
    )
    token.make_encrypted_token(ENC_KEY)
    return token.serialize()

def read_encrypted_jwt(token_str: str) -> dict | None:
    try:
        token = jwcrypto_jwt.JWT(key=ENC_KEY, jwt=token_str)
        claims = json.loads(token.claims)
        if claims.get("aud") != "https://api.natter.example":
            return None
        if claims.get("exp", 0) < time.time():
            return None
        return claims
    except Exception:
        return None  # 不区分"格式错误"和"认证失败"，防止 padding oracle

import { EncryptJWT, jwtDecrypt } from "jose";

const ENC_KEY = Buffer.from(process.env.AES_DIRECT_KEY!, "base64"); // 16 字节 = A128CBC-HS256 所需

export async function createEncryptedJwt(
  username: string, exp: number, attrs: Record<string, unknown>,
) {
  return await new EncryptJWT({ ...attrs })
    .setProtectedHeader({ alg: "dir", enc: "A128CBC-HS256" })
    .setSubject(username)
    .setAudience("https://api.natter.example")
    .setExpirationTime(exp)
    .encrypt(ENC_KEY);
}

export async function readEncryptedJwt(token: string) {
  try {
    const { payload } = await jwtDecrypt(token, ENC_KEY, {
      audience: "https://api.natter.example",
    });
    return payload; // jwtDecrypt 内部已校验认证标签、exp、aud
  } catch {
    return null; // 统一失败，不暴露具体原因
  }
}
✅ 小结：三种保护方式怎么选

只需要"防篡改、内容可以公开" → 签名 JWT（JWS/HS256）就够了；只要 token 里有一丁点 用户不该看到、或者攻击者能利用的信息，就必须上认证加密（NaCl SecretBox、AES-GCM 或 JWE）。 永远不要单独使用不带认证的加密——这不是"更弱一点"的安全，而是"看起来安全实际上不安全"， 比明文更危险，因为它会让人误以为数据是安全的。

6.4用类型系统做安全的 API 设计

本章目前为止的设计是"kit of parts"（零件套装）风格：HmacTokenStore、 EncryptedTokenStore 这些类都可以任意组合、互相包裹。这样固然灵活， 但也很危险——只要有人不小心在 Main.java 里把 EncryptedTokenStore 这层包装注释掉，加密和完整性保护就都没了，代码却照样能编译通过、照样能跑。

🔒 原则：让不安全的代码写不出来

安全的 API 设计不应该只是"能写出安全代码"，而应该"很难写出不安全的代码"——因为开发者总会犯错。

解决办法是引入标记接口（marker interface）：一个不定义任何新方法、纯粹用来 表达"这个实现具备某种安全属性"的接口。项目里定义了 ConfidentialTokenStore（保证机密性）、 AuthenticatedTokenStore（保证不可篡改），再组合出一个 SecureTokenStore（两者都满足）。

from typing import Protocol, runtime_checkable

class TokenStore(Protocol):
    def create(self, request, token) -> str: ...
    def read(self, request, token_id: str) -> dict | None: ...
    def revoke(self, request, token_id: str) -> None: ...

@runtime_checkable
class ConfidentialTokenStore(TokenStore, Protocol):
    """标记：保证 token 内容不会被无密钥的人读到。"""

@runtime_checkable
class AuthenticatedTokenStore(TokenStore, Protocol):
    """标记：保证 token 不能被伪造或篡改。"""

class SecureTokenStore(ConfidentialTokenStore, AuthenticatedTokenStore, Protocol):
    """两者兼备，才是 TokenController 允许使用的类型。"""

class TokenController:
    def __init__(self, token_store: SecureTokenStore):
        # mypy 静态检查能挡住大部分误用；
        # 运行时可以再加一道 isinstance 断言兜底
        assert isinstance(token_store, SecureTokenStore)
        self.token_store = token_store

6.5处理 token 撤销

自包含 token 最大的软肋，就是撤销（revocation）。数据库 token 撤销很简单——删一行记录就行； 自包含 token 的状态全在客户端手里，服务器根本没地方"删"。

常见的几种应对思路：

  • 不管它：如果 token 本来就短命、API 也不涉及敏感数据，可以干脆不支持主动登出。但这适用范围很窄。
  • allowlist（白名单）：数据库里存一份"有效 token ID"列表，撤销时删掉对应记录；每次校验都要查一遍数据库确认 token 还在名单里。
  • blocklist（黑名单）：反过来，只在撤销时往数据库里加一条记录；平时校验只要确认没在黑名单里就行，条目在 token 过期后即可清理。
  • 按属性批量撤销：比如用户改密码时，让"这之前签发的所有 token"统统失效——只需要记一条"某用户在某时间点之前的 token 全部作废"，不用一条条记。
  • 短有效期 + 强制重新登录：牺牲一点用户体验换取安全性，第 7 章会讲 OAuth2 的 refresh token 如何优雅地实现这个模式。
📰 真实案例：Facebook 2018 年 9000 万 token 事件

2018 年 9 月，Facebook 因为一处 token 处理漏洞遭到攻击，事后不得不紧急撤销 9000 万个 access token，强制这些用户重新登录。如果当时用的是纯无状态 JWT、完全没有撤销机制，这次应急响应根本无法执行—— 这正是"纯自包含 token 看似解放了数据库，实则丢掉了应急能力"的活教材。

6.5.1 混合 token：自包含 + 一个可撤销的短 ID

本章给出的推荐方案是混合 token（hybrid token）：JWT 里大部分字段仍然自包含， 但额外塞一个数据库生成的 jti（JWT ID），这个 ID 对应数据库里的一行"allowlist"记录。 平时校验时先解密验证 JWT 本身的签名/加密（不查库），再拿 jti 去数据库确认它还没被撤销 （查一次库，但只查主键，很快）。这样既保留了"部分信息不用查库就能用"的优势， 又拿回了"随时能立即撤销"的能力——鱼与熊掌兼得。

ch06/.../EncryptedJwtTokenStore.java（加上 DatabaseTokenStore 做 allowlist 后的版本，节选）
public class EncryptedJwtTokenStore implements SecureTokenStore {
    private final SecretKey encKey;
    private final DatabaseTokenStore tokenAllowlist;

    @Override
    public String create(Request request, Token token) {
        // 数据库里只存一条"空壳"记录，换回一个短 ID
        var allowlistToken = new Token(token.expiry, token.username);
        var jwtId = tokenAllowlist.create(request, allowlistToken);

        var claimsBuilder = new JWTClaimsSet.Builder()
                .jwtID(jwtId)                       // 把短 ID 塞进标准的 jti claim
                .subject(token.username)
                .audience("https://localhost:4567")
                .expirationTime(Date.from(token.expiry));
        token.attributes.forEach(claimsBuilder::claim);

        var header = new JWEHeader(JWEAlgorithm.DIR, EncryptionMethod.A128CBC_HS256);
        var jwt = new EncryptedJWT(header, claimsBuilder.build());
        var encrypter = new DirectEncrypter(encKey);
        jwt.encrypt(encrypter);
        return jwt.serialize();
    }

    @Override
    public void revoke(Request request, String tokenId) {
        var jwt = EncryptedJWT.parse(tokenId);
        jwt.decrypt(new DirectDecrypter(encKey));   // 先验证 JWT 本身没被篡改
        var claims = jwt.getJWTClaimsSet();
        tokenAllowlist.revoke(request, claims.getJWTID());   // 再删数据库记录
    }

def create_hybrid_jwt(username: str, expiry) -> str:
    record = AllowlistedToken.objects.create(username=username, expiry=expiry)
    return create_encrypted_jwt(  # 复用 6.3.3 节的加密 JWT 实现
        username=username,
        exp=int(expiry.timestamp()),
        attrs={"jti": str(record.jti)},
    )

def read_hybrid_jwt(token: str) -> dict | None:
    claims = read_encrypted_jwt(token)
    if claims is None:
        return None
    jti = claims.get("jti")
    # 只做主键查询，非常快；不存在 = 已撤销
    if not AllowlistedToken.objects.filter(pk=jti).exists():
        return None
    return claims

def revoke_hybrid_jwt(token: str) -> None:
    claims = read_encrypted_jwt(token)  # 先验证签名/加密，防止越权撤销别人的 token
    if claims and "jti" in claims:
        AllowlistedToken.objects.filter(pk=claims["jti"]).delete()

src/tokens/hybridStore.ts（用 Redis 存 jti 白名单，撤销即 DEL）
import { randomUUID } from "node:crypto";
import { redis } from "../lib/redis"; // ioredis 客户端

export async function createHybridJwt(username: string, expirySec: number) {
  const jti = randomUUID();
  const ttl = expirySec - Math.floor(Date.now() / 1000);
  // allowlist：存在 = 有效；用 TTL 让记录跟 token 一起自然过期
  await redis.set(`token:${jti}`, username, "EX", Math.max(ttl, 1));

  return await createEncryptedJwt(username, expirySec, { jti }); // 复用 6.3.3 节实现
}

export async function readHybridJwt(token: string) {
  const claims = await readEncryptedJwt(token);
  if (!claims || !claims.jti) return null;

  const exists = await redis.exists(`token:${claims.jti}`);
  if (!exists) return null; // 不在 allowlist 里 = 已撤销
  return claims;
}

export async function revokeHybridJwt(token: string) {
  const claims = await readEncryptedJwt(token); // 先验证签名/加密
  if (claims?.jti) await redis.del(`token:${claims.jti}`);
}

// 改密码时批量撤销：给每个用户维护一个 SET 存所有 jti，
// 改密码时遍历该 SET 逐个 DEL，或记录一个 "早于此时间戳的 token 全部作废" 的标记
✅ allowlist 混合方案的三个额外好处

1) 一旦发生 Facebook 那样的安全事件，能立即批量撤销所有 token，而不用干等到期；
2) 就算数据库被拖库，攻击者拿到的也只是一堆随机 ID，伪造不出新 token（因为伪造还需要过 JWT 的签名/加密校验）；
3) 可以按敏感程度把字段分配到 JWT 或数据库——用户基本信息放 JWT 省一次查库， 像"最后活跃时间"这种频繁变化、用于空闲超时判断的字段则放数据库。

本章小结

机制解决什么问题本章对应的类
把状态编码进 JSON + Base64url去掉查数据库的开销JsonTokenStore
HMAC / 签名 JWT（JWS）防止 token 被伪造或篡改HmacTokenStore、SignedJwtTokenStore
认证加密（AEAD）/ 加密 JWT（JWE）防止客户端读到或篡改敏感字段EncryptedTokenStore（NaCl）、EncryptedJwtTokenStore（JWE）
只加密不认证（反例）——展示为什么这样不安全UnauthenticatedEncryptionStore
标记接口用类型系统防止误用不安全的组合ConfidentialTokenStore / AuthenticatedTokenStore / SecureTokenStore
混合 token（allowlist）让自包含 token 也能被立即撤销带 DatabaseTokenStore 的 EncryptedJwtTokenStore
  • 自包含 token 用 JSON 编码状态、Base64url 转成字符串，天然可以省掉数据库查询，但也天然不安全，必须加认证保护。
  • JWT/JOSE 是这套思路的标准化版本，好处是生态成熟，坏处是"kit of parts"设计给了攻击者可乘之机（比如 alg header 混淆攻击）——应该优先信任与密钥绑定的算法，而不是 token 自己声明的算法。
  • 敏感字段必须用认证加密（AEAD）保护，绝不能只加密不认证；NaCl SecretBox 和 JWE 都是现成、可靠的选择。
  • 用标记接口这类类型系统技巧，能把"这个组件是否安全"从人工审查变成编译器检查。
  • 纯无状态 token 撤销困难，混合方案（JWT + 数据库 allowlist 存 jti）在绝大多数场景下是最稳妥的默认选择。
