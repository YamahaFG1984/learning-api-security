第 3 章

为 Natter API 加固安全

给刚建好地基的 Natter 装上门禁：限流、认证、加密、审计、访问控制，一次到位。

设想你负责管理一栋刚建好的公寓楼。开业前，物业得先解决五件事：门口不能同时挤进无限多人，得有人拦一拦（限流）；每个进门的人都要刷身份证或门禁卡证明"你是谁"（认证）；对讲和门禁的通讯不能被楼道里的人截获（加密）；前台要记下谁在什么时间进了门、去了哪层，哪怕是被拦下的人也要记一笔（审计日志）；最后，不是每个住户都能进任何楼层——地下车库、机房、别人家的公寓都需要单独授权（访问控制）。

第 2 章里，我们把 Natter 这栋"楼"的地基和房间（业务逻辑）搭好了，但大门始终敞开——谁都可以自称任何人，也可以无限次地敲门。这一章，我们要把上面这五道门禁真正装上去，而且顺序很讲究：装反了，等于白装。

3.1用安全控制应对威胁

第 1 章介绍过 STRIDE 威胁模型的六类基本威胁：伪装（Spoofing）、篡改（Tampering）、抵赖（Repudiation）、信息泄露（Information Disclosure）、拒绝服务（Denial of Service）、越权（Elevation of Privilege）。本章要引入的五种安全机制（也叫安全控制，security control），刚好能一一对应地把这六类威胁堵住：

  • 限流：防止有人用海量请求把 API 拖垮 —— 对应拒绝服务。
  • 认证：确认用户真的是他自称的那个人 —— 对应伪装。
  • 加密（HTTPS）：保证传输中的数据不会被窃看或篡改 —— 对应信息泄露和篡改。
  • 审计日志：记录谁在何时做了什么 —— 对应抵赖（让人无法说"这不是我干的"）。
  • 访问控制：决定一个已认证的用户到底能不能做某件事 —— 对应信息泄露、篡改和越权。
💡 请求会依次经过这五道关卡

每个进入 Natter API 的请求，都会按固定顺序穿过这五个环节，最后才轮到真正处理业务的应用逻辑。顺序错了，安全性就会出漏洞——比如如果访问控制先于认证执行，你连"这个人是谁"都不知道，还怎么判断他有没有权限？

客户端 会直接拒绝请求（限流 / 访问控制） 认证（失败也放行） 业务逻辑 / 记录 数据库
⚠ 认证失败为什么不立即拒绝？

这是本章最容易让新手困惑的一点：认证环节即使发现用户名密码不对，也不会马上返回错误，而只是不在请求上标记"这是谁"。真正决定"能不能通过"的是后面的访问控制。这样设计是为了保证——即便是未认证、被拒绝的请求，也能完整地被审计日志记录下来，方便事后追查攻击行为。

3.2用限流保证可用性

拒绝服务攻击（Denial of Service，DoS）的目标很直接：让正常用户用不了你的 API。有的攻击发生在网络层——比如攻击者伪造大量 DNS 查询的返回地址，让全世界的 DNS 服务器把远比查询本身大得多的响应，一股脑发给受害者，这叫放大攻击；这类攻击通常要靠防火墙和专业的抗 DDoS 服务来挡。而应用层的 DoS（也叫 L7 DoS）就简单粗暴得多：攻击者发的每个请求本身都合法，只是发得比正常客户端快得多，硬生生把服务器资源耗尽。

💡 限流为什么要放在最前面

限流应该是请求进入 API 后遇到的第一个安全决策。因为认证、审计这些后续步骤本身也要消耗 CPU、内存和数据库连接，如果不先挡掉超量请求，攻击者只要发送合法但海量的请求，同样能拖垮你的服务器——哪怕每个请求最终都会被认证或访问控制拒绝。

Natter 用 Google 的 Guava 库实现了一个最朴素的限流器：RateLimiter.create(2.0d) 创建一个"每秒最多放行 2 个请求"的令牌桶，调用 tryAcquire() 非阻塞地尝试拿一个令牌，拿不到就立即用 halt(429) 拒绝，并带上 Retry-After 头告诉客户端该等多久再试。这个过滤器要注册在 main() 方法里所有其他过滤器之前。

ch03/src/main/java/com/manning/apisecurityinaction/Main.java（节选）
import com.google.common.util.concurrent.RateLimiter;

var rateLimiter = RateLimiter.create(2.0d);

before((request, response) -> {
    if (!rateLimiter.tryAcquire()) {
        halt(429);
    }
});
natter/middleware.py（教学示例，基于 django-ratelimit）
from django_ratelimit.core import is_ratelimited
from django.http import JsonResponse

class RateLimitMiddleware:
    """必须排在 MIDDLEWARE 列表最前面，先于认证/审计中间件执行。"""

    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        limited = is_ratelimited(
            request, group="natter-api", key="ip",
            rate="2/s", increment=True,
        )
        if limited:
            response = JsonResponse(
                {"error": "rate limit exceeded"}, status=429)
            response["Retry-After"] = "2"
            return response
        return self.get_response(request)

# settings.py
MIDDLEWARE = [
    "natter.middleware.RateLimitMiddleware",  # 放在第一位
    "django.middleware.security.SecurityMiddleware",
    ...
]
src/index.ts（使用 hono-rate-limiter）

✅ 纵深防御：网关限流 + 服务器限流 双保险

生产环境里，限流通常先在负载均衡器或 API 网关（比如 HAProxy、Nginx、Envoy）这一层做，避免多余流量打到应用服务器。但即便有网关限流，也建议在每台服务器内部再加一层，这样即使网关配置错误或被绕过，单台服务器依然有自保能力。这是纵深防御（defense in depth）原则的典型体现：任何单一防线失效都不应导致整体沦陷。

3.3认证防止身份伪造

认证要回答的问题只有一个：这个请求真的是它自称的那个用户发的吗？在此之前，Natter 的 Create Space 接口只是简单地信任请求体里的 owner 字段，Post Message 接口信任 author 字段——任何人都可以在请求里填别人的用户名，冒充对方发消息。

3.3.1 HTTP Basic 认证

API 没有网页表单，所以最简单的做法是用 HTTP 标准的 Basic 认证方案（RFC 7617）：客户端把 用户名:密码 拼成一个字符串，用 Base64 编码后放进 Authorization 请求头：

Authorization: Basic ZGVtbzpjaGFuZ2VpdA==

解码后就是 demo:changeit。

🚨 Base64 不是加密，是编码

Base64 只是一种可逆的文本编码方式，任何人拿到这段字符串都能在几毫秒内还原出原始密码，跟明文传输几乎没有区别。HTTP Basic 认证必须配合 HTTPS 使用，否则密码会在网络上裸奔——这也是 3.4 节要解决的问题。

3.3.2 用 Scrypt 安全存储密码

就算传输是安全的，密码也不能明文存进数据库——数据库一旦泄露，所有用户的密码就全没了。正确做法是存密码哈希：把密码喂给一个单向的哈希函数，存下算出来的固定长度字符串，登录时对用户输入的密码做同样的运算，比较结果是否相同。

💡 为什么不能直接用 MD5/SHA-256 哈希密码

普通哈希函数（如 SHA-256）设计目标是"快"，但快恰恰是密码哈希最不想要的属性——攻击者租几台带 GPU 的机器，每秒能试几十亿个密码。Scrypt、Argon2、Bcrypt 这类密码哈希算法反其道而行之，故意设计得很"重"：既要花大量 CPU 时间，还要占大量内存（这叫 memory-hard），把攻击者的暴力破解速度从每秒十亿次砸到每秒几千次。此外还要给每个密码加上随机的盐值（salt），防止攻击者预先算好一张"彩虹表"来查表破解。Scrypt 生成的哈希字符串里已经自带了盐值和参数，验证时无需额外存储。

用户表的结构很简单，只存用户名和密码哈希：

CREATE TABLE users(
    user_id VARCHAR(30) PRIMARY KEY,
    pw_hash VARCHAR(255) NOT NULL
);
GRANT SELECT, INSERT ON users TO natter_api_user;

3.3.3 / 3.3.4 注册用户

注册接口做三件事：校验用户名格式和密码长度、用 Scrypt 计算哈希、把用户名和哈希写进数据库。

ch03/src/main/java/com/manning/apisecurityinaction/controller/UserController.java
public class UserController {
    private static final String USERNAME_PATTERN =
            "[a-zA-Z][a-zA-Z0-9]{1,29}";

    public JSONObject registerUser(Request request,
            Response response) throws Exception {
        var json = new JSONObject(request.body());
        var username = json.getString("username");
        var password = json.getString("password");

        if (!username.matches(USERNAME_PATTERN)) {
            throw new IllegalArgumentException("invalid username");
        }
        if (password.length() < 8) {
            throw new IllegalArgumentException(
                    "password must be at least 8 characters");
        }

        var hash = SCryptUtil.scrypt(password, 32768, 8, 1);
        database.updateUnique(
                "INSERT INTO users(user_id, pw_hash)" +
                        " VALUES(?, ?)", username, hash);

        response.status(201);
        response.header("Location", "/users/" + username);
        return new JSONObject().put("username", username);
    }
}
users/views.py（Django，密码哈希用内置 ScryptPasswordHasher）
import re, json
from django.http import JsonResponse
from django.contrib.auth.hashers import make_password
from .models import NatterUser

USERNAME_RE = re.compile(r"^[a-zA-Z][a-zA-Z0-9]{1,29}$")

def register_user(request):
    body = json.loads(request.body)
    username = body["username"]
    password = body["password"]

    if not USERNAME_RE.match(username):
        return JsonResponse({"error": "invalid username"}, status=400)

            status=400)

    pw_hash = make_password(password, hasher="scrypt")

    response = JsonResponse({"username": username}, status=201)
    response["Location"] = f"/users/{username}"
    return response

src/routes/users.ts（Hono，密码哈希用 @node-rs/argon2）
import { Hono } from "hono";
import { hash } from "@node-rs/argon2";
import { db } from "../db";

const USERNAME_RE = /^[a-zA-Z][a-zA-Z0-9]{1,29}$/;
export const users = new Hono();

users.post("/users", async (c) => {
  const { username, password } = await c.req.json();

  if (!USERNAME_RE.test(username)) {
    return c.json({ error: "invalid username" }, 400);
  }
  if (password.length < 8) {
    return c.json(
      { error: "password must be at least 8 characters" }, 400);
  }

  const pwHash = await hash(password); // Argon2id，自带随机 salt
  await db.insertInto("users")
    .values({ user_id: username, pw_hash: pwHash })
    .execute();

  c.header("Location", `/users/${username}`);
  return c.json({ username }, 201);
});

3.3.5 认证用户

登录校验的逻辑写在一个 before 过滤器里：解析 Authorization 头、Base64 解码、按冒号切出用户名密码、查库拿哈希、用 Scrypt 校验。如果一切吻合，就把用户名写进请求属性 subject；不吻合就什么都不做——按照 3.1 节的原则，这里不会直接拒绝请求。

ch03/src/main/java/com/manning/apisecurityinaction/controller/UserController.java
public void authenticate(Request request, Response response) {
    var authHeader = request.headers("Authorization");
    if (authHeader == null || !authHeader.startsWith("Basic ")) {
        return;
    }

    var offset = "Basic ".length();
    var credentials = new String(Base64.getDecoder().decode(
            authHeader.substring(offset)), StandardCharsets.UTF_8);

    var components = credentials.split(":", 2);
    if (components.length != 2) {
        throw new IllegalArgumentException("invalid auth header");
    }

    var username = components[0];
    var password = components[1];

    if (!username.matches(USERNAME_PATTERN)) {
        throw new IllegalArgumentException("invalid username");
    }

    var hash = database.findOptional(String.class,
            "SELECT pw_hash FROM users WHERE user_id = ?", username);

    if (hash.isPresent() && SCryptUtil.check(password, hash.get())) {
        request.attribute("subject", username);
    }
}

// Main.java
before(userController::authenticate);
users/auth.py（自定义 DRF BasicAuthentication，验证失败不抛异常，只返回 None）
from rest_framework.authentication import BasicAuthentication
from django.contrib.auth.hashers import check_password
from .models import NatterUser

class NatterBasicAuthentication(BasicAuthentication):
    def authenticate_credentials(self, userid, password, request=None):
        try:
            user = NatterUser.objects.get(user_id=userid)
        except NatterUser.DoesNotExist:
            return None  # 不在此处拒绝，交给下游 permission_classes 判断

        if not check_password(password, user.pw_hash):
            return None

        return (user, None)  # request.user = user，可作为 subject 使用

# settings.py
REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": [
        "users.auth.NatterBasicAuthentication",
    ],
}
src/middleware/auth.ts（Hono 自定义中间件，用 @node-rs/argon2 校验）
import type { Context, Next } from "hono";
import { verify } from "@node-rs/argon2";
import { db } from "../db";

export async function authenticate(c: Context, next: Next) {
  const authHeader = c.req.header("Authorization");

  if (authHeader?.startsWith("Basic ")) {
    const decoded = atob(authHeader.slice(6));
    const [username, password] = decoded.split(":");

    if (/^[a-zA-Z][a-zA-Z0-9]{1,29}$/.test(username ?? "")) {
      const user = await db.selectFrom("users")
        .select("pw_hash")
        .where("user_id", "=", username)
        .executeTakeFirst();

      if (user && await verify(user.pw_hash, password)) {
        c.set("subject", username); // 供后续中间件读取
      }
    }
  }
  await next(); // 无论认证是否成功都放行
}

app.use("*", authenticate);

3.4用加密保护数据隐私

认证解决了"你是谁"的问题，但请求和响应本身仍然裸奔在网络上。想象你在咖啡店蹭 WiFi，用刚才的 Basic 认证登录 Natter——同一个热点里的任何人，只要抓个包，Base64 解码一下就拿到了你的密码。这就是为什么加密要跟认证配套出现：一个安全漏洞常常会连锁触发另一个。

3.4.1 启用 HTTPS

HTTPS 就是跑在 TLS（Transport Layer Security）之上的普通 HTTP。配置好之后，对 API 的业务代码几乎是透明的——它看到的还是正常的请求和响应，只是这一切现在被加密和完整性保护包裹起来。开发环境可以用 mkcert 生成一个本机浏览器信任的证书：

mkcert -install
mkcert -pkcs12 localhost   # 生成 localhost.p12，默认密码 changeit
⚠ 不要用 -k / --insecure 关闭证书校验

开发时嫌证书麻烦，直接跳过校验看起来很省事，但这个习惯一旦带进生产环境，就等于让 TLS 的核心保证形同虚设——客户端将无法判断自己连接的到底是不是真正的服务器。宁可花几分钟正确签发证书，也不要图省事关闭校验。

3.4.2 严格传输安全（HSTS）

API 通常不需要兼容"先访问 HTTP 再跳转 HTTPS"这种网页时代的老习惯——直接拒绝明文请求即可。如果确实有浏览器会直连你的 API，可以加一个 Strict-Transport-Security 响应头，告诉浏览器"以后任何时候都只准用 HTTPS 访问我"：

response.header("Strict-Transport-Security", "max-age=31536000");

3.5审计日志保证可追责

可追责性（accountability）说白了就是：出了问题，能查出是谁干的、什么时候干的。做法很朴素——把每个操作都记进一张日志表。审计日志要放在认证之后（这样才知道是谁），访问控制之前（这样被拒绝的请求也能留痕，因为大量失败尝试本身就是攻击的信号）。

Natter 把审计拆成两个过滤器：请求刚进来时先写一条记录（哪怕后面处理崩溃了，这条记录也在），请求处理完之后再写一条带状态码的记录，两条记录靠同一个 audit_id 关联起来。

CREATE TABLE audit_log(
    audit_id INT NULL,
    method VARCHAR(10) NOT NULL,
    path VARCHAR(100) NOT NULL,
    user_id VARCHAR(30) NULL,
    status INT NULL,
    audit_time TIMESTAMP NOT NULL
);
CREATE SEQUENCE audit_id_seq;
GRANT SELECT, INSERT ON audit_log TO natter_api_user;
✅ 谁来管审计日志？——职责分离

审计日志本身就是敏感数据，通常应该只对少数"审计员"开放，而且这些人最好不是系统管理员本人——因为管理员账号权限最大，恰恰最需要被别人盯着。这条原则叫职责分离（separation of duties）：任何有能力作恶的操作，都不应该由同一个人既能执行又能审查。本章的 /logs 接口为了演示方便没有加访问控制，生产环境务必锁起来。

3.6访问控制

认证只解决了"你是谁"，HTTPS 保护了传输，审计日志记住了一切——但目前任何登录用户都能对任何 space 为所欲为：读别人的消息、冒充别人发消息、甚至删掉别人的帖子。是时候加上真正的访问控制了。

3.6.1 强制认证

最基本的访问控制规则是"必须登录"。实现方式是检查 subject 属性是否存在，不存在就返回 401 Unauthorized，并带上 WWW-Authenticate 头告诉客户端该怎么认证。

💡 401 和 403 到底怎么选

401 Unauthorized：服务器不知道你是谁（没提供凭证，或凭证不对），错误的说法但标准就是这么起名的。403 Forbidden：服务器知道你是谁，但你没权限做这件事。简单记：401 是"先证明你是谁"，403 是"我知道你是谁，但不行"。

3.6.2 访问控制列表（ACL）

"登录了就能做任何事"对社交 App 来说显然不合适。Natter 用一张访问控制列表（Access Control List，ACL）记录"谁在哪个 space 里有什么权限"，权限用 r（读）、w（写）、d（删除，仅版主）三个字符的组合表示。

✅ 最小权限原则（POLA）

不要因为"方便"就把所有权限都给所有人。最小权限原则（Principle of Least Authority）要求：每个用户或进程只应该拥有完成本职工作所必需的最少权限。权限给多了会增加破坏面，给少了用户又会想方设法绕过限制——这正是我们接下来要看到的越权漏洞的根源。

CREATE TABLE permissions(
    space_id INT NOT NULL REFERENCES spaces(space_id),
    user_id VARCHAR(30) NOT NULL REFERENCES users(user_id),
    perms VARCHAR(3) NOT NULL,
    PRIMARY KEY (space_id, user_id)
);

3.6.3 在 Natter 中实现访问控制

与其在每个 controller 方法里手写权限判断，不如写一个过滤器工厂：给定 HTTP 方法和所需权限，返回一个通用的过滤器。这样访问控制的逻辑集中在一处，业务代码可以专心处理业务本身。

public Filter requirePermission(String method, String permission) {
    return (request, response) -> {
        if (!method.equalsIgnoreCase(request.requestMethod())) {
            return;
        }
        requireAuthentication(request, response);

        var spaceId = Long.parseLong(request.params(":spaceId"));
        var username = (String) request.attribute("subject");

        var perms = database.findOptional(String.class,
                "SELECT perms FROM permissions " +
                        "WHERE space_id = ? AND user_id = ?",
                spaceId, username).orElse("");

        if (!perms.contains(permission)) {
            halt(403);
        }
    };
}

from rest_framework.permissions import BasePermission
from .models import Permission

class HasSpacePermission(BasePermission):
    required = ""  # 子类覆盖： 'r' / 'w' / 'd'

    def has_permission(self, request, view):
        if not request.user or not request.user.is_authenticated:
            return False
        space_id = view.kwargs["space_id"]
        perms = Permission.objects.filter(
            space_id=space_id, user_id=request.user.user_id
        ).values_list("perms", flat=True).first() or ""
        return self.required in perms

src/middleware/acl.ts
import type { Context, Next } from "hono";
import { db } from "../db";

export function requirePermission(
  method: string, permission: "r" | "w" | "d") {
  return async (c: Context, next: Next) => {
    if (c.req.method !== method) return next();

    const subject = c.get("subject");
    if (!subject) return c.body(null, 401);

    const spaceId = c.req.param("spaceId");
    const row = await db.selectFrom("permissions")
      .select("perms")
      .where("space_id", "=", spaceId)
      .where("user_id", "=", subject)
      .executeTakeFirst();

    if (!row?.perms.includes(permission)) {
      return c.body(null, 403);
    }
    await next();
  };
}

3.6.5 避免权限提升攻击

🚨 一个只有"读"权限的用户，如何拿到"删除"权限？

如果添加成员的接口只要求调用者有 r 权限，那么一个只被授予"只读"的用户 demo2 可以：① 注册一个新账号 evildemo2；② 用自己的只读权限，把 evildemo2 添加进 space 并赋予 rwd 全部权限；③ 切换到 evildemo2 身份，删除别人的消息。这就是权限提升攻击（privilege escalation）：利用系统里的一个漏洞，把自己（或别人）的权限从低提到高。

修复思路有两种：① 限制"新授予的权限不能超过操作者自己拥有的权限"；② 干脆要求只有拥有全部权限（rwd，即 space 的所有者或版主）的人才能添加新成员。Natter 采用了更简单的第二种：

class AddMemberView(APIView):
    permission_classes = [CanManageMembers]

    def post(self, request, space_id):
        username = request.data["username"]
        perms = request.data["permissions"]
        if not re.match(r"^r?w?d?$", perms):
            return Response({"error": "invalid permissions"}, status=400)

        Permission.objects.create(
            space_id=space_id, user_id=username, perms=perms)
        return Response({"username": username, "permissions": perms})

⚠ "能不能做 X" 和 "能不能授权别人做 X" 是两件事

权限提升漏洞几乎总是出现在"某个操作本身权限要求较低，但这个操作又能间接产生更高权限的后果"的地方。添加成员、修改角色、生成邀请码、重置密码……凡是会改变别人权限的接口，都要单独想一遍：执行者自己的权限，是否真的覆盖了他将要授予别人的权限。

本章小结

安全机制解决的 STRIDE 威胁关键技术本章要点
限流拒绝服务（DoS）Guava RateLimiter，429 + Retry-After放在过滤器链最前面，服务端限流作为网关限流的最后一道保险
认证伪装（Spoofing）HTTP Basic + Scrypt 密码哈希认证失败不立即拒绝，只是不标记 subject，留给访问控制处理
加密信息泄露 + 篡改HTTPS/TLS + HSTSBasic 认证的明文密码必须配合 HTTPS，否则形同虚设
审计日志抵赖（Repudiation）请求前后各写一条记录，用 audit_id 关联连被拒绝的请求也要记录，日志本身要限制访问（职责分离）
访问控制信息泄露 + 篡改 + 越权基于 ACL 的 permissions 表凡是会授予他人权限的接口，都要检查是否可能被用来提升自己的权限

五道关卡装好之后，Natter 已经从一个"谁都能冒充谁"的裸奔 API，变成了一个有基本安全底线的服务：请求先被限流兜底，再确认身份，全程留痕，最后才按 ACL 判断能不能放行。但目前的认证方式还很原始——密码每次请求都要带着走一遍，也没有"登出"这回事。下一章会引入更贴近真实 Web 应用的会话 Cookie认证，看看如何在浏览器场景下把身份验证做得更省心、更安全。
